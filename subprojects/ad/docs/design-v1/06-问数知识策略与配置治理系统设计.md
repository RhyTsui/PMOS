# 问数知识策略与配置治理系统设计

## 1. 设计目标

本文承接：

- `04-数据查询与报表系统设计.md`
- `04A-MCP能力发现与问数归属矩阵.md`
- `05-问数系统性问题决策台账.md`
- `00A-待补知识清单.md`

本设计解决一个核心问题：问数系统里哪些东西应该写死在代码，哪些应该做成运行时配置，哪些应该封装在 MCP / Workflow / Tool，哪些应该放入知识库。

目标不是让知识库替代能力发现，也不是让大模型自由补参，而是形成可治理的四层事实来源：

1. 代码不变量：执行顺序、安全红线、状态机、Trace 字段、失败闭环。
2. 运行时策略：路由优先级、alias、默认值、Manifest 覆盖、Prompt 版本。
3. MCP / Workflow：真实业务数据、字典、项目权限、包状态、联调状态、可执行动作。
4. 知识库：术语解释、指标口径、SOP、方法论、历史 case。

## 2. 当前问题

### 2.1 旧方案的风险

旧方案容易把四类内容混在一起：

- 把业务术语放进 Prompt，导致每次模型理解不稳定。
- 把 MCP 已有能力误认为系统缺失，重复规划假能力。
- 把用户口语 alias 写死在代码，后续业务变化需要发版。
- 把实时项目数据或权限信息放进知识库，造成权限与数据安全风险。
- 把知识库检索结果当执行事实，绕过 MCP schema 和真实权限。

### 2.2 当前已纠偏的基础

当前已经具备以下工程基础：

- `ReportCapabilityManifest`：从运行态 MCP server / tool 生成问数能力清单。
- `report-capability-overrides.json`：支持对 tool 的报表域、字典依赖、路由词做人工覆盖。
- `ControlledGlossaryIndex`：从受控术语知识库同步结构化术语索引。
- `report-query-policy.json`：保存问数路由、schema adapter、capability、semantic defaults、alias。
- `ReportQueryPlan`：记录复合问数计划、子查询、待补 slot、证据引用和执行状态。
- `ReportAnswerComposer`：只从结构化结果、Plan、Evidence、质量检查生成答案。
- 失败 Case：硬失败、缺能力、工具失败时进入需求池，缺用户字段时继续追问。

当前缺口是：策略、知识和后台配置的产品化治理还不完整，尤其是 alias 的维护入口、术语同步目标、MCP 样本校验和连弩用例回传。

## 3. 事实来源分层

### 3.1 必须写进代码

代码只承载不应该被运营配置随意改变的系统约束：

- 路由执行顺序：意图识别 -> 项目上下文编译 -> 术语归一化 -> 能力发现 -> slot 补齐 -> 字典解析 -> MCP 调用 -> 结果解析 -> 答案生成 -> Trace / Evidence / Case。
- 权限红线：不能绕过项目权限，不能用顶部项目覆盖用户明示项目，不能把无权项目数据展示给用户。
- 数据红线：不能编造报表数据，不能在 MCP 未成功调用时输出完成口吻。
- 状态枚举：`success`、`empty`、`failed`、`blocked`、`missing_input`、`not_configured`。
- 失败归因：MCP 未配置、endpoint 不通、tool 未发现、权限失败、入参不匹配、返回为空、结构变化、解析失败。
- Trace 字段：`manifest_version`、`capability_id`、`candidate_tools`、`glossary`、`query_plan`、`preflight`、`resolved_filters`、`tool_chain`、`failure_case_id`。
- 测试门禁：P0 tool mismatch / not selected 必须阻断。

### 3.2 应该做成运行时配置

运行时配置承载可变业务策略：

- 路由规则：`tool_selection_rules` 的优先级、include terms、exclude terms、tool keywords。
- Schema adapter：不同报表 tool 的默认入参，例如 `promotionSource`、`timeType`、`dataType`、`retentionType`。
- Capability 配置：业务报表、媒体字典、终端字典、团队字典、应用类型字典、账户字典、包体字典、优化师字典、项目查找、知识库补充。
- Alias 配置：媒体、终端、团队、应用类型、账户、包体、优化师的自然语言表达。
- Manifest override：某个 tool 属于哪个报表域、依赖哪些字典、补充哪些 route terms。
- 兜底文案：缺字段追问、能力缺失、失败 case 提示、下一步建议模板。

当前运行时配置位置：

- `.runtime/zhitou-chat/report-query-policy.json`
- `.runtime/zhitou-chat/report-capability-overrides.json`
- `.runtime/zhitou-chat/controlled-glossary-index.json`

### 3.3 应该封装在 MCP / Workflow / Tool

这些是系统执行事实来源，不应该写入知识库或 Prompt：

- 报表数据：日报、周报、月报、小时报表、ROI、留存、素材。
- 字典数据：项目、应用、媒体、终端、团队、应用类型、账户、包体、优化师。
- 项目权限：用户可见项目、项目动态权限、跨项目范围。
- 包状态：上报检查、等待提审、等待媒体后台更新、联调中、联调成功、联调失败。
- 自动化任务：定时报表、调度任务、联调任务、Workflow 执行状态。
- 真实动作：创建任务、触发联调、调用包服务、获取下载地址、生成 case。

### 3.4 应该放入知识库

知识库承载解释型、背景型、SOP 型内容：

- 内部术语解释和行业表达差异。
- 指标口径、公式、口径来源、口径变更记录。
- 使用手册、排查 SOP、历史 case 总结。
- 非执行型方法论，例如行业投放方法论、趋势分析框架。
- 受控术语结构化 JSON 的源材料。

知识库不得作为：

- 项目权限事实来源。
- 报表结果事实来源。
- 当前可执行 tool 清单唯一来源。
- 业务状态机事实来源。
- 绕过 MCP schema 的执行依据。

## 4. 问数配置模型

### 4.1 `ReportQueryPolicy`

核心结构：

```ts
type ReportQueryPolicy = {
  schema_version: 1
  enabled: boolean
  lookup_tool_keywords: string[]
  trigger_terms: string[]
  exclude_terms: string[]
  require_chinese_project_name: boolean
  skip_when_app_id_present: boolean
  tool_selection_rules: ReportQueryToolSelectionRule[]
  schema_adapters: ReportQuerySchemaAdapter[]
  capabilities: ReportQueryCapabilityConfig[]
  semantic_defaults: ReportQuerySemanticDefaults
  updated_at: string
}
```

关键设计：

- `tool_selection_rules` 只决定候选路由权重，不决定能力事实。
- 能力事实必须来自 `ReportCapabilityManifest`。
- `schema_adapters` 只填可确定默认值，不猜测用户没说的业务筛选。
- `semantic_defaults.*_aliases` 只用于触发字典解析，最终 id 必须来自 MCP 字典返回。

### 4.2 `ReportCapabilityManifest`

核心结构：

```ts
type ReportCapabilityManifest = {
  manifest_version: string
  generated_at: string
  tools: ReportToolCapability[]
  dictionary_tools: ReportToolCapability[]
  warnings: CapabilityWarning[]
}
```

设计原则：

- 自动从 MCP tool name、description、input_schema 推断报表域和字典依赖。
- 过滤非问数执行 tool，例如配置检查、联调、归因诊断、模板预览、回传检查。
- 允许 `report-capability-overrides.json` 修正自动推断。
- unmatched override 必须进入 warning，避免配置失效不可见。

### 4.3 `ControlledGlossaryIndex`

受控术语索引用于“理解用户说的是什么”，不是执行事实：

```ts
type ControlledGlossaryIndex = {
  index_version: string
  terms: Array<{
    term_id: string
    canonical: string
    aliases: string[]
    route_terms: string[]
    slot_hints?: Record<string, unknown>
    source?: string
    priority?: number
  }>
}
```

设计原则：

- 只接受结构化 JSON / fenced JSON。
- 同步失败不覆盖旧索引。
- 命中的 `term_id`、alias、canonical、source、index_version 进入 Trace。
- 可辅助 alias 维护，但不能直接写入报表入参。

## 5. 问数执行设计

### 5.1 总链路

1. 输入用户问题和当前会话上下文。
2. 编译项目上下文，识别顶部默认项目、用户明示项目、跨项目意图和权限。
3. 使用 `ControlledGlossaryIndex` 生成归一化路由文本。
4. 读取运行态 MCP server / tool，生成 `ReportCapabilityManifest`。
5. 根据 Manifest + policy 选择候选报表 tool。
6. 解析日期、指标、维度、alias。
7. 对命中的 alias 调用对应字典 MCP。
8. 将字典 id 回填到报表 tool input。
9. 检查 required fields，缺用户不可推断字段时追问。
10. 调用真实报表 MCP。
11. 解析 rows、columns、quality_check、empty_diagnosis。
12. 生成 `ReportQueryPlan`、Trace、Evidence。
13. 使用 `ReportAnswerComposer` 输出受控答案。
14. 成功后给保存资产、定时报表、继续分析等下一步建议。
15. 硬失败或多轮不可完成时生成 Case。

### 5.2 字典解析链路

当前支持的字典：

| 筛选类型 | alias 配置 | MCP capability | 回填字段 |
|---|---|---|---|
| 媒体 | `media_aliases` | `media_dictionary` | `mediaId` |
| 终端 | `terminal_aliases` | `terminal_dictionary` | `osTypes` |
| 团队 | `team_aliases` | `team_dictionary` | `teamIds` |
| 应用类型 | `app_package_type_aliases` | `app_package_type_dictionary` | `appPackageType` |
| 账户 | `account_aliases` | `account_dictionary` | `accountId` |
| 包体 | `package_aliases` | `package_dictionary` | `pkgId` |
| 优化师 | `optimizer_aliases` | `optimizer_dictionary` | `optimizerIds` |

约束：

- 没有 alias 命中时，不主动扫描所有中文短语当作团队名或账户名。
- alias 命中但 appId 缺失时，不调用字典，先追问项目。
- alias 命中但字典 tool 缺失时，阻断报表调用并记录缺能力。
- 字典返回空时，阻断报表调用并要求用户确认名称或提供 id。

### 5.3 复合问数计划

当问题同时包含多个报表域，例如“看消耗、ROI、留存趋势”，系统生成 `ReportQueryPlan`：

- 主查询：根据优先级选择 primary question type。
- 子查询：ROI、留存、日报、素材等分别对应独立 tool。
- 执行：串行执行，逐个记录 input、row_count、status、message。
- 展示：先给总体结论，再按子查询分块展示，不能把不同口径强行合成一个表。
- 失败：部分失败时输出 `partial_success`，成功项仍展示，失败项给原因和下一步。

## 7. Trace 与证据设计

每次问数至少记录：

```ts
type ReportTrace = {
  intent_type: 'report_query'
  original_question: string
  normalized_question: string
  project_context: unknown
  manifest_version: string
  capability_id?: string
  candidate_tools: unknown[]
  glossary: {
    index_version: string
    matched_terms: unknown[]
  }
  query_plan: ReportQueryPlan
  preflight: ReportQueryPreflight
  resolved_filters: ReportResolvedFiltersSummary
  tool_chain: ToolCallStep[]
  failure_case_id?: string
}
```

验收要求：

- 任何回答里的数据都能追溯到具体 MCP tool 和 input。
- 任何缺能力都能追溯到 Manifest / policy。
- 任何术语归一化都能追溯到 `ControlledGlossaryIndex`。
- 任何字典 id 都能追溯到对应字典 tool。
- 任何失败 case 都能看到用户问题、候选能力、缺失 slot、已调用 tool、错误摘要。

## 9. 设计结论

问数系统的产品化路线应按以下判断推进：

- 能力事实优先来自 MCP Manifest，不来自知识库。
- 用户表达理解依赖受控术语和 alias，不依赖模型自由猜测。
- 业务数据和字典 id 必须真实调用 MCP 获取。
- 知识库主要负责解释、口径、SOP 和结构化术语来源。
- 后台配置是策略治理中心，但配置修改必须可审计、可回归、可回滚。
- 失败闭环不是兜底话术，而是继续追问、阻断错误执行、生成 Case、沉淀证据。
