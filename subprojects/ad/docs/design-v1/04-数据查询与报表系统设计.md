# 数据查询与报表系统设计

## 1. 对应需求

本设计对应：

- `docs/prd-v2.2/06-数据查询报表与定时报表PRD.md`
- `docs/prd-v2.2/09-我的资产与自动化任务中心PRD.md`
- `docs/prd-v2.2/20-对话路由需求PRD.md`
- `docs/design-v1/01-对话路由系统设计.md`
- `docs/design-v1/02-项目权限与跨项目上下文系统设计.md`

本文覆盖数据查询、数据分析、拼报表、报表草稿、报表模板和查询结果保存。定时报表创建、调度执行、数据延迟策略和自动化产物入资产将在 `05-定时报表与自动化任务系统设计.md` 中展开；本文只定义从查询或报表进入定时报表的出口契约。

## 2. 设计目标

数据查询与报表是一期 P0 的主闭环。目标不是让 Chat 看起来会分析，而是让用户从自然语言问数进入真实数据能力，并得到可追溯、可保存、可复用的结果。

这里的数据查询不是从零建设 MCP。报表 MCP / 广告 BI 数据分析能力已经在其它 Chat 或系统中使用过，当前设计的重点是把已有基础服务在小乔智投 Chat 中完整产品化接入：稳定路由、准确补参、权限过滤、真实调用、结构化解析、Evidence 展示、资产沉淀和后续动作建议。不能把“服务已存在”误写成“功能已闭环”，也不能把“Chat 已能调用一次”误写成“产品能力完整”。

本设计目标：

- `report_query` 能从自由对话正确路由到已上线或已可用的报表 MCP / 数据查询能力。
- 能力发现早于 slot 补齐，用于确认当前 Chat 绑定的工具、权限、配置和 schema 是否可执行。
- 项目解析使用 `effective_project_refs`，不能静默使用顶部项目。
- 数据必须来自 MCP / 智投接口 / 已校验上传数据，不由 Prompt 生成。
- 查询结果默认不入资产，用户保存后才入资产。
- 报表草稿默认不保存。
- 报表模板可跨项目复用，但运行时重新绑定项目和权限。
- 返回结果必须展示数据来源、更新时间、指标口径、质量检查和下一步建议。

## 3. 当前实现核对

当前已有基础：

- 报表 MCP / 广告 BI 数据分析能力不是空白能力，已有上线和复用基础。
- `report-query-orchestrator.ts` 已有真实报表查询链路。
- `executeReportQueryStep` 已能完成工具选择、能力预检、字典匹配、MCP 调用、结果归一化、空结果诊断和图表 `viz_spec` 生成。
- `ReportQueryResult` 已包含 `status`、`rows`、`columns`、`metrics`、`dimensions`、`date_range`、`quality_check`、`selection_trace`、`preflight`、`resolved_filters`、`empty_diagnosis`。
- `report-query-policy-store` 已有报表查询能力策略、工具选择规则和语义默认值。
- `report-template-store.ts` 已有报表模板、草稿 / 模板结果存储。
- `createReportDraftFromTemplate` 当前主动抛出 `REPORT_DRAFT_REAL_DATA_REQUIRED`，避免没有真实数据时生成假报表。
- `report-session` 已能把需求解析、模板候选和草稿生成尝试串起来，并记录 trace。
- `scheduled-task-store.ts` 已有定时任务对象基础。
- 运行态 `.runtime/zhitou-chat/mcp-servers.json` 中 `报表MCP` 已 connected，披露 47 个 tool，包含 `get_zt_ad_day_report`、`get_zt_hour_report`、`get_zt_ad_roi_report`、`get_zt_ad_mat_report`、`get_zt_ad_retention_report`、`list_all_apps` 和多类 `get_dict_zt_*` 字典工具。详见 `04A-MCP能力发现与问数归属矩阵.md`。

当前风险：

- 风险不在于 MCP 从零缺失，而在于小乔 Chat 对已有 MCP 的绑定、入参、权限、解析、展示和资产化闭环不完整。
- 项目权限和 `ProjectResolution` 尚未贯穿所有报表查询请求。
- 查询结果保存为资产的规则尚未形成统一对象契约。
- 报表草稿、模板结果、资产之间边界仍容易混淆。
- `report-template-store.ts` 中 `createdBy` 仍存在 `user-001` 默认值。
- `scheduled-task-store.ts` 中 `created_by` 仍存在 `user-001` 默认值，该问题在 05 中继续处理。
- 数据来源、更新时间、指标口径 Evidence 还没有统一展示契约。
- 报表模板跨项目复用时的运行时权限校验需要明确。
- 当前能力发现仍主要依赖已保存 tools 和关键词规则，未生成可审计的 `ReportCapabilityManifest`；因此已披露 MCP 能力可能没有被 Chat 稳定命中。

## 4. 核心产品规则

### 4.1 查询结果与资产边界

一次性查询结果是对话内结果，不默认进入资产。

进入资产的条件：

- 用户明确点击保存。
- 用户明确要求“保存这份结果”。
- 查询结果被转成正式报表。
- 查询结果被用于创建定时报表配置，后续产物由定时报表系统默认入资产。

不进入资产的情况：

- 仅在对话中查看一次结果。
- 报表草稿处于多轮调整中。
- MCP 返回失败或空结果，除非用户要求保存为排查证据或 Case。

### 4.2 报表草稿边界

报表草稿是临时工作态，不是资产。

草稿用途：

- 承接多轮调整。
- 试排指标、维度、排序和展示形式。
- 作为创建报表资产、报表模板或定时报表的候选输入。

草稿默认不保存。用户离开会话、重新开会话或不明确保存时，不应把草稿沉淀为资产。

### 4.3 报表模板边界

报表模板记录结构，不记录固定项目事实。

模板可以包含：

- 指标集合。
- 维度集合。
- 默认筛选条件。
- 时间窗口表达。
- 展示结构。
- 口径说明。
- 数据源要求。

模板不能绕过运行时权限。每次运行模板时都必须重新注入项目、时间和权限上下文。

### 4.4 数据真实性红线

Chat 和 Prompt 禁止：

- 编造数据。
- 编造指标口径。
- 编造数据更新时间。
- 编造 MCP 调用成功。
- 编造报表草稿行列。
- 把知识库召回当成真实数据查询结果。

当 Chat 侧绑定、配置、授权、入参或结果解析异常时，系统只能说明具体阻断点、返回边界、生成 Case 或建议修复绑定，不能把已有 MCP 能力误描述成整体缺失。

## 5. 系统流程

### 5.1 数据查询主流程

1. 用户用自然语言发起问数。
2. Route Engine 命中 `report_query` 候选意图。
3. Route Engine 查询能力注册，确认当前 Chat 可绑定的报表 MCP / 数据查询工具、schema、权限和启用状态。
4. Context Compiler 编译用户、角色、项目、会话、个人记忆和页面上下文。
5. Project Resolver 生成 `ProjectResolution`。
6. Slot Resolver 补齐或追问项目、时间、指标、维度和筛选条件。
7. 后端构造 `ReportQueryRequest`。
8. 数据查询 Skill 将请求适配为 MCP / 智投接口入参。
9. 已上线或已可用 MCP / 智投接口返回真实数据。
10. Orchestrator 归一化为 `ReportQueryResult`。
11. Chat 展示表格、图表、质量检查、来源、更新时间和下一步建议。
12. 用户可继续保存、转报表、转模板、创建定时报表或进入异常排查。

### 5.2 最小追问流程

追问只发生在影响执行或结果真实性的字段缺失时：

- 项目缺失且无法从上下文继承。
- 时间范围缺失且不能安全默认。
- 指标缺失或表达歧义。
- 维度缺失且用户目标依赖拆分维度。
- 媒体、终端、APPID 等筛选条件无法匹配。

可直接默认的字段必须在回答中提示：

- 用户问“昨天”时使用昨天。
- 用户问“近 7 天”时使用最近 7 天。
- 用户问“这个项目”时使用 `ProjectResolution` 确认后的当前项目。
- 用户只问 ROI 时，默认指标为 ROI，但要展示口径来源。

### 5.3 结果保存流程

1. 用户点击保存或明确要求保存结果。
2. 后端校验当前用户仍有结果中项目的可见权限。
3. 生成 `ReportAsset`。
4. 资产绑定 `project_binding`、来源查询、数据快照摘要、Evidence 和 Trace。
5. 我的资产按项目动态权限展示。

查询结果保存后，原始数据不应无限制复制。资产中至少保留可复现的查询条件、结果摘要、来源引用和 Trace；是否保存完整数据行由资产容量和合规策略决定。

### 5.4 转报表流程

1. 用户在查询结果上要求生成报表。
2. Chat 收集报表目标、展示结构、指标、维度和结论重点。
3. Workflow 生成 `ReportDraft`。
4. 用户可继续调整。
5. 用户确认保存时，生成正式报表资产。
6. 用户要求模板化时，生成或更新 `ReportTemplate`。

### 5.5 转定时报表出口

当用户说“以后每天生成”“定时发一下”“每天自动保存”时，04 只输出定时报表候选配置：

- 项目范围。
- 指标和维度。
- 报表模板或报表结构。
- 频率和执行时间候选。
- 仍需确认的数据延迟策略。

是否启用、如何调度、失败如何重试、产物如何自动入资产，由 05 定义。

## 6. 前端职责

前端负责：

- 展示数据查询结果表格和图表。
- 展示数据来源、更新时间、指标口径和质量检查。
- 展示空结果诊断和下一步建议。
- 提供保存结果、转报表、转模板、创建定时报表入口。
- 区分“查询结果”“报表草稿”“正式资产”“报表模板”。
- 在跨项目结果中展示部分不可见状态。
- 保存成功后在我的资产中可见。

前端禁止：

- 在 API 未成功前把结果标记为已保存。
- 把草稿显示为正式资产。
- 展示无权限项目数据。
- 隐藏数据来源或更新时间。
- 用静态 mock 数据补齐真实查询失败。

## 7. 后端职责

后端负责：

- 从登录态解析用户、角色和权限。
- 调用项目解析，生成 `ProjectResolution`。
- 查询能力注册、MCP 绑定状态、工具 schema 和报表查询策略。
- 构造 `ReportQueryRequest`。
- 调用数据查询 Skill / MCP。
- 归一化 `ReportQueryResult`。
- 生成质量检查、空结果诊断和下一步建议。
- 保存报表资产、模板和草稿。
- 写入 Trace、Evidence 和资产来源。

后端禁止：

- 信任顶部项目作为唯一项目事实。
- 在用户明示项目无权限时回退到顶部项目。
- 让 Prompt 生成报表结果行。
- 在 Chat 绑定、配置、授权、入参或解析失败时生成假草稿。
- 保存资产时绕过项目权限过滤。

## 8. Workflow / Skill / MCP 边界

### 8.1 Chat

Chat 负责：

- 识别问数意图。
- 承接最小追问。
- 解释结构化结果。
- 引导保存、报表化、模板化和定时化。

Chat 不负责：

- 直接查询数据库。
- 直接生成业务数据。
- 决定最终项目权限。

### 8.2 数据查询 Skill

数据查询 Skill 负责：

- 将自然语言槽位转换成结构化查询入参。
- 匹配指标、维度、媒体、终端和项目字段。
- 校验 MCP 入参。
- 解释 MCP 返回结构。

Skill 必须返回结构化结果，不能只返回自然语言结论。

### 8.3 报表 Workflow

报表 Workflow 负责：

- 管理多步骤报表生成状态。
- 调用数据查询 Skill。
- 组合多个查询结果。
- 生成报表草稿。
- 生成正式报表资产或模板候选。

### 8.4 MCP / 智投接口

MCP / 智投接口负责：

- 返回真实数据。
- 返回数据来源。
- 返回数据更新时间或数据可用时间。
- 返回错误码、权限错误和空结果。

MCP 不负责 Chat 展示，不负责资产保存。

产品化接入要求：

- 小乔 Chat 必须配置到真实报表 MCP 服务和 tool schema。
- Chat 侧不得使用 demo mode、静态 mock 或手写数据替代真实 MCP 结果。
- MCP 已存在时，失败原因应定位到绑定缺失、工具未启用、权限不足、入参不匹配、返回结构变化、结果为空或解析失败，而不是笼统写成“数据能力未接入”。
- 已被其它 Chat 使用过的 MCP 仍需要在小乔侧补齐项目权限、角色权限、Evidence、资产保存和 Trace 契约。

### 8.5 MCP 能力发现纠偏

当前系统不是完全没有能力发现。代码层已经存在以下基础：

- `mcp-server-store.ts` 能加载内置和运行态 MCP server / tool 配置。
- `mcp-discovery.ts` 支持通过 MCP `initialize`、`tools/list`、`tools/call` 做工具发现和调用。
- `report-query-orchestrator.ts` 已有 `selectReportTool`、能力预检、字典能力检查、MCP 调用和结果归一化。
- `report-query-policy-store.ts` 已配置 `business_report`、`media_dictionary`、`terminal_dictionary`、`project_lookup`、`knowledge_fallback` 等能力类型。

但这不等于问数能力发现已经产品化闭环。当前风险是：能力发现主要依赖 `listMcpServers()` 中已经保存的 tools 和关键词规则。如果真实生产 MCP 已披露更多 tool / schema，但没有被发现、保存、归类和映射到 `report_query` 能力清单，Chat 仍可能误判能力缺失，或者补参后选错 tool。

因此设计上必须把能力发现分为三层：

1. MCP 原生能力发现
   从当前绑定 MCP 的 tool name、description、input_schema、output_schema、错误码和权限字段生成 `McpCapabilityManifest`，并记录发现时间、server、tool、schema 版本和可调用状态。

2. Chat 路由映射能力
   把自然语言问题、业务术语、指标别名、维度别名、时间语义和项目上下文映射到已发现的 MCP 能力。这里可以使用规则、Prompt 分类和受控术语词典，但不能覆盖 MCP schema 的事实。

3. 编排后处理能力
   对 MCP 返回的结构化数据做排序、TopN、环比、差异、总计核对、条件分支和诊断候选生成。后处理能力必须标注依赖的原始字段和公式来源。

问数测试集反推需求时，禁止默认判定为 MCP 缺失。每一项必须先归属为：

- `mcp_native`：当前绑定 MCP 已直接披露并可调用。
- `chat_mapping_required`：MCP 有能力，但 Chat 需要补路由、slot、schema adapter、别名或项目权限映射。
- `orchestrator_postprocess`：MCP 返回基础数据，Chat / Orchestrator 需要做结构化计算。
- `ui_required`：后端已有结果，但前端需要表格、图表、来源、口径、下一步建议和 Trace 展示。
- `unknown_or_gap`：完成当前绑定 MCP 发现和 schema 核对后仍无法覆盖，才算真实能力缺口。

## 10. API / 事件 / Trace 契约

### 10.1 API

```ts
POST /api/xiaoqiao/report-query
POST /api/xiaoqiao/report-query/{id}/save
POST /api/xiaoqiao/report-session
POST /api/xiaoqiao/report-drafts
PATCH /api/xiaoqiao/report-drafts/{id}
POST /api/xiaoqiao/report-drafts/{id}/save-asset
POST /api/xiaoqiao/report-templates
PATCH /api/xiaoqiao/report-templates/{id}
```

现有接口可以继续兼容，但必须满足：

- 查询接口返回结构化 `ReportQueryResult`。
- 保存接口必须重新校验项目权限。
- 草稿接口不自动写资产。
- 模板运行时必须重新提供项目和权限上下文。

### 10.2 Trace

每次数据查询必须记录：

- 用户原文。
- `user_scope_key`。
- 角色和权限。
- `ProjectResolution`。
- 候选意图和最终意图。
- 能力发现结果。
- 缺失字段和追问。
- 数据查询 Skill 入参。
- MCP / 智投接口名称。
- MCP 入参和返回摘要。
- 数据更新时间。
- 指标口径 Evidence。
- 质量检查。
- 保存资产动作。
- 转报表、转模板或转定时报表动作。

### 10.3 Evidence

数据查询 Evidence 至少包含：

- 数据源引用。
- 数据更新时间。
- 指标口径来源。
- MCP 调用摘要。
- 权限过滤说明。
- 空结果或失败诊断。

## 11. Prompt 与配置边界

写进代码：

- 数据查询主流程。
- 能力发现前置。
- 项目解析和权限校验。
- 查询结果保存规则。
- 草稿默认不保存规则。
- 报表模板运行时权限校验。
- 防假数据红线。

写进配置：

- 报表查询能力注册。
- 工具选择规则。
- 指标、维度、媒体、终端别名。
- 默认时间范围策略。
- 报表模板定义。
- 图表展示规则。

写进 Prompt：

- 槽位结构化抽取。
- 报表结果解释。
- 空结果追问文案。
- 报表草稿叙述生成。
- 下一步建议生成。

Prompt 禁止：

- 生成真实数据行。
- 生成数据更新时间。
- 生成不存在的指标口径来源。
- 生成 MCP 成功状态。
- 把草稿说成资产。

## 12. 失败闭环

### 12.1 MCP 绑定或配置异常

说明当前 Chat 未绑定到可用报表 MCP、工具未启用、schema 不匹配或授权配置异常。不继续追问业务执行字段。生成配置 / 绑定修复 Case，并带上 server、tool、schema、权限和错误摘要。

### 12.2 项目无权限

阻断查询，不回退顶部项目，不展示历史缓存数据。

### 12.3 项目歧义

追问确认项目，不直接查询。

### 12.4 缺少关键字段

只追问影响执行的关键字段。可继承字段必须说明继承来源。

### 12.5 MCP 调用失败

展示失败原因、错误码、是否可重试和下一步建议。保留 Trace。

### 12.6 空结果

展示空结果诊断，说明是条件过窄、数据未就绪、权限范围、字段匹配失败还是接口空返回。

### 12.7 结果无法解析

不生成业务结论。展示“数据服务有返回但当前无法解析”，并生成排查记录。

### 12.8 保存资产失败

查询结果仍在当前会话展示，但不能显示已保存。提示用户稍后重试或生成 Case。

## 13. 验收场景

- 用户问“昨天 ROI”，当前项目明确时直接查询当前项目。
- 顶部项目为 A，用户明示 B 项目时查询 B，不查询 A。
- 用户明示无权限 B 项目时阻断，不回退 A。
- 用户问“这个项目近 7 天消耗”，系统继承当前项目并说明时间范围。
- 用户问“巨量和快手哪个好”，系统识别媒体维度并调用媒体字典或报表能力。
- 缺少 APPID 且需要媒体编号时，追问或阻断，不猜测。
- 报表 MCP 已在服务侧存在时，小乔 Chat 必须能通过能力注册发现并调用；如果调用失败，必须定位到绑定、配置、授权、入参或解析问题。
- 报表 MCP 绑定异常时，不生成数据，返回可修复的绑定问题。
- MCP 返回空表时，展示空结果诊断和建议。
- MCP 返回失败时，展示错误原因和可重试建议。
- 查询结果默认不进入我的资产。
- 用户保存查询结果后，我的资产出现对应资产。
- 报表草稿默认不保存。
- 用户保存草稿后才生成正式报表资产。
- 报表模板跨项目复用，运行时重新校验权限。
- 指标口径有内部来源标注。
- 图表来自 `viz_spec`，表格来自 `rows` 和 `columns`。
- 无权限项目内容在资产和历史会话中动态隐藏。

## 14. 测试集与验收分层

### 14.0 从测试集反推的需求归属与缺口

`智投Chat_广告业务（问数）测试集_预期精简版_v3.xlsx` 不是单纯验收清单，它反向暴露出 PRD 和系统设计必须补齐的需求。但这里的“补齐”不能简单理解为 MCP 功能缺失。大量取数、指标、维度和字典能力本身应优先归属到已披露的报表 MCP / 智投接口；小乔 Chat 侧更常见的缺口是能力发现没有把已披露 MCP schema 转成可路由、可补参、可调用、可展示的产品能力。

因此每条需求进入工程前必须先做归属判定：

- `mcp_native`：当前绑定 MCP 已直接支持。
- `chat_mapping_required`：MCP 支持，但 Chat 需要补路由规则、slot 解析、schema adapter、别名词典或项目权限映射。
- `orchestrator_postprocess`：MCP 返回基础数据，Orchestrator 负责排序、比较、汇总、派生计算或诊断候选。
- `ui_required`：后端结构化结果已具备，前端需要补结果卡片、表格、图表、Evidence、Trace 和下一步建议。
- `unknown_or_gap`：检查当前绑定 MCP tool / schema 后仍不能覆盖，才标记为真实能力缺口。

1. 报表类型识别需求
   系统必须识别日报、周报、月报、广告小时报表、媒体报表、自然量报表等报表类型，并把报表类型映射到正确 MCP tool、时间粒度、默认维度和口径。归属优先级：`mcp_native` + `chat_mapping_required`，如果 MCP 只提供日报基础 tool，周报 / 月报可能由 schema adapter 或聚合参数表达。

2. 日期语义解析需求
   系统必须支持自然日期、标准日期、连续区间、紧凑日期、上周、二月、同期、环比、小时段等表达。无效日期必须阻断或说明，不得静默改写。归属优先级：`chat_mapping_required`，MCP 只接收结构化时间字段。

3. 多维筛选与组合维度需求
   系统必须支持项目、媒体、团队、应用类型、终端、小游戏平台等维度的组合筛选，并支持“细分媒体 + 应用类型”“媒体 + 团队”“应用类型 + 团队”等组合拆分。归属优先级：`mcp_native` + `chat_mapping_required`，维度是否可用以当前 MCP schema 和字典 tool 为准。

4. 指标口径与派生指标需求
   系统必须支持激活、注册、消耗、折后消耗、折后现金消耗、首日 ROI、累计 ROI、30 日 ROI、第 2 日 ROI、留存、激活成本、转化率等指标。归属优先级：基础指标为 `mcp_native`，指标别名和内部口径为 `chat_mapping_required`，转化率等派生指标为 `orchestrator_postprocess`。派生指标必须由真实返回字段或明确公式计算，不得由 Prompt 猜测。

5. 排序、TopN 和比较需求
   系统必须支持“哪个最高”“哪个最低”“top3”“对比”“环比变化”“高多少”等分析型问法。归属优先级：`orchestrator_postprocess`，除非 MCP 明确提供排序 / 聚合参数。排序和比较必须基于结构化结果计算，并展示排序口径。

6. 多轮上下文与条件分支需求
   系统必须支持“第一轮查 A，第二轮那 iOS 呢”“如果 ROI 低于 20% 再查苹果广告”“如果注册用户留存更高，再告诉我高多少”等多轮继承和条件分支。归属优先级：`chat_mapping_required` + `orchestrator_postprocess`。分支条件必须写入 Trace。

7. 总计与明细一致性核对需求
   系统必须支持媒体明细与总计、维度汇总与总量之间的一致性核对，发现差异时输出差异金额、差异比例、可能原因和下一步排查建议。归属优先级：`orchestrator_postprocess`，依赖 MCP 返回总计和明细或可重复查询两类结果。

8. 权限与范围边界需求
   系统必须区分项目权限、团队权限、媒体范围和应用类型范围。归属优先级：Chat / 后端权限层 + MCP 权限错误解析。无权限时阻断，不回退其它项目；范围不存在时提示未匹配，不伪造空值为 0。

9. 空结果、无效输入和超时兜底需求
   系统必须区分无效日期、不存在媒体、数据为空、大范围查询超时、MCP 调用失败、返回无法解析等状态，并给出不同闭环。归属优先级：MCP 错误结构 + Chat 结果解析 + Case 生成。

10. 结果呈现格式需求
    系统必须支持日报格式、表格格式、对比格式、明细 + 汇总格式、口径说明格式。归属优先级：`ui_required` + 后端 `viz_spec`。格式选择不能只靠自然语言生成，必须与结果结构和前端组件能力绑定。

11. 问数转诊断需求
    当用户问“为什么 ROI 下降”时，系统不能只查数或只解释指标，应从问数结果进入异常诊断候选流程，保留查询证据并提出排查链路。归属优先级：路由 / Workflow 编排，可能继续调用诊断 MCP。

12. 可解释 MCP 调用需求
    系统必须能展示本次调用了哪个 MCP、哪个 tool、关键入参、返回摘要、过滤条件和数据来源，满足用户复核和连弩 Trace 回放。归属优先级：Trace / Evidence / UI，不是 MCP 本身的取数能力。
