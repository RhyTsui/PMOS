## 当前重点

- 顶部项目只是默认上下文，用户明示项目优先。
- 明示项目无权限时阻断，不回退顶部项目。
- 所有工具请求必须使用经过权限校验的项目上下文。
- 项目解析不得硬编码项目名、项目 ID 或示例 A/B。
- 个人记忆必须按登录用户隔离，不能使用 `user-001` 兜底。
- 通用知识库全员只读，个人知识库由用户配置 Key，二者不能混写。
- 数据查询必须调用真实 MCP / Skill，不得由 Prompt 生成数据。
- 查询结果默认不入资产，用户保存后才沉淀为资产；自动化产物默认入资产。
- 定时报表创建时必须确认数据延迟策略。
- 问数测试集反推项必须先核对运行态 MCP tool / schema，不得默认写成 MCP 缺失。
- 问数闭环必须按路由、项目、slot、字典、tool、调用、解析、后处理、UI 和建议分层验收。
- 已披露 MCP 能力必须生成能力矩阵，再进入路由、补参、执行、解析和 UI 验收。
- 知识库用于术语、口径、SOP 和方法论，不作为实时数据、权限和业务状态事实来源。
- 包交付是单项目能力，可交付投放必须由真实 Workflow / MCP 证据派生，Chat 不得自行生成包状态或联调结论。
- 包交付上报检查不通过时不得提示提审、后台更新或触发联调；单独触发联调也必须先确认上报检查通过。
- 异常排查必须调用真实诊断能力；没有 Evidence 的异常原因只能标记为待验证假设，不能作为确定结论。
- 指标解释必须内部结构化口径优先；知识库和外部资料只能补充，不能覆盖公司内部口径。
- 需求沟通必须先形成结构化草案并等待用户确认；创建 Case / 写入需求池必须调用真实服务并返回编号，不能把整理文案当成已提交。
- 所有业务能力必须先经过 CapabilityRegistry 和 Preflight；已上线 MCP / Skill / Workflow 不得被误判为缺失，未真实调用不得输出完成口吻。
- 资产与证据沉淀服务用户可见闭环，Trace 服务连弩回放和评测，两者必须分离设计、分离验收。
- 进入实施阶段前，所有“有条件充分”的模块必须补齐服务返回样本、字段枚举、UI 状态或 SDK 映射，不得用工程实现掩盖设计缺口。
