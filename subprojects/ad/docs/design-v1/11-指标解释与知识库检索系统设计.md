# 指标解释与知识库检索系统设计

## 1. 文档目的

本文定义小乔智投一期“指标解释与知识库检索”的系统设计，承接：

- `docs/prd-v2.2/08-异常排查需求沟通与指标解释PRD.md`
- `docs/prd-v2.2/18-意图路由知识库与能力闭环设计准入评估.md`
- `docs/prd-v2.2/19-个人记忆与知识库用户隔离需求设计.md`
- `docs/design-v1/03-个人记忆与知识库用户隔离系统设计.md`
- `docs/design-v1/06-问数知识策略与配置治理系统设计.md`
- `docs/design-v1/10-异常排查系统设计.md`

本文只覆盖指标、口径、字段、内部术语和知识检索类解释。异常原因诊断不在本文生成，需求整理不在本文生成。

本文重点解决：

- 指标解释必须内部口径优先，不能由大模型自由解释。
- 受控术语、内部口径库、通用知识库、个人记忆、个人知识库、外部资料如何分层。
- 路由前术语归一化与正式 RAG 检索如何边界清晰。
- 内部与外部冲突时如何处理。
- 指标解释结果如何带来源、组件、下一步建议和 Evidence。

## 2. 设计目标

指标解释是“可信口径服务”，不是通用百科问答。

目标：

- 用户问 ROI、激活、注册、付费、留存、回收、自然量等指标时，优先读取内部结构化口径。
- 用户问内部术语时，先做受控术语归一化，再检索通用知识库。
- 用户问个人保存过的说明时，可检索个人记忆和个人知识库，并明确标注来源。
- 外部资料只作为行业背景补充，不能覆盖内部口径。
- 指标解释必须展示内部口径、适用范围、数据来源、计算方式、差异说明和 Evidence。
- 无内部口径时，不能假装已有内部标准；应明确缺口，可进入指标需求确认或 Case。

## 3. 当前实现核对

### 3.1 已具备

当前系统已经具备：

- `metric-explainer-store.ts`：已有结构化指标解释配置和内置示例。
- `/api/xiaoqiao/admin/metric-explainers`：已有指标解释管理接口。
- `MetricExplainerRenderer`：已有指标解释 UI Schema 渲染基础。
- `metric_explainer_skill`：Skill Contract 已声明从后台结构化指标资料生成动态组件。
- `controlled-glossary-index.ts`：已有受控术语索引、知识库同步和归一化基础。
- `admin/controlled-glossary`：已有受控术语管理接口。
- `runtime-config` 和 `model-service-config/test`：已有通用知识库配置与连接测试基础。
- `user-memory-store`、`dataki-memory-sync`、`/api/xiaoqiao/memory`：已有个人记忆和同步基础。
- Chat 前端已有“保存到个人知识库”和知识来源展示基础。

### 3.2 当前缺口

当前仍缺少：

- 正式的 `MetricExplanationWorkflow`。
- 指标解释的来源优先级和冲突处理执行规则。
- 指标口径库、通用知识库、个人记忆、个人知识库、外部来源的统一 `KnowledgeSourceRef`。
- 指标解释和问数、异常排查之间的转接规则。
- “无内部口径”时生成指标需求或能力缺口 Case 的闭环。
- 外部联网补充的触发条件、来源约束和冲突提示。
- 指标解释 Trace / Evidence 契约。

## 4. 核心产品规则

### 4.1 内部口径优先

指标解释来源顺序：

1. 内部结构化指标口径库。
2. 内部通用知识库。
3. 个人记忆 / 个人知识库。
4. 外部公开资料。
5. 大模型通用语言组织。

规则：

- 内部口径存在时，最终解释必须以内口径为准。
- 外部资料只能补充行业背景、常见叫法和公开方法论。
- 内部与外部冲突时，明确提示“公司内部口径优先”。
- 没有内部口径时，不能把外部解释写成公司口径。

### 4.2 路由前只做轻量术语归一化

路由前可以调用 `ControlledGlossaryIndex`。

它负责：

- 标准词映射。
- 别名识别。
- 简称展开。
- 歧义项提示。
- 低置信度追问。

它不负责：

- 生成最终指标解释。
- 解释业务原因。
- 替代内部口径库。
- 替代工具返回。

### 4.3 正式解释走 MetricExplanationWorkflow

正式指标解释必须进入 `MetricExplanationWorkflow` 或 `metric_explainer_skill`。

Workflow 负责：

- 识别指标。
- 查询结构化指标解释。
- 补充内部知识库。
- 按需检索个人记忆。
- 按需补充外部资料。
- 生成 UI Schema 和文本解释。
- 输出来源和下一步建议。

### 4.4 项目数据不走知识库

以下问题不能由知识库直接回答：

- “A 项目昨天 ROI 多少”
- “B 项目激活为什么掉了”
- “这个包联调通过了吗”
- “某项目消耗和 BI 为什么对不上”

这些问题必须转入问数、异常排查或包交付。

指标解释只回答：

- 指标是什么。
- 怎么算。
- 适用于哪里。
- 与相近指标有什么差异。
- 口径来源是什么。
- 查询或排查时下一步该怎么做。

### 5.4 MetricExplainerUISchema

当前工程已有 `MetricExplainerUISchema`。设计上它是指标解释的前端契约，不是知识原文。

它应表达：

- 指标解释卡。
- 计算公式卡。
- 追踪 / 上报逻辑卡。
- 口径差异卡。
- 报表差异卡。
- 来源。
- 后续动作。

## 6. 来源分层

### 6.1 受控术语索引

用途：

- 路由前归一化。
- 指标别名识别。
- 内部简称识别。
- 低置信度追问。

示例：

- “回收” -> ROI / 回本 / 收入回收，可能需要结合上下文确认。
- “付费留存” -> 首日付费账号留存或付费用户留存，低置信度时追问。

### 6.2 内部结构化指标口径库

用途：

- 最权威的指标解释来源。
- 用于生成 MetricExplainerUISchema。
- 用于诊断前的口径对齐。
- 用于问数字段映射和指标需求判断。

当前可由 `metric-explainer-store.ts` 承接，后续可接后台口径库服务。

### 6.3 内部通用知识库

用途：

- SOP。
- 报表说明。
- 业务规则。
- 内部术语解释。
- 指标口径的长文本补充。

限制：

- 不能覆盖结构化指标口径。
- 不能回答实时项目数据。
- 不能生成工具执行结果。

### 6.4 个人记忆 / 个人知识库

用途：

- 用户保存过的口径说明。
- 用户个人偏好。
- 用户历史确认过的解释。
- 用户自己的工作备注。

限制：

- 只对本人可见。
- 不能覆盖公司内部口径。
- 不能覆盖项目权限。
- 不能作为实时业务事实。

### 6.5 外部资料

用途：

- 行业通用背景。
- 广告平台公开方法论。
- 公开术语解释。

触发条件：

- 用户明确要求行业解释或外部对比。
- 内部口径存在，但需要补充外部差异说明。
- 内部口径不存在，且用户接受“非公司口径”的通用解释。

限制：

- 必须标注来源。
- 不能覆盖内部口径。
- 不能写成公司事实。

## 7. 处理流程

### 7.1 总流程

```text
Chat
-> ControlledGlossaryIndex 轻量归一化
-> 路由到 help / metric_explanation
-> 能力发现
-> MetricExplanationWorkflow
-> 查询结构化指标口径
-> 检索内部通用知识库
-> 按需检索个人记忆 / 个人知识库
-> 按需外部补充
-> 生成 MetricExplainerUISchema
-> 输出来源、下一步和 Trace
```

### 7.2 指标定义解释

触发表达：

- “ROI 怎么算”
- “激活口径是什么”
- “注册数是什么意思”
- “首日付费账号留存怎么算”

流程：

1. 术语归一化识别指标候选。
2. 查询结构化指标口径。
3. 命中后生成定义、公式、适用范围和来源。
4. 如果命中多个指标，追问用户选择。
5. 如果未命中，进入 unsupported metric 流程。

### 7.3 指标差异解释

触发表达：

- “注册设备数和注册账号数有什么区别”
- “媒体后台 ROI 和智投 ROI 为什么不一样”
- “ROI 和 ROAS 是一个东西吗”

流程：

1. 识别对比对象。
2. 查询两个指标或两个报表来源的内部口径。
3. 输出差异类型、原因、用户可理解解释。
4. 如涉及项目具体数值，建议进入问数或异常排查。

### 7.4 内部术语解释

触发表达：

- “内部说的回收是什么意思”
- “自然量扣除是什么意思”
- “付费留存到底指什么”

流程：

1. 受控术语归一化。
2. 查询通用知识库和指标口径库。
3. 输出标准词、别名、适用范围。
4. 对歧义词先追问，不直接解释错方向。

### 7.5 无内部口径

流程：

1. 明确提示“当前未找到内部结构化口径”。
2. 如果通用知识库有补充，标注为补充说明。
3. 如果用户需要正式口径，转入 `metric_requirement_intake_skill`。
4. 可生成 `capability_not_connected` 或指标需求 Case。

## 8. Chat 交互策略

### 8.1 追问规则

需要追问的情况：

- 一个词命中多个内部指标。
- 用户问“回收”“成本”“自然量”等多义词。
- 用户要求解释项目数据异常，但未给项目或时间。
- 用户要求公司口径，但内部口径库未命中。

不需要追问的情况：

- 指标唯一命中且内部口径充分。
- 用户只问通用概念，且内部知识库已有标准解释。

### 8.2 回答结构

标准回答：

```text
结论：{指标是什么}
内部口径：{公司内部定义}
计算方式：{公式 / 聚合方式}
适用范围：{报表、媒体、项目类型}
容易混淆：{相近指标差异}
来源：{结构化口径库 / 知识库}
下一步：{查数据 / 排查异常 / 提口径需求}
```

### 8.3 冲突表达

内部与外部冲突时：

```text
公司内部口径以“{内部口径}”为准。外部资料中“{外部说法}”更偏行业通用定义，不能直接替代智投报表口径。
```

无内部口径时：

```text
当前没有查到这项指标的内部结构化口径。我可以先按通用解释说明它通常怎么理解，但不能把它标记为公司正式口径。需要的话我可以整理成指标口径需求。
```

## 9. Workflow / Skill / 服务边界

### 9.1 Chat 负责

- 识别指标解释意图。
- 调用术语归一化。
- 判断是否需要追问。
- 调用 MetricExplanationWorkflow。
- 展示解释结果、来源和下一步。

Chat 不负责：

- 生成公司内部口径。
- 修改指标口径。
- 用外部资料覆盖内部资料。
- 用知识库回答实时项目数据。

### 9.2 MetricExplanationWorkflow 负责

- 管理解释任务。
- 查询结构化口径。
- 检索内部知识库。
- 检索个人记忆或个人知识库。
- 按需调用外部检索。
- 生成 UI Schema。
- 处理无口径和来源冲突。
- 生成 Case 或指标需求草案。

### 9.3 Skill 负责

- `metric_explainer_skill`：读取结构化指标资料并渲染组件。
- `knowledge_answer_skill`：检索内部知识库并生成来源化解释。
- `metric_requirement_intake_skill`：未覆盖指标的需求收集。
- `report_query` 能力：用户要查具体数据时转入问数。
- `DiagnosisWorkflow`：用户要解释异常原因时转入排查。

### 9.4 知识库 / MCP / 外部服务负责

- 知识库服务负责检索，不负责权限判断。
- 小乔负责用户隔离、来源标注和优先级裁决。
- 外部检索只在允许场景下调用。

## 11. 前端设计

### 11.1 指标解释卡

必须展示：

- 指标名称。
- 别名。
- 内部定义。
- 业务含义。
- 适用场景。
- 计算方式。
- 口径差异。
- 来源。
- 更新时间。
- 负责人或维护方。

### 11.2 来源区域

来源必须区分：

- 结构化口径。
- 受控术语。
- 内部知识库。
- 个人记忆。
- 个人知识库。
- 外部资料。
- 工具结果。

不得统一显示为“知识库”。

### 11.3 下一步建议

根据问题类型展示：

- “查询这个指标数据”。
- “排查这个指标异常”。
- “创建指标口径需求”。
- “保存到个人知识库”。
- “查看来源”。

## 12. Trace 与 Evidence

每次指标解释必须记录：

- `trace_id`
- `conversation_id`
- `task_id`
- `user_id`
- `raw_question`
- `glossary_normalization`
- `metric_candidates`
- `selected_metric`
- `source_lookup_chain`
- `source_refs`
- `external_supplement_used`
- `conflict_resolution`
- `ui_schema`
- `next_actions`
- `case_id`

Evidence 要求：

- 内部口径结论必须关联 `metric_schema`。
- 内部知识补充必须关联 `system_common_knowledge`。
- 个人内容必须关联 `personal_memory` 或 `personal_knowledge`。
- 外部补充必须关联 `external_source`。

## 13. Prompt 与配置边界

写进代码的内容：

- 来源优先级。
- 内部优先冲突处理。
- 项目数据不得走知识库的红线。
- 无内部口径不得伪装正式口径的规则。
- Trace / Evidence 字段。

写进运行时配置的内容：

- 指标别名。
- 指标分类。
- 口径适用范围。
- 是否允许外部补充。
- 知识库 ID。
- 受控术语索引版本。

写进结构化指标库的内容：

- 指标定义。
- 公式。
- 数据来源。
- 聚合方式。
- 去重规则。
- 归因规则。
- 相近指标差异。
- 维护人和更新时间。

写进知识库的内容：

- SOP。
- 长文本说明。
- 常见问答。
- 业务背景。
- Case 复盘。

## 14. 失败闭环

失败类型：

| 类型 | 处理 |
|---|---|
| 指标未命中 | 追问或进入指标需求确认 |
| 多指标歧义 | 展示候选并追问 |
| 内部口径缺失 | 明确缺口，不生成正式口径 |
| 知识库不可用 | 使用结构化口径，标注补充来源不可用 |
| 个人知识库不可用 | 不影响通用解释 |
| 外部来源冲突 | 内部优先并展示冲突说明 |
| 用户问实时数据 | 转入问数 |
| 用户问异常原因 | 转入异常排查 |

Case 生成条件：

- 用户要求补正式口径。
- 指标是业务高频但结构化口径缺失。
- 内部资料冲突且无法自动裁决。
- 知识库或口径库长期不可用影响业务解释。

## 15. 验收场景

P0：

- 用户问“ROI 怎么算”，系统优先返回内部结构化口径。
- 用户问“激活口径是什么”，结果展示内部定义、适用范围、来源和更新时间。
- 用户问“媒体后台 ROI 和智投 ROI 为什么不一样”，输出差异说明，不进入项目异常结论。
- 用户问“A 项目昨天 ROI 多少”，系统转入问数，不用知识库回答。
- 用户问“ROI 为什么掉了”，系统转入异常排查，不只解释 ROI 概念。
- 内部口径缺失时，不伪装正式口径，并提供指标需求入口。
- 外部资料与内部口径冲突时，内部优先并提示差异。
- 来源区域能区分结构化口径、知识库、个人记忆和外部资料。

P1：

- 个人知识库命中的内容只对本人可见。
- 受控术语低置信度时先追问。
- 指标解释可保存到个人知识库。
- Trace 记录术语归一化、来源链和 UI Schema。

P2：

- 指标口径版本管理。
- 外部资料自动更新和冲突检测。
- Case 复盘自动补充知识库草稿。
- 指标口径变更通知。
