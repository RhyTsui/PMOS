# 设计阶段总说明与文档规范

## 1. 文档目的

本文档定义小乔智投第三阶段设计文档的组织方式。第三阶段不再继续写需求摘要，而是把已经确认的 PRD 转成可研发落地的系统设计、交互设计、数据模型、接口契约、Trace 契约和验收规则。

设计文档必须能直接支撑工程拆解，不能停留在产品愿景、功能清单或页面描述。

## 2. 文档目录原则

设计阶段采用“一需求一设计”的方式。复杂需求必须单独成文，不能压缩在综合文档中。

## 3. 单篇设计文档结构

每篇设计文档必须包含：

1. 对应需求文档。
2. 设计目标。
3. 当前实现核对。
4. 核心产品规则。
5. 系统流程。
6. 前端职责。
7. 后端职责。
8. Workflow / Skill / MCP 边界。
9. 数据模型。
10. API / 事件 / Trace 契约。
11. Prompt 与配置边界。
12. 失败闭环。
13. 验收场景。
14. 测试集与验收分层。
15. 工程实施映射。

## 4. 设计红线

- 不能把顶部项目选择器当成唯一项目事实。
- 不能把用户自然语言中明确提到的项目忽略掉。
- 不能硬编码项目名、项目 ID 或把 A/B 示例写入实现。
- 不能让 Chat 绕过能力注册和权限检查直接调用工具。
- 不能让 Prompt 生成内部数据、包状态、联调结果或上报检查结论。
- 不能把知识库召回当成工具执行结果。
- 不能把未接入能力写成已完成能力。

## 5. 设计输出要求

每篇设计文档必须回答：

- 用户说什么会触发该能力。
- 系统如何解析上下文。
- 系统如何确认项目、权限、能力和必填字段。
- 如果信息冲突，谁优先。
- 如果不能执行，如何闭环。
- 请求真实工具时传什么字段。
- 返回结果如何解析和展示。
- Trace 记录什么。
- 如何验收不是假功能。
- 已有测试集覆盖哪一层，未覆盖的前端、可视化、建议和资产闭环如何补验收。
