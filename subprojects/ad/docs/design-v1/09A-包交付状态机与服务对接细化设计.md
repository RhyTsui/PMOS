# 包交付状态机与服务对接细化设计

> 主文档：`09-包交付与联调系统设计.md`。
> 本文只细化包交付状态机、上报检查、后台更新检测、联调触发、可投结论和 Case 闭环。暂不展开资产沉淀、证据沉淀系统和连弩 Trace。

## 1. 细化目标

包交付的一期目标是让优化师能问清楚：“当前项目这个包能不能投、卡在哪里、下一步谁处理”。系统必须基于真实 Workflow / Skill / MCP 返回形成状态和结论。

本细化文档解决四个工程落点：

- 状态机不能只用一串枚举，必须能区分首次、更新、媒体包、官包和智投分包。
- 上报检查是交付前置条件，不通过时不能提示用户提审、更新包或触发联调。
- 后台更新检测决定新版本何时出现，媒体包和官包路径不同。
- 可投结论只能由状态机派生，Chat 不得直接输出“可投”。

## 2. 当前实现需要补的关键层

当前已有 `get_delivery_packages`、`delivery` agent、包交付相关 SkillContract、自动联调 API 和前端交付卡片基础。

还需要补齐：

| 缺口 | 需要新增的设计约束 |
|---|---|
| 状态枚举过粗 | 建立 `flow_type + package_source + delivery_status + business_conclusion` 四段模型 |
| 上报检查和联调关系不清 | 联调触发前必须存在“上报检查通过”结果 |
| 媒体后台更新和智投后台更新混淆 | 媒体包等待媒体后台更新，官包/智投分包等待智投后台更新 |
| 新包失败时旧包处理不清 | 新包一旦后台已更新，旧包标记为已被新包替代；失败只影响新包风险结论 |
| 单独触发联调边界不清 | 单独联调仍归包交付能力，但入口可由用户主动触发 |
| 强阻断风险 | 一期只给可信结论和风险提示，不做禁止建监测活动或后台放行 |

## 3. 状态模型

### 3.1 FlowType

```ts
type PackageFlowType =
  | 'media_first_delivery'
  | 'media_update_delivery'
  | 'official_first_delivery'
  | 'official_update_delivery'
  | 'manual_integration_check'
  | 'status_query'
```

### 3.2 PackageSource

```ts
type PackageSource =
  | 'media_backend'
  | 'official_package'
  | 'zhitou_sub_package'
```

### 3.3 DeliveryStatus

```ts
type DeliveryStatus =
  | 'waiting_package'
  | 'report_checking'
  | 'report_check_failed'
  | 'waiting_submission'
  | 'waiting_media_backend_update'
  | 'waiting_zhitou_backend_update'
  | 'integration_checking'
  | 'integration_failed'
  | 'integration_success'
  | 'replaced_by_new_package'
  | 'historical'
```

### 3.4 BusinessConclusion

```ts
type PackageBusinessConclusion =
  | 'deliverable'
  | 'not_recommended'
  | 'pending'
  | 'risk_attention'
  | 'historical'
```

状态和结论的派生关系：

| DeliveryStatus | BusinessConclusion | 用户表达 |
|---|---|---|
| `waiting_package` | `pending` | 等待出包 |
| `report_checking` | `pending` | 上报检查中 |
| `report_check_failed` | `not_recommended` | 上报不通过，不建议交付 |
| `waiting_submission` | `pending` | 上报检查通过，等待提审 |
| `waiting_media_backend_update` | `pending` | 上报检查通过，等待媒体后台更新 |
| `waiting_zhitou_backend_update` | `pending` | 数据检查通过，等待智投后台更新 |
| `integration_checking` | `pending` | 联调检查中 |
| `integration_failed` 首次包 | `not_recommended` | 联调不通过，不建议交付 |
| `integration_failed` 更新包 | `risk_attention` | 新包已更新但联调不通过，存在生产验证风险 |
| `integration_success` | `deliverable` | 联调成功，可交付投放 |
| `replaced_by_new_package` | `historical` | 已被新包替代 |

## 4. 状态机细化

### 4.1 媒体包首次交付

适用：巨量、腾讯、快手首次媒体包。

```text
waiting_package
-> report_checking
-> waiting_submission
-> waiting_media_backend_update
-> integration_checking
-> integration_success
```

失败：

```text
report_checking -> report_check_failed
integration_checking -> integration_failed -> case_created
```

关键规则：

- 智投收到包后立即进入上报检查。
- 上报检查通过后，只能提示“上报检查通过，等待提审”。
- 系统检测到媒体后台出现该版本后，才进入联调检查。
- 联调成功后才派生 `deliverable`。
- 联调失败后派生 `not_recommended` 并创建失败 Case。

### 4.2 媒体包更新交付

适用：巨量、腾讯、快手的新包更新。

```text
waiting_package
-> report_checking
-> waiting_media_backend_update
-> integration_checking
-> integration_success
-> old_package.replaced_by_new_package
```

失败：

```text
report_checking -> report_check_failed
integration_checking -> integration_failed -> risk_attention -> case_created
```

关键规则：

- 上报不通过时，不提示用户更新媒体后台，旧包保持当前有效。
- 上报通过后提示“上报检查通过，等待媒体后台更新”。
- 检测到媒体后台更新后，展示新版本号并进入联调。
- 新包联调成功后，旧包自动标记“已被新包替代”。
- 新包联调失败时，旧包通常已经被替代，仍标记历史；新包为 `risk_attention`，必须生成 Case。

### 4.3 官包 / 智投分包首次交付

```text
waiting_package
-> report_checking
-> integration_checking
-> integration_success
```

关键规则：

- 官包上报检查通过后，直接触发智投分包联调。
- 上报不通过时，不触发智投分包联调。
- 联调失败派生 `not_recommended` 并创建 Case。

### 4.4 官包 / 智投分包更新交付

```text
waiting_package
-> report_checking
-> waiting_zhitou_backend_update
-> integration_checking
-> integration_success
-> old_package.replaced_by_new_package
```

关键规则：

- 上报通过后提示“数据检查通过，等待智投后台更新”。
- 检测到智投后台更新后，抽取一个在投媒体分包检查。
- 联调成功后新包可交付，旧包进入历史。
- 联调失败后生成 Case，给出生产验证风险说明。

## 5. 服务对接边界

### 5.1 Chat

Chat 只负责：

- 识别用户是查询可投、查卡点、查包状态还是主动触发联调。
- 解析项目、媒体、终端、包名、版本。
- 项目冲突时按用户明示项目优先。
- 调用 PackageDeliveryWorkflow。
- 用用户语言解释 Workflow 返回的状态、结论和下一步。

Chat 禁止：

- 自己判断上报通过。
- 自己判断媒体后台已更新。
- 自己判断联调成功。
- 根据自然语言直接说“可投”。

### 5.2 PackageDeliveryWorkflow

Workflow 负责：

- 创建和推进 `PackageDeliveryTask`。
- 选择 flow type。
- 调用上报检查、后台更新检测、联调检查 Skill。
- 合法状态流转校验。
- 业务结论派生。
- 旧包替代处理。
- 失败 Case 创建。

### 5.3 Skill / MCP

建议 Skill 拆分：

| Skill | 真实能力来源 | 输出 |
|---|---|---|
| `package_status_query_skill` | 智投配置 MCP / 包服务 | 包列表、下载地址、版本、当前生命周期 |
| `package_report_check_skill` | 数据上报报告 MCP | 通过项、失败项、报告地址、检查时间 |
| `package_backend_update_check_skill` | 媒体后台 / 智投后台 MCP | 后台版本、更新时间、审核状态 |
| `package_integration_check_skill` | 自动联调 MCP | 联调状态、失败步骤、日志、截图 |
| `package_delivery_case_skill` | Case 服务 / 需求池 | Case 编号、状态、建议处理角色 |

## 6. 用户触发联调规则

用户可以单独说“帮我触发一次联调”，但仍必须遵守包交付约束。

执行前检查：

1. 项目已确定且用户有权限。
2. 媒体和终端已确定。
3. 目标包或分包可定位。
4. 上报检查结果为通过。
5. 联调配置存在。

处理：

| 场景 | 系统行为 |
|---|---|
| 上报检查未知 | 先查询或触发上报检查，不直接联调 |
| 上报检查不通过 | 阻断联调，展示失败项和修复建议 |
| 联调配置缺失 | 返回 blocker，可创建 Case |
| 联调能力不可用 | 返回能力缺口，不输出执行成功 |
| 联调失败 | 自动生成 Case |

## 7. API 细化

### 7.1 查询包交付状态

```http
POST /api/xiaoqiao/package-delivery/query
```

最小请求：

```ts
type PackageDeliveryQueryRequest = {
  conversation_id?: string
  user_id: string
  project_ref: string
  media_scope?: string[]
  terminal?: string
  package_name?: string
  version?: string
  query_type: 'deliverable_packages' | 'package_status' | 'delivery_blocker'
}
```

响应：

```ts
type PackageDeliveryQueryResponse = {
  task_id: string
  flow_type: PackageFlowType
  project_ref: string
  delivery_status: DeliveryStatus
  business_conclusion: PackageBusinessConclusion
  packages: PackageSummary[]
  blockers: PackageBlocker[]
  next_actions: string[]
  case_id?: string
}
```

### 7.2 刷新状态

```http
POST /api/xiaoqiao/package-delivery/tasks/{taskId}/refresh
```

规则：

- 刷新只能推进真实状态，不能手动指定目标状态。
- 如果依赖 MCP 不可用，状态保持不变并返回失败原因。

### 7.3 单独触发联调

```http
POST /api/xiaoqiao/package-delivery/tasks/{taskId}/integration-check
```

请求必须带：

```ts
type PackageIntegrationCheckRequest = {
  user_id: string
  project_ref: string
  media: string
  terminal: string
  package_id?: string
  require_report_check_passed: true
}
```

## 8. 前端结果细化

### 8.1 可投结果

必须展示：

- 项目、媒体、终端、包名、版本。
- 下载地址或 APK 地址。
- 上报检查状态。
- 后台更新状态。
- 联调状态。
- 业务结论。
- 下一步建议。

### 8.2 阻塞结果

必须展示：

- 当前卡点。
- 失败原因。
- 需要谁处理。
- 建议动作。
- 是否已创建 Case。

### 8.3 历史包

规则：

- 已被新包替代的旧包进入历史包区域。
- 默认不展开。
- 展开后只展示历史状态，不作为当前可投包。

## 9. 防假功能验收

上线前必须证明：

- 上报检查状态来自真实上报报告 MCP。
- 后台更新状态来自媒体后台或智投后台检测。
- 联调状态来自自动联调 MCP / Workflow。
- `deliverable` 由 `integration_success` 等合法状态派生。
- 上报不通过时不会提示提审、更新或联调。
- 单独触发联调前会检查上报通过。
- Case 创建必须返回真实 Case 编号。
