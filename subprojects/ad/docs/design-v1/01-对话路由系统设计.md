# 对话路由系统设计

## 1. 对应需求

本设计对应：

- `docs/prd-v2.2/20-对话路由需求PRD.md`
- `docs/prd-v2.2/18-意图路由知识库与能力闭环设计准入评估.md`
- `docs/prd-v2.2/05-项目角色权限与跨项目设计.md`

## 2. 设计目标

对话路由负责把用户自由表达转成可执行服务闭环。它不是简单的 Agent 分类，而是统一完成：

- 意图识别。
- 术语归一化。
- 项目上下文解析。
- 能力发现。
- 权限检查。
- slot 补齐。
- 追问 / 调用 / 失败闭环分发。
- Trace 与评测记录。

## 3. 当前实现核对

当前实现基础：

- 前端在发送消息时会把右上角项目选择器拼接为 `[项目上下文]`。
- `/api/chat/route.ts` 会从 `projectContext` 解析当前项目。
- `conversation-context.ts` 和 `context-compiler.ts` 会基于项目上下文构造业务上下文。
- `slot-resolver.ts` 支持从上下文继承项目或应用字段。
- `report-query-orchestrator.ts` 最终会解析 appId / projectId 并发起真实查询。

当前风险：

- 顶部项目 A 被作为默认项目上下文拼入消息。
- 如果用户原文显式提到 B 项目，但系统没有解析明示项目，就可能静默请求 A 项目数据。
- 这会造成用户表达和真实请求不一致，是高风险数据错误。

## 4. 标准路由流水线

每轮消息按以下顺序处理：

1. 拆分用户原文和系统拼接上下文。
2. 解析用户作用域、角色、权限。
3. 解析顶部项目上下文。
4. 解析用户原文中的显式项目。
5. 生成项目解析结果 `ProjectResolution`。
6. 调用受控术语归一化。
7. 生成候选意图。
8. 查询能力注册表。
9. 校验项目权限和动作权限。
10. 生成最终 `DialogueRouteDecision`。
11. 根据 `next_action` 追问、调用、回答通用问题或生成 Case。
12. 记录 Trace。

## 5. 项目上下文解析与冲突处理

### 5.1 核心原则

顶部项目选择器只是默认上下文，不是本轮请求的绝对项目。用户在自然语言中显式提到项目时，显式项目优先。

系统禁止在以下场景静默使用顶部项目：

- 顶部项目是 A，用户问“查 B 项目昨天消耗”。
- 顶部项目是 A，用户问“B 项目 ROI 怎么样”。
- 顶部项目是 A，用户问“B 项目的包能投吗”。
- 顶部项目是 A，用户问“B 和当前项目对比”。

这里的 A/B 只是验收样例符号，不是可写入工程的项目名或项目 ID。实际项目解析必须基于用户当前权限项目列表、项目字典、项目别名、APPID、历史上下文和个人记忆动态完成。

### 5.2 项目来源

项目上下文有四类来源：

| 来源 | 说明 | 优先级 |
|---|---|---|
| 用户明示项目 | 用户原文里出现项目名、别名、APPID、项目 ID | 最高 |
| 对比表达 | 用户说“和当前项目比”“A 和 B 对比” | 高 |
| 顶部项目 | 右上角选择器当前项目 | 默认 |
| 历史继承 | 历史会话、个人记忆、上一轮任务项目 | 低，需要置信度 |

### 5.3 冲突处理规则

| 场景 | 处理 |
|---|---|
| 顶部 A，用户问“查 B 项目昨天消耗” | 请求 B，不请求 A |
| 顶部 A，用户问“查这个项目昨天消耗” | 请求 A |
| 顶部 A，用户问“B 和当前项目对比” | 请求 A + B |
| 顶部 A，用户问“B 项目的包能投吗” | 包交付请求 B，且保持单项目 |
| 顶部 A，用户问无权限 B | 阻断，不回退到 A |
| 顶部 A，用户提到模糊项目别名 | 追问确认 |
| 顶部 A，历史默认 C，用户说“继续昨天那个项目” | 低置信度时追问 |
| 用户明示多个项目，能力只支持单项目 | 追问选择一个，或拆成多个任务 |

### 5.4 权限处理

项目解析必须先得到候选项目，再做权限判断。

规则：

- 用户明示 B 项目但无权限：提示无权限，不能改查顶部 A。
- 用户明示 B 项目但系统无法识别：提示未识别项目，要求用户确认。
- 用户明示 B 项目且有权限：请求 B。
- 用户要求跨项目对比：对每个项目分别校验权限，部分无权限时只展示有权限部分，并提示部分不可见。

## 6. 数据模型

### 6.1 ProjectResolution

```ts
type ProjectResolution = {
  ui_selected_project_ref?: string
  explicit_project_mentions: Array<{
    raw: string
    project_ref?: string
    project_name?: string
    confidence: number
    matched_by: 'exact_name' | 'alias' | 'app_id' | 'history' | 'fuzzy'
  }>
  inherited_project_refs: string[]
  effective_project_refs: string[]
  resolution_source:
    | 'explicit_user_project'
    | 'ui_selected_project'
    | 'cross_project_compare'
    | 'history_inherited'
    | 'clarification_required'
  conflict_detected: boolean
  clarification_needed: boolean
  clarification_question?: string
  permission_status: 'allowed' | 'partial_allowed' | 'denied' | 'unknown'
}
```

### 6.2 DialogueRouteRequest

```ts
type DialogueRouteRequest = {
  conversation_id: string
  message_id: string
  raw_text: string
  ui_project_context?: string
  user_scope_key: string
  role_id: string
  allowed_project_refs: string[]
  project_resolution?: ProjectResolution
}
```

### 6.3 DialogueRouteDecision

```ts
type DialogueRouteDecision = {
  route_id: string
  intent_key: string
  confidence: number
  is_business_related: boolean
  project_resolution: ProjectResolution
  capability_id?: string
  capability_status: 'available' | 'partially_available' | 'planned' | 'disabled' | 'missing'
  execution_allowed: boolean
  blocked_reason?: string
  required_slots: string[]
  resolved_slots: Record<string, unknown>
  missing_slots: string[]
  clarification_needed: boolean
  clarification_stage: 'pre_route' | 'post_route' | 'workflow_runtime' | 'none'
  next_action:
    | 'ask_clarification'
    | 'call_workflow'
    | 'call_skill'
    | 'answer_general'
    | 'create_case'
    | 'show_boundary'
}
```

### 6.4 工具请求项目字段

所有 Workflow / Skill / MCP 请求必须带：

```ts
type ProjectAwareToolRequest = {
  project_refs: string[]
  project_resolution_source: ProjectResolution['resolution_source']
  ui_selected_project_ref?: string
  explicit_project_refs?: string[]
}
```

工具层不得自行回退到顶部项目。

## 7. 前端职责

前端负责：

- 继续传递顶部项目上下文。
- 不把顶部项目文案混入用户原文中参与明示项目解析。
- 在追问卡片中展示项目冲突问题。
- 在结果卡片中展示最终查询项目。
- 在跨项目结果中展示部分无权限提示。

前端不负责：

- 决定最终请求项目。
- 绕过后端项目权限。
- 在项目冲突时静默替用户选择。

## 8. 后端职责

后端负责：

- 将用户原文和 `[项目上下文]` 分离。
- 解析明示项目、顶部项目、历史项目和个人记忆项目。
- 生成 `ProjectResolution`。
- 校验用户项目权限。
- 将 `effective_project_refs` 传给真实工具。
- 在 Trace 中记录项目解析过程。

后端禁止：

- 只用顶部项目构造查询请求。
- 明示项目无权限时回退到顶部项目。
- 项目别名低置信度时直接执行。

## 9. Prompt 与配置边界

项目解析优先走确定性规则和项目字典。

项目解析禁止硬编码项目名、项目 ID 或示例 A/B。

写进配置：

- 项目 ID。
- 项目名称。
- 项目别名。
- APPID。
- 历史项目映射。

Prompt 可用于：

- 在项目别名低置信度时生成追问文案。
- 在多个项目候选时解释冲突。

Prompt 禁止：

- 凭常识虚构项目。
- 跳过权限检查。
- 决定无权限项目可以回退到顶部项目。

## 10. 失败闭环

项目解析失败时：

- 如果项目明示但无法识别：追问用户确认项目。
- 如果项目明示但无权限：提示无权限，并建议联系项目管理员。
- 如果项目冲突且无法判断用户意图：追问“你是要查 B 项目，还是当前 A 项目？”
- 如果能力不支持跨项目：提示只能单项目执行，并让用户选择一个项目或拆成多个任务。

## 11. Trace 与评测

Trace 必须记录：

- `ui_selected_project_ref`
- `explicit_project_mentions`
- `inherited_project_refs`
- `effective_project_refs`
- `resolution_source`
- `conflict_detected`
- `permission_status`
- 是否追问
- 最终工具请求项目

评测用例：

1. 顶部 A，用户问“查 B 项目昨天消耗” -> 请求 B。
2. 顶部 A，用户问“查这个项目昨天消耗” -> 请求 A。
3. 顶部 A，用户问“B 和当前项目 ROI 对比” -> 请求 A+B。
4. 顶部 A，用户问“B 项目包能投吗” -> 包交付请求 B。
5. 顶部 A，用户问无权限 B -> 阻断，不请求 A。
6. 顶部 A，用户问模糊项目别名 -> 追问。
7. 历史 C，顶部 A，用户问“继续查昨天那个项目” -> 低置信度时追问。

## 12. 工程实施映射

P0：

- 在 Chat 主链路增加 `ProjectResolution`。
- 工具请求统一使用 `effective_project_refs`。
- `report_query` 请求不再直接依赖顶部项目。
- 追问卡支持项目冲突确认。
- Trace 增加项目解析字段。

P1：

- 项目别名配置化。
- 项目解析评测集接入连弩。
- 个人记忆中的项目上下文参与继承，但低置信度时必须确认。
