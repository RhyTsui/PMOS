# 问数系统性问题决策台账

## 1. 文档目的

本文用于把问数能力建设中的问题系统化拆开，避免继续以“发现一个修一个”的方式推进。

每个问题必须形成：

- 问题定义。
- 当前事实。
- 推荐结局方案。
- 备选方案。
- 取舍影响。
- 需要确认的问题。
- 确认状态。
- 后续落地位置。

确认原则：

- 一次只确认一个问题。
- 未确认的问题不得直接扩大工程实现。
- 已确认的问题必须回写 PRD、设计、工程清单和测试门禁。
- 能从代码、MCP schema、运行态配置、知识库或测试集发现的事实，不向用户重复提问。

## 2. 总体分层原则

### 2.1 事实来源分层

| 层级 | 事实类型 | 归属 |
|---|---|---|
| 代码 | 流程不变量、安全红线、状态枚举、schema 校验、测试门禁 | 工程实现 |
| 动态配置 | 路由优先级、关键词、别名、默认策略、Prompt 版本、灰度阈值 | 配置中心 / 后台 |
| Tool / MCP / Skill | 真实数据、真实动作、tool schema、错误码、权限失败、可执行边界 | 中间服务 |
| 知识库 | 术语解释、指标口径、SOP、历史 case、方法论 | RAG / 知识服务 |
| Prompt / 大模型 | 候选判断、slot 候选抽取、追问表达、结构化结果解释、下一步建议 | Chat 编排 |

### 2.2 决策原则

- MCP schema 是执行能力事实来源。
- 项目权限是可见性事实来源。
- 知识库不能覆盖 MCP schema、权限和实时数据。
- Prompt 不能决定能力是否存在。
- 测试映射脚本只用于归属、门禁和问题发现，不是生产路由事实来源。
- 动态配置负责业务策略变化，代码负责不能被策略绕过的红线。

## 4. 待确认问题详情

### Q1. 测试集映射规则是否只作为测试门禁

问题定义：

当前 `report-query-testcase-mapping.ts` 中存在启发式规则，用于从测试集 Prompt 推断期望 tool、责任层、slot 和失败分类。这个规则能帮助发现问题，但如果直接进入生产路由，会形成另一套事实来源，和 MCP schema、动态配置、知识库产生冲突。

当前事实：

- 测试映射脚本已能读取 91 条问数测试集。
- 当前 tool 选择门禁已通过，91 条均为 exact。
- 脚本中已经声明“测试集推断规则不是生产路由事实来源”。

推荐结局方案：

测试集映射规则只作为测试、评测、诊断和门禁工具，不进入生产 Chat 路由。生产路由必须使用 `ReportCapabilityManifest`、动态策略配置、权限上下文、MCP schema 和受控术语 / 口径知识。

备选方案：

- 方案 A：把测试映射规则复用到生产路由。优点是快；缺点是会把测试启发式变成生产事实，后续维护风险高。
- 方案 B：测试映射规则只做门禁。优点是边界清晰；缺点是还要继续建设生产 Manifest 和配置层。

推荐选择：

方案 B。

影响：

- 测试脚本可以继续快速迭代。
- 生产路由不能依赖脚本规则，需要后续实现 Manifest 和配置化能力选择。
- 以后测试集新增用例时，先更新映射门禁，再决定是否进入生产配置。

需要确认：

是否确认“测试集映射规则只作为测试门禁和诊断工具，不进入生产路由”？

确认状态：已确认。

确认结论：

- 测试集映射规则只作为测试门禁、评测归属、诊断和问题发现工具。
- 不进入生产 Chat 路由。
- 生产路由事实来源必须是 `ReportCapabilityManifest`、动态策略配置、权限上下文、MCP schema 和知识库口径说明的组合。
- 当前 `report-query-testcase-mapping.ts` 中的启发式规则不得被复用为生产执行规则。

落地位置：

- `frontend/src/scripts/report-query-testcase-mapping.ts`
- `docs/design-v1/generated/report-query-testcase-capability-mapping.md`
- 后续 `ReportCapabilityManifest` 实现。

### Q2. 生产能力发现是否必须从 MCP schema 生成 Manifest

推荐结局方案：

必须生成 `ReportCapabilityManifest`，作为生产能力发现的事实层。它记录当前可用 server、tool、schema、字典依赖、支持报表域、字段要求、生成时间和版本。

需要确认：

是否确认生产路由不能直接扫 `mcp-servers.json + 关键词`，必须先生成 Manifest？

确认状态：已确认。

确认结论：

- 生产能力发现不能直接依赖 `mcp-servers.json + 关键词`。
- 必须先从当前 connected MCP 的 tool name、description、input_schema、output_schema、错误码和权限结构生成 `ReportCapabilityManifest`。
- 路由、slot 补齐、追问、schema adapter、执行前校验和 Trace 都引用 Manifest 版本。
- 关键词规则只能作为候选选择权重，不能作为能力事实来源。
- Manifest 需要在 MCP 配置变更、tools/list 刷新、管理员手动刷新时重新生成。

### Q3. 路由规则放代码还是动态配置

推荐结局方案：

代码固化流程和红线；动态配置承载业务可变规则，包括关键词、优先级、排除词、默认策略、tool override。

需要确认：

是否确认路由规则优先级、关键词、默认值和 Prompt 版本必须后台可配置，代码只做兜底和校验？

确认状态：已确认。

确认结论：

- 需要增加“问数策略变量配置”，但不能做成泛化万能变量。
- 代码负责不可被绕过的不变量：路由流程、安全红线、权限校验、schema 校验、状态枚举、失败分类、测试门禁。
- 动态变量配置负责业务可变策略：路由关键词、排除词、优先级、报表域到 tool 的 override、slot 别名、默认时间 / 粒度 / 指标、Prompt 版本、追问话术、结果解释模板、门禁阈值、灰度开关。
- 变量配置不能承载项目权限、MCP schema、当前可用 tool 事实、真实报表数据、字典 ID 唯一事实，也不能允许绕过权限或工具失败。
- 生产优先级为：代码红线 > 权限上下文 > MCP Manifest > 策略变量配置 > 知识库解释 > Prompt 表达。

### Q4. 术语和指标口径放知识库还是配置

推荐结局方案：

指标口径解释、术语背景、SOP 放知识库；执行映射、字段枚举、tool schema、权限放配置和 MCP；两者都要返回证据来源。

需要确认：

是否确认知识库只做解释和术语背景，不直接决定执行 tool 和字段值？

确认状态：已确认。

确认结论：

- 知识库放术语解释、行业表达与内部表达差异、指标口径说明、公式来源、SOP、历史 case 和方法论。
- 策略变量配置放术语到执行字段的别名映射、默认口径选择、路由权重、追问话术和解释模板。
- MCP / Tool schema 决定字段是否可执行、枚举值是什么、哪些组合维度可查、真实数据如何返回。
- Prompt 只能基于知识库、配置、Manifest、权限上下文和结构化结果做解释与追问，不能自定义口径。
- 当知识库口径和 MCP schema / 接口结果冲突时，以 MCP schema / 接口事实为执行准绳，知识库冲突作为 Evidence 风险提示。

### Q5. 多工具复合问数如何闭环

推荐结局方案：

一期至少识别复合问数并拆成多 tool 串行执行计划。例如同一问题同时包含激活、ROI、留存、小时指标时，不能只选一个 tool；必须输出多 tool plan、执行顺序和合并结果。

需要确认：

是否确认一期就要支持多 tool 复合问数的执行编排，而不是只提示用户拆开问？

确认状态：已确认。

确认结论：

- 一期支持“串行编排”作为默认方案，不要求用户自行拆问，也不在 P0 做并行编排。
- 识别到日常投放指标、ROI、留存、小时、素材等跨报表域组合时，生成 `ReportQueryPlan`，拆成多个 `ReportSubQuery` 顺序执行。
- 每个子查询都必须记录 selected tool、入参、字典解析、执行结果、失败原因和 evidence refs。
- 合并回答必须说明哪些子查询成功、哪些失败或为空；部分成功时允许展示已完成结果，同时给出失败项下一步建议。
- 复合问数的事实来源是 `ReportQueryPlan` 和 Trace，不依赖模型长上下文重新猜测。

需要确认：

大模型基于结构化结果、Evidence、质量检查和模板约束生成解释与下一步建议。它不能创造新数据，也不能隐藏工具失败。

需要确认：

确认状态：已确认。

确认结论：

- 可以使用大模型生成结果解释和下一步建议，但必须通过 `ReportAnswerComposer` 受控生成。

推荐结局方案：

先追问确认；当必要字段多轮仍缺失、权限不足、MCP 不可用、返回无法解析或业务执行失败不可自动恢复时生成 Case。

需要确认：

是否确认失败闭环采用“先追问，多轮仍不行再生成 Case”的策略？

确认状态：已确认。

确认结论：

- 失败闭环采用“先追问确认，多轮后不行再生成 Case”的策略，避免过早兜底。
- 缺必要字段、项目冲突、口径不明确时优先追问；MCP 不可用、权限不足、返回无法解析、不可恢复工具失败时生成 Case。
- Case 必须记录原始问题、归一化意图、缺失 slot、候选能力、已调用 tool、错误码、返回摘要、Trace 和建议处理人。

### Q11. 长上下文与任务状态如何恢复

问题定义：

问数、多工具编排、追问、失败闭环和资产沉淀都会拉长对话。如果只依赖模型上下文，长会话后会出现历史条件丢失、项目错用、tool plan 被重建、执行结果无法复核等问题。

当前事实：

- 当前讨论已经出现多阶段设计、测试映射、门禁、路由修复和决策确认，单靠聊天上下文不可持续。
- 工程侧已经有文档、生成物、Trace、mcp-context checkpoint 等沉淀手段。
- 多工具复合问数需要记录子查询、已补 slot、tool 调用和部分结果，否则上下文截断后无法继续。

推荐结局方案：

产品会话上下文采用分层恢复机制，不把所有历史消息都塞给模型。

上下文优先级：

1. 当前用户输入。
2. 当前任务结构化 state。
3. 最近 N 轮对话。
4. 会话结构化摘要。
5. 资产 / Trace / tool call 引用。
6. 知识库和个人记忆检索结果。

多工具问数必须生成 `ReportQueryPlan`，用于跨轮和上下文截断恢复：

```ts
type ReportQueryPlan = {
  plan_id: string
  conversation_id: string
  user_scope_key: string
  project_context: ProjectResolution
  original_question: string
  normalized_intent: string
  sub_queries: ReportSubQuery[]
  required_slots: string[]
  resolved_slots: Record<string, unknown>
  pending_slots: string[]
  tool_calls: ToolCallRef[]
  partial_results: ResultRef[]
  merge_rules: string[]
  failed_items: ReportPlanFailure[]
  evidence_refs: EvidenceRef[]
  trace_id: string
  status: 'planning' | 'waiting_for_user' | 'executing' | 'partial_success' | 'success' | 'failed' | 'case_created'
  updated_at: string
}
```

备选方案：

- 方案 A：继续依赖最近对话和模型摘要。优点是简单；缺点是不可靠，容易错用项目和丢失执行证据。
- 方案 B：引入结构化 state / plan / Trace 恢复。优点是可审计、可恢复、能支持多工具；缺点是需要新增对象和存储。

推荐选择：

方案 B。

影响：

- Chat 不再从长历史里猜测当前执行状态。
- 多轮追问、部分成功、失败重试和 Case 生成都能引用同一个 plan。
- 历史会话打开后可以恢复任务状态，而不是重新路由。
- Trace 和连弩回放可以看到 plan 的每一步演进。

需要确认：

是否确认长上下文问题采用“结构化 state / plan / Trace 恢复”，并把 `ReportQueryPlan` 作为多工具复合问数和长链路问数的核心状态对象？

确认状态：已确认。
