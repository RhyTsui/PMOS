# 能力发现与服务绑定执行闭环系统设计

> 承接文档：`01-对话路由系统设计.md`、`04A-MCP能力发现与问数归属矩阵.md`、`06-问数知识策略与配置治理系统设计.md`、`docs/prd-v2.2/10-数据建模与请求反馈模型.md`。
> 本文把问数中已经验证过的能力发现方法扩展为全局机制，覆盖 Chat 到 MCP / Skill / Workflow / 内部 API 的真实执行闭环。

## 1. 为什么需要全局能力发现

当前系统已经接入多个 MCP，且部分能力已经给其他 Chat 使用过。问题不在于“没有 MCP”，而在于 Chat 到服务能力之间缺少稳定的产品化绑定层。

如果没有全局能力发现，会出现四类问题：

- 用户问的问题明明已有 MCP 能力，但 Chat 不知道，导致错误兜底或重复规划假功能。
- Chat 只靠关键词路由，未检查工具 schema、必填字段、权限和状态，补参后仍无法执行。
- 不同能力各自实现调用和解析，Evidence、Trace、Case、UI 呈现不统一。
- Prompt、配置、知识库、MCP 事实来源混用，后续很难评测和治理。

全局能力发现的目标：

1. 把所有可执行能力登记成可审计的 Capability。
2. 让路由先判断“用户要做什么”，再判断“系统能不能做”。
3. 在追问前做能力预检，避免无效补参。
4. 执行必须真实调用 MCP / Skill / Workflow / 内部 API。
5. 结果必须结构化解析，进入 Evidence、Trace、UI 和 Case。

## 2. 当前实现基础

| 模块 | 当前实现 | 可复用点 | 主要缺口 |
|---|---|---|---|
| MCP 管理 | `mcp-server-store.ts` 管理运行态 MCP，内置和运行态配置可合并 | 可作为服务目录来源 | 缺全局 capability manifest，只在问数域有 manifest |
| MCP 发现与调用 | `mcp-discovery.ts` 支持 initialize、`tools/list`、`tools/call` | 可作为所有 MCP 的发现和调用底座 | 缺统一错误分类、schema 适配和 evidence 生成 |
| Skill 合约 | `skill-contract-store.ts` 存在多个 SkillContract | 可表达 skill 的触发、输入、步骤和输出 | 缺与路由、CapabilityRegistry、Trace 的统一绑定 |
| Workflow 运行 | `workflow-task-store.ts`、`workflow-engine.ts` 支持运行记录 | 可作为流程执行记录 | 缺统一 WorkflowBinding 和外部服务调用链契约 |
| 路由引擎 | `intent-route-engine.ts`、`intent-router.ts` 已读取 MCP / skill 基础信息 | 可作为候选意图生成层 | 缺“能力状态 + schema + 权限 + slot”联合决策 |
| 问数能力 | `report-capability-manifest.ts` 已实现报表域能力清单 | 可抽象成全局 manifest 模式 | 目前只服务 report_query |

结论：当前系统不是从零开始，应该抽象统一层，而不是为每个场景重新写一套调用逻辑。

## 3. 核心设计原则

1. 能力事实来自运行态服务披露，不来自 Prompt。
2. Chat 只负责理解、路由、追问、确认、结果解释和下一步建议，不直接实现业务服务。
3. MCP / Skill / Workflow / 内部 API 都必须通过统一 ServiceBinding 注册。
4. 能力可用性要同时看状态、schema、权限、项目范围、运行开关和版本。
5. 追问发生在能力预检之后，只问能让执行继续的字段。
6. 结果必须从结构化响应解析，不允许模型补造业务事实。
7. 失败闭环不是兜底话术，而是错误分类、重试、追问、Case 和证据沉淀。

## 4. 分层架构

```text
User Message
  -> Context Compiler
  -> Term Normalizer
  -> Intent Router
  -> Capability Registry
  -> Capability Preflight
  -> Slot Resolver
  -> Service Binding Executor
  -> Result Parser
  -> Answer Composer
  -> UI / Evidence / Trace / Case / Asset
```

### 4.1 Capability Registry

能力注册表负责回答：系统当前有什么能力、状态如何、由什么服务提供、需要什么输入、输出什么结果。

### 4.2 Capability Preflight

能力预检负责回答：本轮用户问题是否可以执行、还缺什么、是否需要权限、是否只能单项目、是否需要用户确认。

### 4.3 Service Binding Executor

服务绑定执行器负责真实调用 MCP / Skill / Workflow / 内部 API，并把输入、输出、错误和证据统一成标准结构。

### 4.4 Result Parser

结果解析器负责把工具返回转成业务结构，区分成功、部分成功、空结果、失败、等待外部状态。

### 5.1 ServiceBinding

```ts
type ServiceBinding = {
  binding_type: 'mcp_tool' | 'skill' | 'workflow' | 'internal_api' | 'model_answer'
  mcp?: {
    server_id: string
    tool_name: string
    transport: 'stdio' | 'sse' | 'streamable-http'
  }
  skill?: {
    skill_id: string
  }
  workflow?: {
    workflow_id: string
    workflow_type: string

    method: 'GET' | 'POST' | 'PATCH'

```

`model_answer` 只允许用于不需要内部事实和真实业务动作的通用解释场景。业务域能力不得用 `model_answer` 伪装完成。

### 5.2 CapabilityInputContract

```ts
type CapabilityInputContract = {

```

### 5.3 CapabilityOutputContract

```ts
type CapabilityOutputContract = {
  result_type:
    | 'report_query_result'

    | 'demand_case'

```

### 5.4 权限和项目策略

```ts
type CapabilityProjectPolicy = {
  project_scope: 'none' | 'single_project' | 'multi_project_allowed' | 'cross_project_compare'
  require_project_resolution: boolean
  reject_on_permission_denied: boolean
}

type CapabilityPermissionPolicy = {
  required_actions: string[]
  role_allowlist?: string[]
  write_operation: boolean
  audit_required: boolean
}
```

包交付、联调、上报检查属于 `single_project`；问数和资产可支持多项目；通用知识问答可为 `none`。

## 6. 能力来源与生成

全局 CapabilityRegistry 由四类来源合并生成。

| 来源 | 作用 | 可信边界 |
|---|---|---|
| MCP `tools/list` | 发现服务、tool、input_schema、description | 只说明工具存在和 schema，不说明产品路由策略 |
| SkillContract | 发现 Skill 的触发语、输入、步骤、输出、风险红线 | 需要绑定真实服务或 workflow |
| WorkflowDefinition | 发现流程型能力、状态机和步骤 | 需要每步绑定真实能力 |
| Runtime Override | 补充路由词、禁用能力、字段映射、灰度策略 | 必须可审计、可回滚 |

禁止把知识库作为 capability 唯一来源。知识库可以补充术语、SOP、解释和样例，但不能声明“某能力可执行”。

## 7. 路由到执行的标准流程

### 7.1 候选能力生成

1. Router 输出候选 `intent_key`。
2. 受控术语索引提供归一化词和 route hints。
3. CapabilityRegistry 根据 intent、domain、route_terms、role、phase 生成候选能力。
4. 候选能力按可用状态、项目策略、schema 匹配度、历史成功率排序。

### 7.2 能力预检

预检输出：

```ts
type CapabilityPreflightResult = {
  capability_id: string
  status: 'executable' | 'missing_input' | 'permission_denied' | 'not_available' | 'requires_confirmation' | 'blocked'
  resolved_slots: Record<string, unknown>
  missing_slots: MissingSlot[]
  dictionary_calls_required: string[]
  project_resolution: ProjectResolution
  permission_status: 'allowed' | 'partial_allowed' | 'denied'
  warnings: string[]
  next_action:
    | 'call_service'
    | 'ask_clarification'
    | 'ask_confirmation'
    | 'create_case'
    | 'answer_boundary'
}
```

规则：

- `not_available` 时不继续补业务参数，直接说明能力缺口或生成 Case。
- `missing_input` 时只追问必填且不可推断字段。
- `requires_confirmation` 时展示将要执行的动作和影响。
- `permission_denied` 时阻断，不回退到顶部项目。

### 7.3 执行

执行请求统一封装为：

```ts
type ServiceExecutionRequest = {
  execution_id: string
  capability_id: string
  conversation_id: string
  message_id: string
  user_id: string
  role_id: string
  project_refs: string[]
  project_resolution: ProjectResolution
  input: Record<string, unknown>
  permission_context: PermissionContext
  trace_context: TraceContext
}
```

执行响应统一封装为：

```ts
type ServiceExecutionResponse = {
  execution_id: string
  capability_id: string
  binding_type: ServiceBinding['binding_type']
  status: 'success' | 'partial' | 'empty' | 'waiting' | 'failed'
  output?: unknown
  parsed_result?: unknown
  evidence_refs: EvidenceRef[]
  errors: ServiceExecutionError[]
  next_actions: RecommendedAction[]
  raw_payload_ref?: string
}
```

## 8. 各业务域绑定要求

| 业务域 | 绑定形态 | 关键预检 | 结果要求 |
|---|---|---|---|
| 问数 | MCP tool + Orchestrator | 项目、日期、报表域、字典依赖 | 表格、摘要、来源、下一步建议 |
| 定时报表 | Workflow + 内部 API | 查询计划、项目、数据延迟策略、确认 | 任务 ID、下次执行时间、资产策略 |
| 包交付 | Workflow + MCP | 单项目、包类型、上报检查状态、后台更新状态 | 包版本状态、可投结论、证据 |
| 联调 | MCP / Workflow | 上报检查通过、项目、媒体、包版本 | 联调状态、失败原因、截图 / 日志 |
| 异常排查 | Workflow + 多 MCP | 异常类型、时间、对象、证据 | 诊断结论、置信度、检查项、Case |
| 指标解释 | 结构化口径库 + 知识库补充 | 指标命中、内部口径优先 | 口径、公式、适用范围、来源 |
| 需求沟通 | DemandWorkflow + Case | 能力可用性、字段缺口、用户确认 | 草案、Case 编号、需求池记录 |
| 我的资产 | 内部 API | 用户权限、项目过滤、资产类型 | 资产列表、可见性、来源 |
| 通用问答 | Model + 知识库 / 外部资料 | 是否涉及业务事实或项目数据 | 明确来源和边界 |

## 9. 写死、配置、工具、知识库边界

必须写进代码：

- 能力发现和执行顺序。
- 权限、项目、确认、审计红线。
- 状态机和错误分类。
- Schema 校验、必填字段阻断。
- Evidence / Trace 事件结构。
- 禁止伪造数据和伪造 Case 的规则。

做成动态配置：

- route terms、alias、能力权重、灰度开关。
- Capability override、临时禁用、parser 绑定、UI 组件绑定。
- 追问文案、失败文案、下一步建议模板。
- 各业务域的默认值策略和字段映射。

封装在 Tool / MCP / Workflow：

- 真实查数、包状态、联调、上报检查、归因、调度、资产、Case 创建。
- 服务 schema、错误码、返回结构。
- 写操作和外部系统状态变化。

放入知识库：

- 术语、口径、SOP、历史 Case、使用说明、方法论。
- 能力使用边界说明和字段含义解释。

## 10. 错误分类和失败闭环

统一错误类型：

```ts
type ServiceExecutionErrorType =
  | 'capability_not_registered'
  | 'capability_disabled'
  | 'server_disconnected'
  | 'tool_not_found'
  | 'schema_mismatch'
  | 'missing_required_slot'
  | 'permission_denied'
  | 'project_resolution_failed'
  | 'mcp_call_failed'
  | 'workflow_failed'
  | 'result_parse_failed'
  | 'empty_result'
  | 'timeout'
  | 'external_waiting'
```

闭环规则：

- 缺用户字段：追问。
- 权限不足：阻断并说明，不创建误导性 Case。
- 能力未接入：可生成 `capability_not_connected` Case。
- 工具失败：允许一次重试；仍失败则生成失败 Case。
- 返回为空：说明筛选条件和数据范围，建议放宽条件或转诊断。
- 解析失败：保留 raw payload ref，生成工程排查 Case。
- 外部等待：返回等待状态和下一步检查时间。

## 11. Trace 与 Evidence 契约

每次服务执行必须记录：

- `capability.discovered`
- `capability.preflight`
- `slot.resolved`
- `permission.checked`
- `service.binding_selected`
- `tool_call` / `workflow.step` / `skill.started`
- `tool_result` / `workflow.result` / `skill.finished`
- `result.parsed`
- `evidence.attached`
- `case.created` 或 `case.skipped`
- `answer.final`

Trace 必须能回答：

- 为什么选这个能力。
- 为什么没有选其他候选能力。
- 哪些字段来自用户、上下文、字典、配置或历史结果。
- 实际调用了哪个 server / tool / workflow。
- 返回结果如何解析。
- 为什么失败或为什么需要追问。

## 12. 后台治理

后台至少需要以下治理面：

1. 全局能力清单：按 domain、phase、status、binding_type 查看。
2. 能力详情：查看 schema、绑定服务、权限策略、项目策略、输入输出契约。
3. 能力刷新：触发 MCP `tools/list`、Skill 合约刷新、Workflow 定义刷新。
4. Override 管理：临时禁用、route terms、parser、UI 组件和灰度开关。
5. 变更审计：谁改了能力配置、改前改后、影响范围。
6. 测试映射：某条测试集用例命中了哪个 capability，失败在哪一层。
7. 健康检查：server disconnected、tool not found、schema mismatch、近期失败率。

## 13. 验收规则

P0 验收：

- 任一业务意图都能输出候选 capability 和选择原因。
- 已上线 MCP 能力能被发现，不再被误判为缺失。
- 工具调用前能看到项目、权限、slot、schema 预检结果。
- 成功结果有 Evidence；失败结果有错误分类和下一步建议。
- 写操作必须用户确认并记录审计。
- 无真实调用不得输出“已完成”“已提交”“已联调成功”“可投放”等完成口吻。

P1 验收：

- 支持 capability override 的版本管理和回滚。
- 支持按测试集逐条生成 capability mapping。
- 支持连弩回放完整 Trace。
- 支持跨业务域复合计划，例如查数后转诊断、查询后创建定时报表、包失败后生成 Case。

## 14. 工程实施清单

1. 新增全局 `CapabilityRegistry`，抽象 MCP、Skill、Workflow、内部 API。
2. 将 `ReportCapabilityManifest` 的模式推广为 `GlobalCapabilityManifest`，问数保留领域扩展。
3. 新增 `CapabilityPreflight`，统一项目、权限、slot、schema、确认策略。
4. 新增 `ServiceBindingExecutor`，封装 MCP / Skill / Workflow / API 调用和错误分类。
5. 新增 `ResultParserRegistry`，按 `parser_id` 解析返回结构。
6. 扩展 `IntentRouteDecision`，必须带 `capability_id`、`capability_status`、`preflight_status`。
7. Chat route 改为基于 CapabilityRegistry 执行，不允许直接按关键词调用工具。
8. 后台增加全局能力清单页，并保留问数能力矩阵作为领域视图。
9. Trace 增加 capability 和 service binding 事件。
10. Case 生成接入统一错误分类。
11. 为包交付、联调、异常排查、指标解释、需求沟通补齐 capability 配置。
12. 将测试集验收扩展为 route、preflight、tool call、parse、ui、evidence 六段断言。

## 15. 用户需求回映射

| 用户原始诉求 | 设计满足情况 |
|---|---|
| “MCP 本身不缺，已经上线给其它 chat 使用过” | 能力事实来自 MCP `tools/list` 和运行态配置，防止误判缺失 |
| “能力发现环节是不是没生效” | 定义全局 CapabilityRegistry 和 Preflight，让发现成为路由必经步骤 |
| “哪些写死、哪些动态配置、哪些封装在 tool、哪些放知识库” | 第 9 节明确四层边界 |
| “正确路由、自动补齐信息、追问、真实调用工具、解析结果、下一步建议、证据沉淀” | 设计覆盖路由到执行到 Evidence / Case 的完整闭环 |
| “系统性解决，不要一个个补假功能” | 通过统一注册、绑定、预检、执行、解析、治理机制解决 |
