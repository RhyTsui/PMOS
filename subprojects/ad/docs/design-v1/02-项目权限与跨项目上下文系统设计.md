# 项目权限与跨项目上下文系统设计

## 1. 对应需求

本设计对应：

- `docs/prd-v2.2/05-项目角色权限与跨项目设计.md`
- `docs/prd-v2.2/20-对话路由需求PRD.md`
- `docs/design-v1/01-对话路由系统设计.md`

## 2. 设计目标

项目权限与跨项目上下文是小乔智投的安全底座。系统既要支持自由对话和跨项目分析，又不能因为历史会话、顶部项目、资产引用或个人记忆导致越权查询、错查项目或错误展示。

本设计目标：

- 用户项目权限动态生效。
- 顶部项目只是默认上下文。
- 用户明示项目优先。
- 项目解析不得硬编码项目名、项目 ID 或示例 A/B。
- 会话、资产、自动化任务可以跨项目。
- 包交付必须单项目。
- 前台按权限动态过滤。
- Trace 保留完整项目引用。

## 3. 当前实现核对

当前已有基础：

- 前端保存 `projectContextText`，发送消息时作为 `[项目上下文]` 传入。
- Chat 主链路已能读取 `projectContext`。
- `context-compiler` 和 `conversation-context` 能把项目上下文编译进业务上下文。
- `ProjectBinding`、`PermissionContext`、`ProjectResolution` 已在 PRD 数据模型中定义。
- 会话、资产、自动化任务已有入口，但项目绑定和动态权限过滤还未完全统一。

当前风险：

- 右上角项目可能被误当成真实请求项目。
- 用户明示项目未解析时，可能请求顶部项目。
- 资产和历史会话如果不按当前权限动态过滤，可能暴露已失效权限数据。
- 自动化任务如果只按创建时权限运行，权限变化后可能继续生成不可见项目结果。
- 项目解析如果写死示例项目或项目 ID，会导致环境切换后失效。

## 4. 项目解析红线

项目解析必须是数据驱动，禁止硬编码：

- 禁止硬编码项目名。
- 禁止硬编码项目 ID。
- 禁止把文档中的 A/B 示例写入代码。
- 禁止用顶部项目覆盖用户明示项目。
- 禁止明示项目无权限时回退顶部项目。

A/B 只表示：

- A：右上角当前选择项目。
- B：用户自然语言中明示的另一个项目。

真实实现必须基于：

- 用户当前有权限的项目列表。
- 项目服务或项目字典。
- 项目别名配置。
- APPID / project_id / projectId。
- 历史会话项目。
- 个人记忆项目上下文。

推荐解析函数：

```ts
resolveProjectContext({
  rawText,
  uiSelectedProject,
  allowedProjects,
  projectDictionary,
  historyContext,
  personalMemory,
})
```

## 5. 核心产品规则

### 5.1 自由对话

会话不按项目强隔离。用户可以在一个会话里问多个项目，也可以做跨项目对比。

但每一轮执行必须明确本轮真实请求项目，即 `effective_project_refs`。

### 5.2 动态权限

项目权限每次请求和每次展示都要重新判断。

不能因为用户过去看过某项目，就继续展示该项目内容。

### 5.3 包交付单项目

包交付必须单项目。用户问多个项目的包时：

- 追问选择一个项目，或
- 拆成多个独立包交付任务。

### 5.4 Trace 完整保留

前台展示按权限过滤，但 Trace 需要保留完整项目引用。连弩回放权限由连弩平台控制。

## 6. 数据模型

### 6.1 PermissionContext

```ts
type PermissionContext = {
  user_id: string
  user_scope_key: string
  role_id: string
  role_name: string
  allowed_project_refs: string[]
  allowed_actions: string[]
  current_project_ref?: string
}
```

### 6.2 ProjectBinding

```ts
type ProjectBinding = {
  project_refs: string[]
  default_project_ref?: string
  last_active_project_ref?: string
  source_project_refs?: string[]
}
```

### 6.3 ProjectResolution

```ts
type ProjectResolution = {
  ui_selected_project_ref?: string
  explicit_project_mentions: Array<{
    raw: string
    project_ref?: string
    project_name?: string
    confidence: number
    matched_by: 'exact_name' | 'alias' | 'app_id' | 'history' | 'fuzzy'
  }>
  inherited_project_refs: string[]
  effective_project_refs: string[]
  resolution_source:
    | 'explicit_user_project'
    | 'ui_selected_project'
    | 'cross_project_compare'
    | 'history_inherited'
    | 'clarification_required'
  conflict_detected: boolean
  clarification_needed: boolean
  clarification_question?: string
  permission_status: 'allowed' | 'partial_allowed' | 'denied' | 'unknown'
}
```

### 6.4 ProjectScopedObject

```ts
type ProjectVisibilityState =
  | 'visible'
  | 'partially_hidden'
  | 'hidden_by_permission'
  | 'permission_unknown'

type ProjectScopedObject = {
  object_id: string
  object_type:
    | 'conversation'
    | 'message'
    | 'asset'
    | 'automation_task'
    | 'report'
    | 'scheduled_report_result'
    | 'package_delivery_record'
    | 'case'
    | 'evidence'
  project_binding: ProjectBinding
  visibility: ProjectVisibilityState
  hidden_project_refs?: string[]
}
```

## 7. 系统流程

### 7.1 Chat 本轮请求

1. 前端传入用户原文和顶部项目上下文。
2. 后端解析登录用户，得到 `PermissionContext`。
3. 后端获取用户有权限项目列表。
4. 后端读取项目字典和别名配置。
5. 后端调用 `resolveProjectContext`。
6. 如果项目明确且有权限，生成 `effective_project_refs`。
7. 如果项目歧义，返回追问。
8. 如果项目无权限，返回无权限说明。
9. Workflow / Skill / MCP 请求只使用 `effective_project_refs`。

### 7.2 打开历史会话

1. 读取会话 `ProjectBinding`。
2. 检查 `default_project_ref` 或 `last_active_project_ref` 是否仍有权限。
3. 有权限时，右上角项目选择器切换到该项目。
4. 无权限时，不切换到无权限项目。
5. 会话内容按当前权限动态隐藏或脱敏。
6. 前台提示“部分项目内容因权限变化不可见”。

### 7.3 查看资产

1. 资产列表按当前用户权限过滤。
2. 单项目资产无权限时隐藏。
3. 跨项目资产部分无权限时显示 `partially_hidden`。
4. 资产详情中的表格、图表、证据按字段或区块隐藏。
5. 资产来源 Trace 不在前台完整展开无权限内容。

### 7.4 自动化任务运行

1. 创建和编辑任务必须绑定项目。
2. 任务运行前重新校验项目权限。
3. 无权限项目跳过或标记不可见，不能继续生成可见结果。
4. 定时报表产物进入资产后继续按项目权限过滤。

## 8. 前端职责

前端负责：

- 展示右上角当前项目。
- 传递顶部项目上下文。
- 展示项目冲突追问。
- 展示无权限提示。
- 在跨项目结果中标记部分不可见。
- 打开历史会话时根据后端返回状态切换或不切换顶部项目。

前端禁止：

- 自行决定真实请求项目。
- 在用户明示项目无权限时替换成顶部项目。
- 展示无权限项目明细。
- 展示完整 Trace 中无权限内容。

## 9. 后端职责

后端负责：

- 从登录态解析用户和角色。
- 查询当前项目权限。
- 查询项目字典和别名。
- 解析 `ProjectResolution`。
- 校验每个工具请求项目。
- 返回对象级 `visibility`。
- 记录 Trace。

后端禁止：

- 信任前端传入的项目作为最终请求项目。
- 只用顶部项目构造查询请求。
- 项目解析低置信度时直接执行。
- 无权限时回退到其它项目。

## 10. Workflow / Skill / MCP 契约

所有能力请求必须携带：

```ts
type ProjectAwareExecutionContext = {
  permission_context: PermissionContext
  project_resolution: ProjectResolution
  project_refs: string[]
  trace_context: {
    conversation_id?: string
    message_id?: string
    workflow_run_id?: string
  }
}
```

能力层要求：

- 不自行推断项目。
- 不接受空项目执行高风险业务。
- 再次校验项目权限。
- 返回结果时携带项目引用。

## 11. Trace 契约

Trace 必须记录：

- `user_id`
- `user_scope_key`
- `role_id`
- `allowed_project_refs`
- `ui_selected_project_ref`
- `explicit_project_refs`
- `effective_project_refs`
- `hidden_project_refs`
- `permission_status`
- `visibility_state`
- `project_resolution_source`
- `permission_decision_reason`

## 12. 失败闭环

### 12.1 项目无权限

提示用户无权限，不执行查询，不回退其它项目。

### 12.2 项目歧义

追问用户确认具体项目。

### 12.3 部分项目无权限

展示有权限部分，隐藏无权限部分，并提示部分不可见。

### 12.4 能力不支持跨项目

提示能力只支持单项目，要求用户选择项目或拆成多个任务。

### 12.5 权限接口失败

不执行高风险查询。可提示权限状态暂不可用，并生成失败记录。

## 13. 验收场景

- 顶部选 A，用户问 B 项目数据，请求 B。
- 顶部选 A，用户问无权限 B，阻断且不请求 A。
- 用户打开历史会话 C，已无 C 权限，不切换顶部项目，隐藏 C 内容。
- 跨项目报表 A+B，用户只有 A 权限，只展示 A 部分并提示 B 不可见。
- 自动化任务覆盖 A+B，用户失去 B 权限，列表标记部分不可见，产物只展示 A。
- 包交付请求 A+B，系统追问选择单项目或拆成两个任务。
- 资产详情中 Evidence 包含无权限项目，Evidence 局部隐藏。
- Trace 发送完整项目引用，但前台展示过滤后的内容。
- 用户权限变化后，刷新页面立即生效，不依赖历史缓存。
- 项目字典中 A/B 替换成任意真实项目后，解析规则仍成立。
- APPID 明确时优先按 APPID 匹配。
- 项目别名冲突时必须追问。

## 14. 工程实施映射

P0：

- 建立项目解析服务或工具函数。
- Chat 请求增加 `ProjectResolution`。
- 工具请求统一使用 `effective_project_refs`。
- 会话、资产、自动化返回 `ProjectBinding` 和 `visibility`。
- 无权限项目动态隐藏。
- Trace 增加项目解析和权限字段。

P1：

- 项目别名管理。
- 历史 `projectContextText` 迁移为结构化项目绑定。
- 个人记忆项目继承接入项目解析。
- 连弩项目权限评测集。
