# 异常排查系统设计

## 1. 文档目的

本文定义小乔智投一期“异常排查”的系统设计，承接：

- `docs/prd-v2.2/08-异常排查需求沟通与指标解释PRD.md`
- `docs/prd-v2.2/10-数据建模与请求反馈模型.md`
- `docs/prd-v2.2/11-状态流转与业务结论说明.md`
- `docs/prd-v2.2/12-Chat交互追问与结果呈现规范.md`
- `docs/design-v1/01-对话路由系统设计.md`
- `docs/design-v1/02-项目权限与跨项目上下文系统设计.md`
- `docs/design-v1/04-数据查询与报表系统设计.md`
- `docs/design-v1/07-问数编排与结果呈现系统设计.md`
- `docs/design-v1/09-包交付与联调系统设计.md`

本文只覆盖异常排查。指标解释进入 `11-指标解释与知识库检索系统设计`，需求沟通进入 `12-需求沟通与 Case 闭环系统设计`。

本文重点解决：

- 用户问“为什么没量、为什么没回传、为什么对不上、为什么掉了”时，系统如何正确路由。
- 异常排查如何在信息不足时追问，而不是过早兜底。
- 诊断 Workflow 如何调用问数、包交付、联调、采集网关、监控巡检等真实能力。
- 诊断结论如何带证据、置信度、下一步建议和 Case。
- 系统无力定位时，如何把失败也做成闭环。

## 2. 设计目标

异常排查的目标不是一次性“猜原因”，而是把异常定位过程产品化为可追踪的诊断链。

目标：

- 正确识别异常排查意图，并区分宽泛巡检、指标差异、回传问题、包/联调问题、报表质量问题。
- 自动补齐项目、媒体、时间、指标、对比数据源、样例等上下文。
- 信息不足时只追问会影响诊断路径的关键字段。
- 调用已接入的真实 Workflow / Skill / MCP，不由 Prompt 生成异常原因。
- 输出最可能原因、置信度、已检查项、证据、下一步动作和责任角色。
- 证据不足时返回 `waiting_input` 或 `partial`，由 Chat 继续追问。
- 多轮后仍无法定位时生成 Case。

## 3. 当前实现核对

### 3.1 已具备

当前系统已有以下基础：

- `IntentType` 已包含 `diagnosis` 和 `monitor`。
- `AgentType` 已包含 `diagnosis` 和 `monitoring`。
- 路由层已识别异常、差异、失败、不一致等表达：
  - `intent-router.ts`
  - `intent-route-rules.ts`
  - `intent-route-engine.ts`
- `slot-resolver.ts` 已为 `diagnosis` 定义基础 slot：
  - 媒体平台。
  - 项目或应用。
  - 排查时间。
  - 异常指标。
  - 对比数据源。
  - 样例或截图。
- Skill Contract 已具备相关能力声明：
  - `ads_health_monitor_skill`
  - `metric_diff_diagnosis_skill`
  - `delivery_diagnosis_skill`
  - `auto_debug_skill`
  - `report_data_quality_check_skill`
  - `preflight_quality_check_skill`
- MCP 配置中已有采集、包、媒体配置、自动联调、监测链接等工具声明。
- 问数链路已有空结果诊断、质量检查、失败 Case 生成和 Trace 证据字段基础。

### 3.2 当前缺口

当前仍缺少：

- 独立的 `DiagnosisWorkflow`。
- 诊断任务对象、诊断步骤、证据链和状态模型。
- 宽泛异常巡检到具体排查的转换规则。
- 指标差异按指标类型分流的确定性规则。
- 问数结果、包交付结果、联调结果、采集检查结果之间的证据融合。
- 多轮追问计数和失败 Case 生成策略。
- 诊断结果卡片的统一数据契约。
- 诊断 Case 与我的资产、Trace、连弩评测的统一关联。

## 4. 核心产品规则

### 4.1 不猜原因

Chat 不得根据语言常识直接输出确定性异常原因。

禁止：

- 没查数据就说“可能是回传延迟”并当作结论。
- 没有采集或报表证据就判断媒体异常。
- 没有包/联调证据就判断包不可用。
- 没有口径库或报表结果就判断 BI 与智投谁对谁错。

允许：

- 输出“待验证假设”。
- 明确说明缺少哪些证据。
- 给出下一步检查建议。

### 4.2 先区分巡检与排查

用户问“昨天投放有没有异常”“最近广告有什么问题”时，这是宽泛巡检，优先进入 `monitor` / `ads_health_monitor_skill`。

用户问“为什么激活少了”“BI 和智投注册对不上”“巨量回传失败”时，这是具体排查，进入 `diagnosis`。

规则：

- 宽泛问题先巡检，巡检发现具体异常后再转诊断。
- 具体问题直接诊断，不绕到通用监控。
- 从问数结果发现空值、字段缺失、日期缺口、异常波动时，可自动建议进入诊断。

### 4.3 按异常类型分流

诊断 Workflow 必须先识别异常类型：

- `no_volume`：没量、消耗为 0、展示点击异常低。
- `no_postback`：没回传、回传少、事件不上报。
- `metric_mismatch`：BI、媒体后台、智投报表对不上。
- `metric_drop`：ROI、激活、注册、付费、留存下降。
- `package_or_integration`：包、分包、联调、应用共享相关。
- `report_quality`：报表空结果、字段缺失、日期缺口、异常波动。
- `configuration`：归因、监测链接、事件映射、账号 token、媒体配置。
- `unknown`：暂未归类。

异常类型决定后续调用路径和追问字段。

### 4.4 消耗类与转化类分流

消耗、展示、点击异常不默认进入回传链路。

规则：

- 消耗、展示、点击优先检查媒体报表采集、账号权限、预算/计划状态、调度延迟。
- 激活、注册、付费、ROI、ROAS、留存优先检查口径、归因、回传、事件上报和报表聚合。
- 用户明确说“回传”时，再进入回传链路。

### 4.5 多轮后再 Case

异常诊断失败不等于立即结束。

建议策略：

1. 第一次缺信息：追问关键字段。
2. 第二次仍不充分：缩小范围，给出可选诊断路径。
3. 已有足够输入但工具失败：重试或降级为部分诊断。
4. 多轮仍无法定位：生成 `diagnosis_unresolved` Case。

## 6. 诊断流程

### 6.1 总流程

```text
Chat
-> 术语归一化
-> 意图路由
-> 项目解析与权限校验
-> slot 补齐
-> 能力发现
-> DiagnosisWorkflow
-> 调用诊断 Skill / MCP / 关联 Workflow
-> 汇总 Evidence
-> 生成 Findings
-> 输出结论 / 追问 / Case
```

### 6.2 宽泛巡检

触发表达：

- “昨天投放有什么异常”
- “最近广告有什么问题”
- “看下项目健康情况”
- “有没有回传延迟”

流程：

1. 进入 `monitor`。
2. 调用 `ads_health_monitor_skill`。
3. 检查媒体报表、点击日志、自归因、平台上报、数据质量、调度状态。
4. 如果无异常，输出巡检摘要和证据。
5. 如果发现具体异常，生成诊断建议，并允许用户一键进入 `DiagnosisWorkflow`。

### 6.3 指标差异排查

触发表达：

- “BI 和智投注册对不上”
- “媒体后台激活比我们多”
- “为什么消耗不一致”

流程：

1. 确认指标、项目、媒体、时间、对比数据源。
2. 调用报表查询 Skill 查询系统实际值。
3. 调用指标口径 / 口径库对齐统计范围。
4. 按指标类型选择排查路径。
5. 转化类检查回传、归因、事件上报。
6. 消耗类检查媒体报表采集、账号权限和调度。
7. 输出差异范围、可能原因、证据和下一步。

### 6.4 没回传 / 回传少

流程：

1. 确认项目、媒体、事件、时间、包或活动。
2. 查询平台事件上报报告。
3. 查询点击日志和回传日志。
4. 检查归因配置、监测链接、事件映射。
5. 如涉及包或联调，调用包交付或自动联调能力。
6. 输出阻塞点和责任角色。

### 6.5 没量 / 消耗异常

流程：

1. 确认项目、媒体、时间、计划或账户范围。
2. 查询媒体报表采集状态。
3. 查询消耗、展示、点击等基础指标。
4. 检查账号权限、预算/计划状态、调度任务和数据延迟。
5. 不默认检查回传，除非用户明确提到回传或转化。
6. 输出异常范围、已排除项和下一步。

### 6.6 联调失败原因排查

流程：

1. 确认项目、媒体、终端、联调任务或包。
2. 查询自动联调任务。
3. 查询联调步骤、截图、日志和最终结果。
4. 结合包交付状态判断是否属于包交付阻塞。
5. 输出失败步骤、原因、证据和下一步。
6. 自动生成 Case。

### 6.7 报表质量异常

触发来源：

- 用户主动问“这个查询结果是不是有问题”。
- 问数链路返回空结果、字段缺失、日期缺口、异常波动。

流程：

1. 读取 `ReportQueryPlan` 和 `ReportQueryResult`。
2. 执行 `report_data_quality_check_skill`。
3. 判断根因：
   - 空结果。
   - 字段缺失。
   - 日期缺口。
   - 权限或范围异常。
   - 数据延迟。
   - 返回解析失败。
4. 输出质量检查结果和是否建议继续业务分析。

## 7. Chat 交互策略

### 7.1 追问原则

只追问会改变诊断路径的字段。

P0 必填：

- 项目或应用。
- 异常时间。
- 异常指标或问题对象。

按类型必填：

- 媒体：媒体相关问题必填。
- 对比数据源：指标差异问题必填。
- 事件：回传、注册、付费等事件问题必填。
- 包 / 联调任务：包或联调问题必填。

推荐补充：

- 截图。
- 明细。
- trace_id。
- 失败样例。

### 7.2 追问话术结构

```text
我需要先确认 2 个会影响排查路径的信息：
1. 异常发生在哪个项目 / 应用？
2. 对比的是媒体后台、智投报表还是 BI？

有截图或 trace_id 可以一起发，我会作为证据挂到排查记录里。
```

### 7.3 结果结构

诊断结果必须包含：

- 当前结论。
- 置信度。
- 异常类型。
- 影响范围。
- 已检查项。
- 证据来源。
- 未确认问题。
- 下一步建议。
- Case 入口。

禁止只输出泛化建议。

## 8. Workflow / Skill / MCP 边界

### 8.1 Chat 负责

- 意图识别。
- 项目解析和权限入口。
- 必填字段追问。
- 调用 DiagnosisWorkflow。
- 展示诊断结果、证据和下一步。
- 在用户确认或失败闭环时生成 Case。

Chat 不负责：

- 生成异常原因。
- 自行判断报表数据是否正确。
- 自行判断包或联调状态。
- 自行生成媒体后台状态。

### 8.2 DiagnosisWorkflow 负责

- 管理诊断状态。
- 选择诊断路径。
- 编排诊断 Skill。
- 调用问数、包交付、联调、监控巡检等已有 Workflow / Skill。
- 汇总 Evidence。
- 生成 Findings。
- 判断是否 resolved、partial、unresolved。
- 生成 Case。

### 8.3 Skill 负责

- `ads_health_monitor_skill`：宽泛巡检。
- `metric_diff_diagnosis_skill`：指标差异排查。
- `report_data_quality_check_skill`：报表结果质量检查。
- `delivery_diagnosis_skill`：包交付阻塞排查。
- `auto_debug_skill`：联调执行与步骤观测。
- `preflight_quality_check_skill`：投放前质量检查。
- 后续可新增 `callback_diagnosis_skill`、`attribution_config_diagnosis_skill`。

### 8.4 MCP / 内部接口负责

- 报表查询。
- 采集状态。
- 点击日志状态。
- 自归因状态。
- 平台事件上报。
- 数据质量监控。
- 调度状态。
- 包状态。
- 联调步骤和结果。
- 监测链接和归因配置。

## 10. 前端设计

### 10.1 诊断结果卡

诊断结果卡展示：

- 异常类型。
- 当前结论。
- 置信度。
- 影响范围。
- 已检查项。
- 证据来源。
- 未确认问题。
- 下一步建议。
- Case 状态。

### 10.2 诊断过程组件

过程组件展示：

- 上下文确认。
- 报表查询。
- 基线对比。
- 采集检查。
- 回传检查。
- 包/联调检查。
- 配置检查。
- Case 创建。

每个步骤必须展示状态和证据入口，不展示内部栈信息。

### 10.3 从问数结果进入诊断

当问数结果存在质量风险时，前端应展示：

- “继续排查”入口。
- 当前查询计划。
- 风险类型。
- 已有证据。

点击后创建 `DiagnosisTask`，并把 `ReportQueryPlan` / `ReportQueryResult` 作为 `previous_result_refs`。

## 11. Trace 与 Evidence

每次诊断必须记录：

- `trace_id`
- `conversation_id`
- `task_id`
- `user_id`
- `project_refs`
- `diagnosis_type`
- `input_context`
- `slot_resolution`
- `capability_check`
- `workflow_steps`
- `skill_calls`
- `mcp_requests`
- `mcp_responses_summary`
- `findings`
- `missing_inputs`
- `next_actions`
- `case_id`

Evidence 必须支撑每个 Finding。没有 Evidence 的内容只能标记为假设或待验证。

## 12. Prompt 与配置边界

写进代码的内容：

- 诊断状态枚举。
- 异常类型枚举。
- 消耗类和转化类分流规则。
- resolved / partial / unresolved 判定。
- Case 生成条件。
- 权限校验。

写进运行时配置的内容：

- 指标到诊断链路映射。
- 媒体到可用检查工具映射。
- 诊断步骤启用开关。
- 失败重试策略。
- Case 优先级规则。

写进 Tool / MCP 的内容：

- 真实报表数据。
- 采集状态。
- 回传日志。
- 归因配置。
- 包状态。
- 联调结果。

写进知识库的内容：

- 常见异常解释。
- 排查 SOP。
- 指标口径补充说明。
- Case 复盘沉淀。

知识库不能替代实时诊断证据。

## 13. 失败闭环

### 13.1 失败类型

| 类型 | 处理 |
|---|---|
| 项目缺失 | 追问项目 |
| 无项目权限 | 阻断，不回退顶部项目 |
| 时间缺失 | 追问异常时间 |
| 指标缺失 | 追问异常指标 |
| 对比数据源缺失 | 指标差异场景追问 |
| 能力未接入 | 说明边界，整理事实，可生成 Case |
| MCP 失败 | 重试或 partial，多次失败生成 Case |
| 证据不足 | 返回 waiting_input 或 partial |
| 结论冲突 | 标记冲突证据，生成人工处理 Case |

### 13.2 Case 生成条件

生成 `diagnosis_unresolved` Case 的条件：

- 已完成关键追问但仍无法定位。
- 已调用可用工具但结果不足。
- 工具返回冲突结论。
- 关键 MCP 不可用且影响结论。
- 用户要求转人工或继续跟进。

Case 必须包含：

- 原始问题。
- 项目。
- 异常类型。
- 时间范围。
- 异常指标。
- 对比数据源。
- 已确认事实。
- 未确认问题。
- 已调用能力。
- Evidence。
- 下一步建议。
- 建议处理角色。

## 14. 验收场景

P0：

- 用户问“为什么没回传”，系统追问项目、媒体、事件和时间，不直接猜原因。
- 用户问“BI 和智投注册对不上”，系统要求对比数据源并进入指标差异排查。
- 用户问“昨天投放有什么异常”，系统进入监控巡检，不直接进入具体诊断。
- 消耗异常不默认检查回传链路。
- 转化异常必须检查口径、回传、归因和事件上报。
- 问数空结果或质量风险可以进入诊断。
- 联调失败排查必须读取联调步骤、截图、日志或明确缺证据。
- 多轮仍无法定位时生成 Case。
- 所有结论必须带 Evidence。

P1：

- 诊断结果可保存为资产或 Case。
- 权限变化后，诊断资产和 Case 中不可见项目数据被过滤。
- Trace 可跳转连弩回放。
- 诊断步骤支持前端过程组件展示。

P2：

- 周期性异常巡检自动生成诊断任务。
- 小闪通知诊断结果。
- Case 复盘自动沉淀到知识库。
- 诊断路径可通过后台配置扩展。
