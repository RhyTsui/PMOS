# 包交付与联调系统设计

## 1. 文档目的

本文定义小乔智投一期“包交付与联调”的系统设计，承接：

- `docs/prd-v2.2/07-包交付与联调状态PRD.md`
- `docs/prd-v2.2/11-状态流转与业务结论说明.md`
- `docs/review/投放包直交付需求文档-2026-05-18.md`
- `docs/design-v1/01-对话路由系统设计.md`
- `docs/design-v1/02-项目权限与跨项目上下文系统设计.md`
- `docs/design-v1/06-问数知识策略与配置治理系统设计.md`

本文重点解决：

- 用户问“这个包能不能投”时，系统如何正确路由、补齐项目和包上下文。
- 包交付 Workflow 如何承接状态机，而不是让 Chat 伪造状态。
- 上报检查、媒体后台更新、智投后台更新、自动联调、Case 和资产如何分层。
- “可交付投放”如何由系统派生，不能人工直接改成可投。
- 包交付结果如何展示证据、下一步建议和失败闭环。

## 2. 设计目标

包交付不是“联调工具入口”，而是面向优化师和投放侧的端到端交付结论。

目标：

- 用户可以直接问某项目、某媒体、某包是否可投放。
- 系统能识别包交付意图，并明确项目、媒体、终端、包类型和版本。
- 所有包状态、上报检查、媒体后台更新、联调结果必须来自真实 Workflow / Skill / MCP。
- Chat 只负责识别、追问、调用、解释和沉淀，不负责自行判断包状态。
- 包交付 Workflow 负责状态机、工具编排、结论派生、旧包替代和 Case 生成。
- Debug Automation 只是底层联调能力，不等同于最终可投结论。
- 失败也要闭环：先追问和补齐，再真实调用；多轮后仍不能完成时生成 Case。

- 旧包被新包替代和历史包默认折叠的结构化模型。
- “可交付投放”的派生规则。

- Chat 对顶部项目和用户明示项目冲突的包交付专门处理。
- 单独触发联调前的上报检查通过校验。

## 4. 核心产品规则

### 4.1 单项目规则

包交付是单项目能力。

规则：

- 用户只问“这个包能投吗”，且当前会话没有明确项目时，Chat 必须追问项目。
- 顶部项目只是默认上下文，不是唯一事实。
- 用户明示“B 项目包能投吗”时，即使顶部选择的是 A 项目，也必须解析 B 项目并校验 B 项目权限。
- 用户跨项目问包时，Chat 必须追问要先看哪个项目，或拆成多个单项目任务。
- 包交付 Workflow 的单次执行只能绑定一个项目。

### 4.2 不强制业务拦截

一期不做“禁止建监测活动”的硬限制，也不新增后台临时放行功能。

原因：

- B 端业务存在临时投放、补救、验证和人工判断场景。
- 强阻断会把系统变成业务风险承担方，并给后续运营设置额外坑位。
- 当前更优解是提供可信结论、风险提示、证据和 Case。

系统行为：

- 联调不通过时，不把包标记为可交付投放。
- 结果区明确提示“不建议交付”或“风险待关注”。
- 提供失败节点、证据、下一步建议和 Case。
- 不阻断用户在其他系统中的人工动作。

### 4.3 可投结论派生

“可交付投放”必须由系统根据真实状态和证据派生。

禁止：

- 普通人工直接把包改成可投。
- Prompt 根据语言推断可投。
- 知识库内容替代实时包状态。
- Debug Automation 成功后直接等同包可投。

允许：

- 后续如果业务确有需要，可设计后台控制功能，但一期不做。
- 后台控制功能即使后续增加，也必须保留审批、原因、操作者和审计记录。

### 4.4 失败闭环

系统无力完成时也要闭环。

规则：

- 信息不足时先追问，不提前兜底。
- 能力缺失时先披露缺失能力和已尝试工具。
- 上报不通过、联调失败、状态不一致、工具不可用时必须生成结构化失败原因。
- 多轮仍无法完成时生成 Case，并告知用户等待处理。

### 5.2 PackageVersion

```ts
type PackageVersion = {
```

包的交付载体可以是下载地址或 APK 地址，但真正交付对象不是一个裸地址，而是带状态、证据、结论和风险说明的包资产。

### 5.3 PackageDeliveryStatus

```ts
type PackageDeliveryStatus =
  | 'waiting_package'
  | 'report_checking'
  | 'report_check_failed'
  | 'waiting_submission'
  | 'waiting_media_backend_update'
  | 'waiting_zhitou_backend_update'
  | 'integration_checking'
  | 'integration_failed'
  | 'integration_success'
  | 'replaced_by_new_package'
  | 'historical_traceable'
```

### 5.4 PackageBusinessConclusion

```ts
type PackageBusinessConclusion =
  | 'deliverable'
  | 'not_recommended'
  | 'pending'
  | 'risk_attention'
  | 'historical'
```

状态和业务结论必须分开：

- `integration_checking` 是流程状态，业务结论通常是 `pending`。
- `integration_failed` 是流程状态，首次包业务结论通常是 `not_recommended`。
- 新包更新后联调失败，业务结论通常是 `risk_attention`。
- `replaced_by_new_package` 是旧包生命周期状态，业务结论是 `historical`。

```ts
type PackageEvidence = {
```

Evidence 必须能支撑用户回答：

- 谁检查的。

- 下一步要谁处理。

## 6. 状态机设计

### 6.1 媒体包首次流程

适用于巨量、腾讯、快手首次媒体包。

```text
waiting_package
-> report_checking
-> waiting_submission
-> waiting_media_backend_update
-> integration_checking
-> integration_success
```

失败流：

```text
report_checking
-> report_check_failed
```

```text
integration_checking
-> integration_failed
-> case_created
```

流程规则：

1. 智投收到包后，Workflow 调用上报检查 Skill。
2. 上报检查 Skill 调用数据上报报告 MCP。
3. 上报检查通过后输出：“上报检查通过，等待提审。”
4. 上报检查不通过时，不提示用户提审，返回失败项、报告、修复建议和 Evidence。
5. 系统检测到媒体后台更新后，展示媒体后台新版本号。
6. 媒体后台更新后进入联调检查。
7. 联调成功后，业务结论为 `deliverable`。
8. 联调失败后，业务结论为 `not_recommended`，并自动生成 Case。

### 6.2 媒体包更新流程

适用于巨量、腾讯、快手的新包更新。

```text
waiting_package
-> report_checking
-> waiting_media_backend_update
-> integration_checking
-> integration_success
-> old_package_replaced
```

失败流：

```text
report_checking
-> report_check_failed
```

```text
integration_checking
-> integration_failed
-> risk_attention
-> case_created
```

流程规则：

1. 智投收到新包后先做上报检查。
2. 上报不通过时，不提示用户更新包，旧包保持当前有效。
3. 上报通过后输出：“上报检查通过，等待媒体后台更新。”
4. 系统检测到媒体后台更新后，展示新版本号并进入联调检查。
5. 联调成功后，新包 `deliverable`，旧包自动标记 `replaced_by_new_package`。
6. 新包联调失败时，旧包通常已被新包替代，旧包仍标记 `replaced_by_new_package`；新包标记 `risk_attention`，生成 Case，并提示生产验证风险。

### 6.3 官方包 / 智投分包首次流程

```text
waiting_package
-> report_checking
-> integration_checking
-> integration_success
```

流程规则：

1. 官包到达后调用数据上报报告 MCP。
2. 上报不通过时，不触发智投分包联调。
3. 上报通过时，直接触发智投分包联调。
4. 联调成功后，业务结论为 `deliverable`。
5. 联调失败后，业务结论为 `not_recommended`，并生成 Case。

### 6.4 官方包 / 智投分包更新流程

```text
waiting_package
-> report_checking
-> waiting_zhitou_backend_update
-> integration_checking
-> integration_success
-> old_package_replaced
```

流程规则：

1. 官包更新后先做数据上报检查。
2. 上报通过后输出：“数据检查通过，等待智投后台更新。”
3. 系统检测到智投后台更新后，抽一个在投媒体分包检查。
4. 联调成功后，新包可交付投放，旧包标记已被新包替代。
5. 联调失败后生成 Case，并输出风险说明和下一步建议。

## 7. Chat 交互设计

### 7.1 意图触发

以下表达应进入 `get_delivery_packages`：

- “这个项目包能投吗”
- “获取当前项目可交付包”
- “给我广告包下载地址”
- “B 项目巨量包能不能投”
- “这个包卡在哪里”
- “为什么包不能交付”
- “最新包联调通过了吗”
- “验流程”

以下表达应进入 `debugging`：

- “帮我发起联调”
- “单独触发一次巨量联调”
- “看最近一次联调失败原因”

边界：

- 用户问可投结论，优先包交付 Workflow。
- 用户问联调动作，优先自动联调 Skill，但必须校验上报检查通过。
- 用户问为什么不能投，进入交付阻塞排查。

### 7.2 项目确认

项目优先级：

1. 用户当前消息明示项目。
2. 当前任务绑定项目。
3. 会话最近明确确认的项目。
4. 顶部项目选择器。

规则：

- 明示项目和顶部项目冲突时，以明示项目为准。
- 明示项目无权限时，阻断并说明无权限，不回退顶部项目。
- 项目名模糊时，展示候选并追问。
- 包交付不能把多个项目混成一个 Workflow。

### 7.3 必填信息

包交付最小必填：

- 项目。

推荐补充：

- 媒体。
- 终端。
- 包名。
- 版本。

如果只缺推荐字段，系统可以先查询项目下包列表，再提示用户筛选。

单独触发联调必填：

- 项目。
- 媒体。
- 终端。

触发联调前必须确认：

- 上报检查通过。
- 联调配置可用。
- 目标包或分包可定位。

### 7.4 用户可见回答结构

成功回答：

```text
当前可交付投放：X 个包。
主包 / 分包 / 媒体 / 版本 / 下载地址 / 上报检查 / 后台更新 / 联调状态。
建议下一步：使用可交付包创建或更新投放。
证据来源：上报报告、媒体后台版本、联调结果。
```

阻塞回答：

```text
当前不建议交付。
卡点：上报检查不通过 / 等待提审 / 等待媒体后台更新 / 联调失败。
原因：来自真实检查返回。
下一步：谁处理、处理什么。
已生成或可生成 Case。
```

风险回答：

```text
新包已更新但联调未通过，存在生产验证风险。
旧包已被新包替代，历史包默认收起。
建议：查看失败步骤，按 Case 跟进。
```

## 8. Workflow / Skill / MCP 边界

### 8.1 Chat 负责

- 意图识别。
- 项目、媒体、终端、包名、版本的追问和上下文解析。
- 用户权限校验入口。
- 调用包交付 Workflow 或自动联调 Skill。
- 展示状态、结论、证据和下一步。
- 将结果写入会话过程和资产入口。

Chat 不负责：

- 判断上报是否通过。
- 判断媒体后台是否更新。
- 判断联调是否成功。
- 派生可投结论。
- 修改包状态。

### 8.2 PackageDeliveryWorkflow 负责

- 管理 `PackageDeliveryTask`。
- 根据包类型选择流程。
- 调用上报检查 Skill。
- 调用后台更新检测 Skill。
- 调用联调检查 Skill。
- 汇总 Evidence。
- 派生业务结论。
- 处理旧包替代。
- 生成 Case。
- 输出标准化结果给 Chat 和前端组件。

### 8.3 Skill 负责

建议拆分：

- `package_status_query_skill`：只读查询包状态、下载地址、版本。
- `package_report_check_skill`：调用数据上报报告 MCP。
- `package_backend_update_check_skill`：检测媒体后台 / 智投后台版本。
- `package_integration_check_skill`：读取或触发联调检查。
- `package_delivery_execution_skill`：编排交付动作和结果整理。
- `delivery_diagnosis_skill`：定位交付阻塞项。

### 8.4 MCP / 智投接口负责

- 数据上报报告。
- 媒体后台版本。
- 智投后台版本。
- 媒体审核状态。
- 应用共享状态。
- 包下载地址或 APK 地址。
- 联调任务。
- 联调步骤。
- 联调截图。
- 联调日志。
- 联调结果。
- 历史包版本。

## 9. 能力调用编排

### 9.1 查询可交付包

```text
Chat
-> resolve project / permission
-> PackageDeliveryWorkflow.queryDeliverablePackages
-> package_status_query_skill
-> zhitou_package.channel_package_query
-> zhitou_package.download_url_query
-> media_config.review_status
-> debug_automation_get_result / debug.watch_steps
-> derive conclusion
-> render delivery result
```

### 9.2 上报检查

```text
PackageDeliveryWorkflow
-> package_report_check_skill
-> collect.platform_event_report_status 或数据上报报告 MCP
-> parse failed items / passed items
-> write evidence
-> transition status
```

### 9.3 后台更新检测

```text
PackageDeliveryWorkflow
-> package_backend_update_check_skill
-> media_config.review_status / zhitou_package.sync_media_sub_package
-> compare version
-> write backend_version_ref
-> transition waiting_*_backend_update -> integration_checking
```

### 9.4 联调检查

```text
PackageDeliveryWorkflow
-> package_integration_check_skill
-> debug.config_check
-> debug.event_report_check
-> debug.start_task 或读取已有 task
-> debug.watch_steps
-> debug_automation_get_result
-> parse success / failed_step / screenshots / logs
-> write evidence
-> derive conclusion
```

```ts
type PackageDeliveryQueryResponse = {
```

### 10.3 单独触发联调

```http
POST /api/xiaoqiao/package-delivery/tasks/{taskId}/integration-check
```

请求：

```ts
type PackageIntegrationCheckRequest = {
```

## 11. 前端设计

### 11.1 交付结果卡片

卡片必须展示：

- 项目。
- 媒体。
- 终端。
- 包名。
- 版本。
- 下载地址 / APK 地址。
- 上报检查状态。
- 后台更新状态。
- 联调状态。
- 业务结论。
- 证据来源。
- 下一步动作。

状态展示使用用户语言，不直接暴露工程状态。

### 11.2 过程组件

过程组件展示：

- 上报检查。
- 等待提审。
- 等待媒体后台更新。
- 等待智投后台更新。
- 联调检查。
- Case 生成。

每个节点展示：

- 当前状态。
- 来源。
- 最近更新时间。
- 失败原因。
- 证据。

### 11.3 历史包展示

规则：

- 旧包被新包替代后进入历史包分类。
- 历史包默认不展开。
- 用户展开后可查看旧版本、替代时间、替代原因和历史证据。
- 历史包不能展示为当前可交付投放。

### 11.4 操作入口

一期可见操作：

- 刷新状态。
- 查看证据。
- 查看联调日志。
- 查看截图。
- 查看 Case。
- 再次检查。

一期不做：

- 人工改成可投。
- 后台人工放行。
- 强制阻断建监测活动。

## 12. 资产与沉淀

包交付结果是可沉淀资产。

资产类型：

```ts
type PackageDeliveryAsset = {

  asset_type: 'package_delivery_result'
  project_ref: string
  task_id: string
  package_refs: string[]
  business_conclusion: PackageBusinessConclusion
  summary: string
  evidence_refs: string[]
  trace_id?: string
  case_id?: string
  created_at: string

```

写入规则：

- 用户明确保存时写入我的资产。
- 自动化或 Workflow 生产的正式交付结果可以默认写入资产。
- 失败 Case 进入 Case 记录，不伪装成可交付资产。
- 资产展示按用户动态项目权限过滤。

## 14. Prompt 与配置边界

写进代码的内容：

- 状态枚举。
- 状态流转合法性。
- 可投结论派生规则。
- 权限校验。
- 上报检查通过才能触发联调的约束。
- 不能人工直接改可投的约束。

写进运行时配置的内容：

- 媒体范围。
- 包类型映射。
- 分包模板。
- 角色可用操作。
- MCP tool 绑定。
- 失败重试策略。

写进 Tool / MCP 的内容：

- 真实包查询。
- 真实上报报告。
- 后台版本查询。
- 审核状态查询。
- 联调任务和结果。
- 下载地址。

写进知识库的内容：

- 包交付术语解释。
- 媒体后台更新 SOP。
- 常见失败原因解释。
- 处理建议模板。

知识库不能保存：

- 实时包状态。
- 用户权限。
- 下载地址。
- 联调结果。
- 上报报告。
- 可投结论。

## 15. 失败闭环

### 15.1 失败类型

| 类型 | 处理 |
|---|---|
| 项目缺失 | 追问项目 |
| 项目无权限 | 阻断，不回退顶部项目 |
| 包不存在 | 查询包列表并提示筛选 |
| 上报不通过 | 不提示提审或更新，输出失败项和修复建议 |
| 等待外部更新 | 展示等待对象和最近检测时间 |
| 联调配置缺失 | 输出缺失配置，不触发联调 |
| 联调失败 | 生成 Case，展示失败步骤、截图和日志 |
| MCP 不可用 | 多次失败后生成 Case |
| 结果冲突 | 标记需人工处理，保留冲突证据 |
| 资产写入失败 | 保留会话结果和 Trace，不展示为已入资产 |

### 15.2 Case 内容

生成 Case 时必须包含：

- 项目。
- 媒体。
- 终端。
- 包名和版本。
- 当前状态。
- 业务结论。
- 已确认事实。
- 未确认问题。
- 已调用能力。
- Evidence。
- 下一步建议。
- 责任角色。

## 16. 验收场景

P0：

- 顶部 A 项目，用户问 B 项目包能不能投，系统使用 B 项目并校验权限。
- 用户未给项目时，系统追问项目，不直接使用不可靠上下文执行。
- 查询可交付包时，只展示真实工具返回且满足派生条件的包。
- 媒体首次包上报通过后，输出“上报检查通过，等待提审。”
- 媒体更新包上报通过后，输出“上报检查通过，等待媒体后台更新。”
- 官方更新包上报通过后，输出“数据检查通过，等待智投后台更新。”
- 上报不通过时，不提示提审或更新，旧包保持有效。
- 单独触发联调前，必须确认上报检查通过。
- 首次联调失败时，不建议交付并自动生成 Case。
- 新包联调失败时，新包风险待关注，旧包已被新包替代，自动生成 Case。

P1：

- 历史包默认折叠。
- 展示联调截图、日志和失败步骤。
- 包交付结果保存到资产后，按项目权限动态过滤。
- 权限变化后，历史会话和资产中的项目包数据不可见。
- Trace 可跳转连弩平台回放。

P2：

- 后台可配置媒体分包模板。
- 批量检查多个媒体包。
- 包交付自动化任务定时巡检。
- 小闪通知包交付状态变化。
