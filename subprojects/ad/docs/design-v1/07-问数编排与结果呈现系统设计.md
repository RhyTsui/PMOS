# 问数编排与结果呈现系统设计

## 1. 文档目的

本文定义 `report_query` 从“已路由到问数”之后的完整编排和结果呈现设计。

本文不重复定义：

- 战略和需求范围：见 `docs/prd-v2.2/06-数据查询报表与定时报表PRD.md`
- MCP 能力归属：见 `04A-MCP能力发现与问数归属矩阵.md`
- 知识与配置边界：见 `06-问数知识策略与配置治理系统设计.md`

本文重点回答：

- 一个问数请求如何生成 `ReportQueryPlan`。
- 如何处理项目、日期、指标、维度、字典和 alias。
- 如何执行单查询和复合查询。
- 如何做后处理、质量检查和失败闭环。
- 后端返回什么结构给前端。
- 前端如何渲染表格、图表、证据、下一步建议和资产化入口。
- 如何验收不是假功能。

## 2. 设计目标

问数闭环的最低标准：

1. 正确路由。
2. 自动补齐可确定信息。
3. 缺关键字段时追问。
4. 真实调用工具完成执行。
5. 正确解析执行结果。
6. 提供下一步建议。
7. 提供证据来源、记录、沉淀。
8. 系统无力完成时，先继续追问确认；多轮后仍不行再生成 Case，并告知用户等待处理。

本设计把这些标准拆成可执行模块：

- `ReportQueryPlanner`
- `DictionaryResolver`
- `ReportToolExecutor`
- `ReportPostProcessor`
- `ReportAnswerComposer`
- `ReportResultPresenter`
- `FailureCaseCreator`

## 3. 总体链路

```text
用户问题
  -> 意图路由 report_query
  -> 项目上下文编译 ProjectResolution
  -> 受控术语归一化 ControlledGlossaryIndex
  -> MCP 能力发现 ReportCapabilityManifest
  -> 生成 ReportQueryPlan
  -> 字典解析 DictionaryResolver
  -> 构造 MCP 入参
  -> 执行报表 MCP
  -> 解析 ReportQueryResult
  -> 后处理 PostProcessor
  -> 质量检查 QualityCheck
  -> 受控答案 AnswerComposer
  -> 前端结果呈现 ResultPresenter
  -> 保存 / 定时 / 继续分析 / 失败 Case
```

## 4. 核心对象

### 4.1 `ReportQueryPlan`

`ReportQueryPlan` 是问数编排的中心对象。

```ts
type ReportQueryPlan = {
  plan_id: string
  original_question: string
  normalized_question: string
  primary_question_type: 'daily' | 'hour' | 'roi' | 'retention' | 'material'
  project_context: Record<string, unknown>
  sub_queries: ReportSubQuery[]
  required_slots: string[]
  resolved_slots: Record<string, unknown>
  pending_slots: string[]
  merge_rules: string[]
  failed_items: Array<{ sub_query_id: string; reason: string }>
  evidence_refs: string[]
  trace_id?: string
  status:
    | 'planning'
    | 'waiting_for_user'
    | 'executing'
    | 'partial_success'
    | 'success'
    | 'failed'
    | 'case_created'
  updated_at: string
}
```

设计原则：

- 单报表问题也必须生成 Plan，避免“只调了 tool 但无法解释为什么”。
- 复合问题必须拆成子查询，不把不同报表口径强行塞进一个 tool。
- `pending_slots` 只放会影响执行真实性的字段。
- `evidence_refs` 必须指向真实 MCP tool、字典 tool、口径库或 Trace。

### 4.2 `ReportSubQuery`

```ts
type ReportSubQuery = {
  sub_query_id: string
  question_type: ReportQuestionType
  tool_name: string
  server_name: string
  status: 'planned' | 'executing' | 'success' | 'empty' | 'failed' | 'skipped'
  input?: Record<string, unknown>
  row_count?: number
  message?: string
  evidence_refs?: string[]
}
```

子查询用于：

- ROI + 日报复合。
- 日报 + 留存复合。
- 素材 + 消耗复合。
- 总计 + 明细核对。

### 4.3 `ReportQueryResult`

后端给前端的核心数据结果：

```ts
type ReportQueryResult = {
  result_type: 'ReportQueryResult'
  status: 'success' | 'empty' | 'failed' | 'blocked'
  question_type: ReportQuestionType
  tool_name: string
  server_name: string
  input: Record<string, unknown>
  rows: Array<Record<string, unknown>>
  columns: string[]
  metrics: string[]
  dimensions: string[]
  date_range: { start_date: string; end_date: string }
  quality_check: ReportQualityCheck
  selection_trace: ReportToolSelectionTrace
  preflight: ReportQueryPreflight
  resolved_filters: ReportResolvedFiltersSummary
  empty_diagnosis?: ReportEmptyDiagnosis
  query_plan?: ReportQueryPlan
  viz_spec?: VizSpec
  recommended_actions?: string[]
  message: string
}
```

约束：

- `rows` 必须来自真实 MCP 返回或基于真实返回的后处理。
- `columns` 必须从真实结果或后处理结果中派生。
- `message` 不能掩盖失败和空结果。
- `viz_spec` 是展示建议，不是数据事实。

## 5. Planner 设计

### 5.1 输入

Planner 输入：

```ts
type PlannerInput = {
  message: string
  conversation_id: string
  user_context: UserContext
  project_resolution: ProjectResolution
  mcp_servers: McpServerConfig[]
  report_policy: ReportQueryPolicy
  controlled_glossary_index: ControlledGlossaryIndex
}
```

### 5.2 输出

Planner 输出：

```ts
type PlannerOutput = {
  plan: ReportQueryPlan
  selected_tool?: SelectedReportTool
  candidate_tools: CandidateTool[]
  pending_questions?: ClarificationQuestion[]
}
```

### 5.3 规则

Planner 必须按以下顺序处理：

1. 使用 `ControlledGlossaryIndex` 生成 `normalized_question`。
2. 从 `ReportCapabilityManifest` 获取可用报表 tool。
3. 使用 `tool_selection_rules` 给候选 tool 打分。
4. 判断是否为复合查询。
5. 生成 `sub_queries`。
6. 检查项目、日期、报表域、必填字段。
7. 缺关键字段时生成追问，不执行 MCP。

### 5.4 复合查询拆分

复合查询识别信号：

- 同时出现 ROI、留存、消耗、素材等多个报表域。
- 用户明确说“一起看”“对比”“同时看”“再看”。
- 用户要求总计 + 明细。

拆分规则：

- ROI 走 ROI tool。
- 留存走 retention tool。
- 素材走 material tool。
- 消耗、激活、注册、付费等基础指标走 daily tool。
- 小时/实时需求走 hour tool，但不因“今天”误选 hour。

## 6. 字典解析设计

### 6.1 字典解析触发

字典解析只在 alias 命中时触发。

| 类型 | alias 来源 | 字典 tool | 回填字段 |
|---|---|---|---|
| 媒体 | `media_aliases` | `get_dict_zt_all_media` / `get_dict_zt_media` / `get_dict_zt_report_media` | `mediaId` |
| 终端 | `terminal_aliases` | `get_dict_zt_rpt_os_type_v2` | `osTypes` |
| 团队 | `team_aliases` | `get_dict_zt_label_team` / `get_dict_zt_asset_team` | `teamIds` |
| 应用类型 | `app_package_type_aliases` | `get_dict_zt_app_package_type` | `appPackageType` |
| 账户 | `account_aliases` | `get_dict_zt_account` | `accountId` |
| 包体 | `package_aliases` | `get_dict_zt_rpt_package` | `pkgId` |
| 优化师 | `optimizer_aliases` | `get_dict_zt_optimizer` | `optimizerIds` |

### 6.2 设计红线

- 不扫描用户问题里的所有中文词并猜团队名。
- 不把 alias 直接当 id。
- 字典 tool 返回空时，不继续调用报表 tool。
- 字典 tool 缺失时，进入缺能力闭环。
- 字典解析必须进入 `tool_chain` 和 `resolved_filters`。

### 6.3 字典解析失败处理

| 场景 | 处理 |
|---|---|
| 缺 appId | 追问项目或 appId |
| alias 命中但字典 tool 不存在 | 阻断报表调用，提示缺能力，生成可沉淀问题 |
| 字典 tool 调用失败 | 阻断报表调用，显示 tool 错误，保留 Trace |
| 字典返回空 | 追问用户确认名称或直接提供 id |
| 多个候选 | 追问用户选择，不静默取第一个 |

## 7. MCP 入参构造

### 7.1 必填字段

通用必填：

- `appId`
- `startDate`
- `endDate`
- `promotionSource`
- `timeType`

不同 tool 的补充字段：

- ROI：`dataType`
- 留存：`retentionType`
- 小时：`baseTimeType`、`dh` 或小时范围
- 素材：素材相关维度和筛选

### 7.2 默认值策略

允许默认：

- `promotionSource = AD`
- 日粒度 `timeType = DAY`
- 周粒度 `timeType = NATURAL_WEEK`
- 月粒度 `timeType = NATURAL_MONTH`
- 小时粒度 `timeType = HOURLY`
- 小时基础口径 `baseTimeType = EVENT_TIME`

不允许默认：

- 项目。
- 用户明示但无法匹配的媒体、团队、账户、包体、优化师。
- ROI 类型存在明显歧义时。
- 留存类型存在明显歧义时。

### 7.3 字段兼容

入参构造必须读取 tool `input_schema`：

- schema 接受 `appId` 时写 `appId`。
- schema 接受 `projectId` 时写 `projectId`。
- schema 接受 `mediaId` 时写 `mediaId`。
- schema 不接受的字段不能硬塞。

## 8. 后处理设计

### 8.1 后处理范围

P0：

- 表格列提取。
- 数值列识别。
- 空结果诊断。
- 基础图表 `viz_spec`。
- 复合查询分块展示。

P1：

- TopN。
- 排序。
- 环比 / 同比。
- 差异比例。
- 总计与明细核对。
- 派生指标计算。

P2：

- 自动诊断候选。
- 异常波动解释。
- 多轮条件分支。

### 8.2 后处理红线

- 后处理只能基于真实 rows。
- 派生指标必须有公式来源。
- 不能因用户想要“好看图表”而补造缺失数据。
- 多结果合并必须保留子查询来源。

## 9. 质量检查设计

`ReportQualityCheck` 至少包含：

```ts
type ReportQualityCheck = {
  ok: boolean
  empty_table: boolean
  missing_fields: string[]
  date_gaps: string[]
  anomaly_warnings: string[]
  metric_risks: string[]
  issues: string[]
  root_cause?:
    | 'none'
    | 'tool_missing'
    | 'missing_context'
    | 'dictionary_unmatched'
    | 'permission_or_scope'
    | 'no_matching_data'
    | 'response_unparsed'
    | 'tool_failed'
  recommended_next_actions?: string[]
}
```

质量检查输出必须影响 UI：

- `ok=true`：展示结果和下一步建议。
- `empty_table=true`：展示空结果诊断，不展示“已完成分析”。
- `tool_failed`：展示失败原因和重试建议。
- `dictionary_unmatched`：提示用户确认筛选项。
- `permission_or_scope`：提示权限或项目范围问题。

## 10. 答案生成设计

### 10.1 `ReportAnswerComposer`

Composer 只读取结构化对象：

- `ReportQueryResult`
- `ReportQueryPlan`
- `quality_check`
- `resolved_filters`
- `selection_trace`
- `source_refs`

Composer 禁止：

- 自由编造数据。
- 隐藏失败子查询。
- 把空结果说成结果正常。
- 使用知识库内容替代报表返回。

### 10.2 答案结构

成功：

```text
已按以下条件查询：
- 项目
- 时间
- 筛选
- 数据来源

核心结果：
- ...

下一步建议：
- 保存到我的资产
- 生成定时报表
- 查看分媒体 / 分团队 / 分素材
```

空结果：

```text
本次查询没有返回数据。
可能原因：
- 条件过窄
- 字典匹配范围无数据
- 数据延迟
- 权限范围内无数据

建议：
- 放宽日期
- 去掉某个筛选
- 确认项目权限
```

失败：

```text
本次没有完成查询。
失败位置：
- MCP tool
- 输入字段
- 权限 / 授权
- 返回解析

已记录：
- trace_id
- failure_case_id 或 case 候选
```

## 11. 前端呈现设计

### 11.1 结果卡片结构

前端展示应使用“工作台结果块”，而不是营销卡片。

推荐结构：

1. 查询条件摘要。
2. 执行状态。
3. 结果表格 / 图表。
4. 数据来源和更新时间。
5. 质量检查。
6. 字典解析和筛选来源。
7. 下一步建议。
8. 操作入口：保存、转报表、创建定时报表、继续分析、查看 Trace。

### 11.2 表格

表格必须：

- 支持横向滚动。
- 支持列宽稳定。
- 数值按类型格式化。
- 百分比、货币、整数、小数分开处理。
- 空值显示为 `--`，不显示为 0。
- 大结果集显示分页或摘要。

### 11.3 图表

图表只在 `viz_spec` 存在且数据结构满足时展示。

图表失败时：

- 不影响表格展示。
- 显示“图表暂不可用，表格数据如下”。
- 记录 UI 渲染失败事件。

### 11.4 复合查询

复合查询展示：

- 顶部显示 Plan 摘要。
- 每个子查询独立展示状态。
- 成功子查询展示结果。
- 失败子查询展示失败原因。
- 不把不同口径混成一个无来源表格。

### 11.5 下一步建议

下一步建议必须基于状态：

| 状态 | 建议 |
|---|---|
| 成功 | 保存资产、生成定时报表、继续按维度拆分 |
| 空结果 | 放宽条件、确认筛选、查看数据延迟 |
| 字典未匹配 | 确认名称、直接提供 id、查看可选字典 |
| 权限失败 | 切换项目、申请权限、联系管理员 |
| tool 失败 | 重试、查看连接、生成 Case |

## 12. 资产化入口

查询结果默认不入资产。

进入资产的触发：

- 用户点击保存。
- 用户明确说“保存这个结果”。
- 用户基于结果创建定时报表。
- 自动化任务产物。

保存前必须：

- 校验当前用户仍有项目权限。
- 绑定涉及项目。
- 写入查询条件、结果摘要、Evidence、Trace。
- 对跨项目结果按项目权限动态展示。

## 13. API 契约

当前 Chat 内部可先通过 `/api/chat` 返回 metadata 承载结果。后续建议拆独立接口：

```http
POST /api/xiaoqiao/report-query
POST /api/xiaoqiao/report-query/{queryId}/save
POST /api/xiaoqiao/report-query/{queryId}/create-report-draft
POST /api/xiaoqiao/report-query/{queryId}/create-schedule
GET  /api/xiaoqiao/report-query/{queryId}/trace
```

`POST /report-query` 返回：

```ts
type ReportQueryResponse = {
  query_id: string
  conversation_id: string
  status: ReportQueryStatus | 'missing_input' | 'not_configured'
  assistant_message: string
  result?: ReportQueryResult
  plan?: ReportQueryPlan
  missing_fields?: string[]
  clarification_question?: string
  trace_id: string
  failure_case_id?: string
}
```

## 14. Trace 契约

每次问数必须记录：

- 原始问题。
- 归一化问题。
- 用户上下文。
- 项目上下文。
- 受控术语命中。
- Manifest 版本。
- 候选 tool。
- 选择原因。
- 字典 tool 调用。
- 报表 tool 调用。
- MCP 输入摘要。
- MCP 返回摘要。
- 后处理步骤。
- UI 展示契约。
- 失败原因。
- Case id。

## 15. 验收设计

### 15.1 服务层验收

必须通过：

- `test:report-query`
- `test:report-query:mapping`
- P0 tool mismatch / not selected 阻断。

补充：

- 字典 alias 命中后真实调用字典 tool。
- 字典为空时不调用报表 tool。
- 缺 appId 时不调用字典 tool。
- 复合查询生成多个子查询。

### 15.2 UI 验收

必须验证：

- 表格渲染。
- 图表渲染。
- 空结果。
- tool 失败。
- 字典未匹配。
- 复合查询部分成功。
- 下一步建议。
- 保存资产入口。
- 移动端布局。

### 15.3 防假功能验收

必须证明：

- 有真实 MCP tool_chain。
- 有真实 input。
- 有真实返回摘要。
- 有 source refs。
- 有 trace id。
- 没有 MCP 成功时，不展示成功结果。
- 没有用户保存时，不进入资产。
