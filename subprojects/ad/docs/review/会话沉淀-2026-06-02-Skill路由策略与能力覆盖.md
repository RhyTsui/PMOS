# 会话沉淀：Skill 路由策略与能力覆盖

- 日期：2026-06-02
- 范围：Skill 路由选择、安卓归因诊断触发边界、能力选择 trace 字段、能力缺口结果承接
- 状态：已验证，待随本轮归档提交推送

## 问题背景

历史改动中，安卓归因诊断 Skill 可能因为整体意图被识别为 `diagnosis` 而获得路由加分。这样会让泛化诊断问题，例如“为什么昨天 ROI 下降”，有机会误进安卓归因诊断流程。

同时，能力选择 trace 对“数据能力是否覆盖”“展示能力是否覆盖”“为什么不能执行”的表达还不完整，后续排查只能看候选分数和简短原因。问数请求带有编号前缀时，也可能把“1、”这类列表编号混进需求理解。

## 决策

- 不再用 Skill ID 硬编码限制安卓归因诊断触发。
- 将“诊断路由加分必须先命中领域触发词”沉淀为 `selection_policy.requires_trigger_match_for_route_bonus`。
- Skill 编排统一读取契约策略，只有命中领域触发词的 Skill 才能拿到对应路由加分。
- 能力选择 trace 补齐执行决策、阻断原因、数据覆盖、展示覆盖等字段类型，为后续链路观测保留结构化位置。
- 能力不足时生成结构化缺口结果，把已识别条件、已检查能力、缺少能力和下一步动作带回消息结果。
- 需求理解先清理编号前缀，并把实体提示并入过滤条件，避免能力覆盖检查误把筛选实体当成输出维度。

## 已落地

- 安卓归因诊断 Skill manifest 增加 `selection_policy`。
- SkillContract 类型与本地契约归一化保留 `selection_policy`。
- Skill 编排按 `selection_policy.requires_trigger_match_for_route_bonus` 控制 diagnosis/debugging 路由加分。
- 路由 golden 增加“泛诊断不误选安卓归因诊断”断言。
- capability manifest 增加 `executionDecision`、`blockingReason`、`dataCoverage`、`presentationCoverage` 等 trace 字段。
- request understanding 增加编号前缀清洗、实体提示过滤条件合并和输出维度收口。
- chat route 在无原生 semantic result 且能力不可执行时，构造 `capability_gap` 语义结果。
- BusinessSummary 支持承载 `capability_gap`，便于消息结果展示层读取。
- 消息展示层增加能力缺口卡片，运行步骤把能力检查事件改写成更清楚的用户提示。

## 本轮补充：展示降级不阻断数据执行

本轮对剩余风险口径做了收口：数据能力是否可执行，由 capability selection 判断；是否能出图，属于 presentation contract、renderer registry 与 data adapter 的验证项。二者不能混用，否则会把“图表暂不可用”误判成“数据能力无覆盖”。

已落地的边界如下：

- 数据能力已覆盖时，即使趋势图 presentationCoverage 不完整，也保持 `executionDecision=executable_with_presentation_fallback`，不返回 `no_full_coverage`。
- 如果工具返回满足 date + metric 趋势结构的数据，且 renderer 支持 chart contract，仍按趋势图展示。
- 如果 renderer 未注册、semantic result 不满足图表 contract，或 adapter 无法归一化为趋势结构，展示层降级为表格、结构化摘要或 fallback renderer，并提示“展示方式已降级”。
- 展示降级不影响工具执行结果，不让主消息为空，也不吞掉 `business_summary` 等结构化摘要。
- 新增回归覆盖 routing golden、chat presentation regression 与 capability chain regression，确保图表 contract 不满足时不会出现 `no_full_coverage`。

## 后续边界

- 本次只处理 Skill 路由误选和能力选择观测字段，不改安卓归因诊断的实际执行流程。
- 泛诊断问题后续应继续走通用报表、诊断或分析链路，不应被单一领域 Skill 抢占。
