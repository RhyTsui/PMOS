4.2 已实现且符合设计

  1. SemanticResultContract 作为最终业务结果协议已成立。
  2. RuntimeDisplayProtocol 作为过程协议已成立。
  3. route-decision-observation 作为只读观测层已成立。
  4. component-registry 与 fallback 机制已成立。
  5. prompt store 已有版本、fallback、cache、seed 机制。
  6. route runtime golden 已开始覆盖关键路径。

4.3 已实现但偏离设计

  1. ResponseContract 仍是兼容型 envelope，而非严格收口的单协议。
  2. /api/chat 仍将路由、上下文、能力、结果、trace、展示编排塞在一个 handler。
  3. admin control plane 仍是多入口并列，不是单一治理台账。
  4. prompt-store 与 managed-prompt-seeds 仍是“运行时 + 种子 + cache + admin”四层并存。
  5. intent-router、intent-route-engine 等旧路线仍在仓库中保留。

4.4 伪实现 / 半实现 / 只打日志未接主链

  1. intent-route-engine.ts 更像影子链路，而不是主链权威入口。
  2. 部分 admin 页面存在入口，但治理边界尚未收敛。
  3. 部分 metadata / trace 字段只在日志侧可见，未形成统一反哺协议。

4.5 P0 / P1 / P2 风险清单

P0

  • 通用 Chat 仍可能退化为 report query，或者问数被误导成能力缺失。
  • /api/chat 仍是超大 handler，单点修改容易破坏主链。
  • clarification 与 capability blocking 的语义边界尚未完全统一。

P1

  • prompt governance 多源并存，生效不透明。
  • admin control plane 入口过多，配置归属不清。
  • ResponseContract 与 runtime / legacy payload 仍耦合。
  • 旧 route engine 仍保留在仓库内，容易被误用。

P2

  • 总纲文档未完整吸收 P0.6 产物。
  • 后台 IA 仍未完全按 control plane 逻辑重排。
  • workflow / skill / capability 的边界表达还不够统一。

4.8 后台有入口但运行时不生效

  • 部分旧式 route engine / shadow config 入口还在，但主链已经不以它们为权威依赖。
  • 一些 admin tab 更接近展示级入口，而不是运行时真源。

4.9 旧设计仍在运行

  • intent-router.ts
  • intent-route-engine.ts
  • response-contract.ts 的 legacy 容器能力
  • ChatContainer.tsx 对 runtime / message / contract 的兼容承载

4.10 新设计已实现但未写入总纲

  • P0.6 的 tool-first runtime 语义。
  • business_outcome、step_status、tool_execution_status、blocking_requirements 等执行状态字段。
  • route-runtime-golden.ts 及其对应的门禁语义。

4.11 风险分层补充

P0

  • 通用 Chat 是否仍会退化为 Report Query。
  • Query Contract 是否仍前置阻断能力发现。
  • metric / time / dimension 是否仍被默认视为所有问数的必填条件。

P1

  • Capability Discovery 是否晚于参数表单。
  • SemanticResultContract 是否参与路由。
  • Prompt 是否覆盖 RouteDecision。
  • Admin Control Plane 是否存在多套配置真源。

P2

  • UI 是否泄露 Runtime 内部状态。
  • Domain Pack 是否覆盖 Top Intent。
  • workflow / skill / capability 边界是否统一。

4.12 重点评估结论

  1. 通用 Chat 仍有退化为 Report Query 的历史风险，但已经明显收缩。
  2. Query Contract 的前置阻断已经减弱，但未完全收口。
  3. metric / time / dimension 已不再是所有问题的默认死锁条件，但仍需持续验证。
  4. Capability Discovery 已前移到 preflight 语义。
  5. SemanticResultContract 不应参与路由，当前主链也尽量隔离。
  6. UI 仍有兼容性泄露风险。
  7. Prompt 参与的是 evidence/support，不应覆盖权威路由。
  8. Domain Pack 只部分覆盖 Top Intent。
  9. body.intent 不应强制进入 report_query。
  10. currentProject 已结构化进入上下文。
  11. capabilityDecision 已真正进入 selector，但与 report orchestrator 仍需统一。
  12. 右侧展示与主消息展示职责仍有交叉。
  13. Admin Control Plane 仍有多套配置真源。
  14. 后台菜单重复、配置归属混乱的问题仍存在。
  15. 连弩 SDK 上报逻辑本轮未见主语义改动。

4.13 后续路线图建议

  1. 继续 P0.6，但只做封版和收口，不再扩面。
  2. P1-C 路由治理建议暂停，先把 clarification / capability / route boundary 收紧。
  3. Admin Console IA 建议暂停，先重画控制面真源图。
  4. Chat Domain Protocol 先只做文档和 type-only，不要直接改主链。
  5. 可并行做总纲、配置真源地图、drift list、golden 说明。
  6. 不能并行改 `/api/chat`、`request-understanding`、`capability-orchestration`、`report-query-orchestrator`、`response-contract`、`prompt-store` 主链。
  7. 建议先封 P0.6，再更新总纲，再收口控制面，再开 P1-C。

4.14 最终判断

  • 当前 HEAD 已包含 P0.6。
  • P0.6 仍属于 未封版实现。
  • 不建议把当前仓库状态写成“稳定最终架构结论”。
