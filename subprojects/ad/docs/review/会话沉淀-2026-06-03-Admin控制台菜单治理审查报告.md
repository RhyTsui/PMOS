# 会话沉淀：Admin 控制台菜单治理审查报告

- 日期：2026-06-03
- 目标：审查当前 Admin Console（管理中心）菜单结构、配置归属与后台治理设计，输出风险与迁移建议。
- 范围：前端管理中心入口、后端配置真源、核心请求理解与能力执行链路。

## 1. 当前重复与重叠

### 1.1 明确重复入口
- `overview` 页签中的卡片入口与顶部 Tab 存在大量一一映射重复：
  - `service-config`
  - `chat-display`
  - `automation-templates`
  - `prompts`
  - `orchestration`
  - `entity-resolution`
  - `intent-rules`
  - `role-profiles`
  - `workflow`
  - `skills`
  - `feature-switches`
  - `auto-debug-config`
  - `demand-pool`
  - `mcp-config`
- 风险：运维使用时难以判断是否“总览入口”和“分类入口”是不同角色或不同作用域，增加误操作可能性。

### 1.2 语义重叠
- `orchestration`、`workflow`、`skills` 在实际职责上交叉：都涉及能力可执行性/路由策略/工具约束，当前文案并未边界化。
- `prompts` 与 `role-profiles` 也可形成一个更完整的“对话语义层”。

## 3. 需要合并的模块建议

### 3.1 建议一：请求理解域
- 合并 `intent-rules + entity-resolution`
- 说明：均直接参与请求理解/意图判断基础输入，且在运行时链路会先后共同生效。

### 3.2 建议二：能力治理域
- 合并 `orchestration + workflow + skills`
- 说明：均围绕能力发现、能力约束、技能调用闭环；`workflow` 与 `skills` 在用户层文案上重叠明显。

### 3.3 建议三：对话语义域
- 合并 `prompts + role-profiles`
- 说明：两个菜单都影响“怎么理解”和“怎样回复”，属于同一决策层次。

---

## 4. 边界混乱评估（实体解析 / 请求理解 / 路由 / 工作流 / MCP / Prompt / Skill）

- 混淆点 A：`entity-resolution` 与 `intent-rules` 在运行链路上是顺序依赖关系，但菜单中独立平列，不利于定位错误源。
- 混淆点 B：`prompts`、`role-profiles`、`workflow`、`orchestration`、`skills` 的文案与实际职责边界不一致，使用者难以判断是“路由提示词”“能力执行提示词”还是“契约定义”。
- 混淆点 C：`workflow` 与运行态的 `workflow_task` 易误解为同一系统，建议文案上区分“能力执行流程（配置）”和“会话任务运行（链路）”。
- 混淆点 D：`skills`（读写 `/skills`）与 `mcp-config`（`/admin/mcp-servers`）职责耦合但入口分裂，造成治理闭环不完整。

---

## 5. 对 Chat 首页链路影响

受影响链路（核心）：
- `/api/chat`：在路由与能力选择中使用 `loadIntentRouteRulesSync`、`deriveRequestRouteDecision`、`deriveUserRequirement`（来自请求理解链路）
- 实体解析通过 `entity-resolution-config-store` 参与请求理解
- 能力匹配通过 `buildCapabilityManifest`、`selectCapabilityForRequirement` 使用 MCP 工具与能力策略
- 能力展示与策略依赖 `report-query-policy`、`report-capability-overrides`、`report-capability-manifest`
- Prompt 全量路由/回复提示词通过 `getActivePromptContent` 参与运行时
- 观测与路由链路依赖 `trace-config`、`model-service-config`
- `chat-display-config` 更多是展示层，不直接决定理解与执行主干

结论：菜单治理若只做“界面重排”即可，但一旦合并后端职责映射不更新，会造成链路误配和应急定位失效，属于高风险迁移动作。

## 7. 风险点与建议优先级

### 高风险
1. 真源归属不清（`skills`/`skill-contracts` 与 `/admin` 家族分离）导致治理操作不可直接追溯来源。
2. 重复入口未关闭：`overview` 与主 Tab 的重复入口仍在，操作歧义高。
3. 菜单内语义边界不清导致 incident 排查时间拉长。

### 中风险
1. `workflow` 命名与运行态“工作流”语义混淆。
2. `orchestration` 与 `mcp-config` 之间“接入 vs 策略”边界不醒目。

### 低风险
1. `chat-display` 与模型/执行能力配置混淆：目前界面上已相对可辨，但仍建议在文案补充“仅影响呈现”提示。
2. `feature-switches` 聚合点未明确作用域。

---

## 8. 下一步行动（可执行）

1. 先落元模型：确认每个新中心的“真源 owner + 读写 API + 变更影响面”。
2. 先做名称/文案重构，不改后端路由：先修复认知边界（低风险）。
3. 再做“重复入口去重（overview 卡片）”。
4. 最后做菜单归组（分组页签 + 映射迁移），并补充回归检查点清单。
