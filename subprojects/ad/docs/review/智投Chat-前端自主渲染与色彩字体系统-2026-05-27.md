## 3. 前端自主渲染方式

当前设计思想不是“后端返回一段文本，前端随便展示”，也不是“MCP 返回 React 组件”。本文归属 Enterprise AI Chat OS 的 Visual System 与前端自主渲染工程口径；最终业务结果仍必须收口到 Unified Semantic Contract，运行过程收口到 Runtime Display Protocol。边界如下：

1. MCP / Skill / workflow 是业务事实源，负责返回状态、步骤、数据、失败原因、建议动作和来源。
2. Chat Runtime 是薄编排层，负责把事实源转换为 `ResponseContract`、`TimelineEvent` 和 `MessagePart`。
3. 前端是自主渲染层，只按协议和组件契约选择展示形态，不反推业务事实。
4. MCP 可以返回 `ui_component.type` 或业务组件建议，但最终是否渲染为正文、时间线、工具卡、结果卡、表格、图表、缺字段卡或来源区，由 Chat UI Renderer 决定。
5. Data Visualization UX、AI Runtime UI、AI Trust UX 都是 Enterprise AI Chat OS 下的子域，不得替代 Unified Semantic Contract、Runtime Display Protocol 或 Action / Evidence / Source 统一协议。
6. `docs/architecture/visual-system/visual-system-breakdown.md` 只负责 Visual System 拆分治理，不覆盖本文已经确定的字体、字号、颜色和 token 值。

### 3.1 渲染协议优先级

| 优先级 | 输入 | 前端行为 |
| --- | --- | --- |
| 1 | `metadata.response_contract.message_parts` | 优先按 MessagePart 渲染 |
| 2 | `metadata.response_contract.timeline` | 渲染用户可理解的过程与 Tool Card |
| 3 | `process_events` / `tool_calls` / `workflow_result` | 作为旧消息兼容回退 |
| 4 | `content` 自然语言正文 | 只做说明和串联，不作为状态事实源 |

### 3.2 MessagePart 到组件的映射

| MessagePart | 展示形态 | 当前组件或方向 |
| --- | --- | --- |
| `text` | 正文说明 | `MessageSurface` / X Markdown |
| `timeline` | 过程记录 | `ChatContainer` 现有过程展示 |
| `tool_card` | 工具调用卡 | Tool 展示组件，默认折叠技术细节 |
| `result_card` | 结果摘要卡 | `ReportQueryResultCard` 等业务卡 |
| `table` | 数据表 | `DataVizRenderer` / AG Grid legacy theme |
| `chart` | 图表 | `DataVizRenderer`，只消费结构化数据 |
| `missing_fields` | 补充信息卡 | `MissingFieldsCard` |
| `source_refs` | 来源与证据 | 来源条、证据区或结果卡来源段 |
| `action_list` | 下一步建议 | `Actions` / 等价动作区 |
| `collapsible` | 折叠详情 | 工具输入输出、长日志、原始结构预览 |

## 4. 字体系统

旧规范里的 `Inter` 不再作为默认字体栈。当前字体系统优先中文可读性和企业系统稳定性。

### 4.1 字体栈

```css
font-family: 'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei',
  'Noto Sans SC', -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif;
```

等宽文本使用：

```css
font-family: ui-monospace, SFMono-Regular, Menlo, Consolas, 'Liberation Mono', monospace;
```

### 4.2 字号与行高

| token | 字号 | 行高 | 用途 |
| --- | --- | --- | --- |
| `--font-size-display` | `28px` | `36px` | 空态欢迎、核心引导标题 |
| `--font-size-title` | `20px` | `28px` | 页面/面板标题 |
| `--font-size-subtitle` | `16px` | `24px` | 区块标题、关键说明 |
| `--font-size-body` | `14px` | `22px` | 正文、对话说明、表格正文 |
| `--font-size-label` | `12px` | `18px` | 标签、按钮辅助文字 |
| `--font-size-caption` | `12px` | `18px` | meta 信息、弱说明 |
| `--font-size-micro` | `10px` | `16px` | 极弱辅助信息 |
| `--font-size-code` | `12px` | `18px` | 代码、结构化片段 |

### 4.3 字重与字距

| token | 值 | 用途 |
| --- | --- | --- |
| `--font-weight-regular` | `400` | 正文 |
| `--font-weight-medium` | `500` | 标签、选中项、轻强调 |
| `--font-weight-semibold` | `600` | 标题、关键结果 |
| `--font-weight-bold` | `700` | 品牌、登录页强标题 |
| `--letter-spacing-*` | `0` | 默认字距；不得用负字距压缩中文 |

### 5.3 Ant Design token

`AntdProvider.tsx` 负责把主色、字体、文本、背景和边框传给 Ant Design：

- `colorPrimary` 使用 `ZHITOU_CHAT_COLORS.primary`
- `fontFamily` 使用当前中文优先字体栈
- 亮色主线：`colorBgLayout #F8FAFC`、`colorText #10233F`、`colorTextSecondary #6B7C93`
- 当前产品主线固定亮色；深色 token 保留给登录页、浏览器资源或后续模式，但不得自行扩展成一套新视觉体系

## 6. 会话工作台背景与视觉方向

5 月 26 日后，会话主区域、空态区域、底部输入区统一在同一背景容器中处理，不再出现顶部、正文、底部割裂的白色块。

当前方向：

1. 工作台背景使用浅灰蓝基底和柔和径向光，不做大面积强蓝色块。
2. 输入区、空态推荐、右侧面板要像同一工作台表面，不用强分割线制造后台感。
3. 主色只给“可以推进任务”的交互，不用作正文色、大面积装饰背景或无意义高亮。
4. 登录页可使用更强的深色品牌氛围，但不反向污染会话工作台的亮色主线。

## 7. 硬编码治理

1. 新增或重写智投 Chat 用户可见组件时，禁止直接写入与本规范同义的十六进制、rgb、rgba、hsl 色值；必须引用 `ZHITOU_CHAT_COLORS`、CSS 变量或 Ant Design 主题 token。
2. 允许局部硬编码的例外只包括：第三方图表库入参、不可控内联 SVG 资源、品牌图片资源、登录页独立氛围、一次性静态验收 HTML。例外必须在同文件附近写明原因。
3. 触达历史硬编码区域时，不要求全量重构，但新增色值必须收口，不得继续扩大分散定义。
4. 不允许为同一语义新增近似色，例如 `#2f76ff`、`#2e74fe`、`rgba(46,117,254,.12)`。需要新色阶时先更新 `zhitou-chat-colors.ts` 和本文。
5. 新色阶按语义命名，不按视觉形容命名。推荐：`primarySoftBg`、`textMuted`、`borderFaint`；不推荐：`blue1`、`lightBlue`、`grayNew`。

## 8. 新增或调整色阶准入

新增 token 前必须满足：

1. 现有 token 无法表达该状态或层级。
2. 新色值有明确使用语义、使用边界和不可使用场景。
3. 已检查桌面端与移动端可读性，不造成正文、按钮、提示、边框之间层级混乱。
4. 不会把会话工作台带回单一蓝色、单一紫色或装饰性色块过重的方向。

新增 token 后必须同步更新：

- `frontend/src/src/lib/zhitou-chat-colors.ts`
- `frontend/src/src/app/globals.css` 中对应 CSS 变量，若需要页面级使用
- `frontend/src/src/components/AntdProvider.tsx`，若需要同步 Ant Design 组件
- 本文档
- 可视验收截图或记录

## 9. Review 口径

交付前必须检查：

1. 前端是否按 Result / Timeline / MessagePart 消费，不从自然语言正文反推业务状态。
2. 新增文案是否是用户语言，没有工程黑话、内部接口名、schema、mock、乱码。
3. 字体是否使用当前中文优先字体栈，字号、行高、字重是否来自 token。
4. 新增色彩是否引用 token 或 CSS 变量，没有分散硬编码同义色。
5. 主色是否只用于任务推进、焦点、可执行建议和关键交互。
6. 结果卡、表格、图表是否来自结构化数据，空结果和失败态是否展示原因和下一步。
7. 桌面端和移动端是否都能读清文本，按钮和卡片内文字不重叠、不溢出。

任一项不满足，结论只能是 `partial` 或 `unsolved`。

## 10. 迁移说明

| 旧口径 | 新口径 |
| --- | --- |
| `Inter` 作为默认 UI 字体 | 中文优先字体栈作为默认 UI 字体 |
| “冷静蓝 + 青绿辅助” | `#2E75FE` 主色 + 成功/警示/危险/信息语义色 |
| 5 月 24 日局部主色规范 | 被本文吸收为完整色彩系统 |
| 页面按组件散落写色值 | 从 `ZHITOU_CHAT_COLORS`、CSS 变量、Ant Design token 取值 |
| 后端或 MCP 决定 UI 细节 | 前端按 MessagePart 自主选择渲染形态 |
| 自然语言正文承担结果状态 | `ResponseContract.status` 是结果状态入口 |

## 11. 执行清单

后续触达用户可见 UI 时，按以下顺序执行：

1. 先确认当前消息或结果是否已有 `response_contract.message_parts`；有则优先按协议渲染。
2. 若只有旧字段，允许从 `process_events`、`tool_calls`、`workflow_result` 回退，但不得从正文猜测状态。
3. 新增色值先查 `ZHITOU_CHAT_COLORS` 和 CSS 变量；没有合适 token 时先补 token 和本文，再写组件。
4. 新增字体、字号、行高、字重先查 `globals.css` token；不得恢复 `Inter` 首选字体或负字距。
5. Ant Design 组件优先继承 `AntdProvider.tsx` token，不在组件内覆盖同义色。
6. 会话背景、输入区、右侧面板、空态推荐必须保持同一工作台表面感，不新增明显白底分割或大面积主色装饰。
7. 登录页可保留独立深色品牌氛围，但不得作为会话工作台色彩主线。
8. 交付记录必须写明截图或浏览器验收结果；涉及色彩和布局时覆盖桌面端与移动端。
