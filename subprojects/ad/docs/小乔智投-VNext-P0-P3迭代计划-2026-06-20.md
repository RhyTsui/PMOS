# 小乔智投 VNext P0-P3 迭代计划

- 日期：2026-06-20
- 来源：`docs/sources/inbox/小乔智投AI服务平台白皮书_VNext_内部查看版.pdf`
- 当前架构真源：`docs/architecture/ENTERPRISE_AI_CHAT_OS_SPEC.md`
- 评审记录：`docs/review/xiaoqiao-vnext-p0-p3-review-docket-2026-06-20.md`
- 实施原则：不推翻 Enterprise AI Chat OS，不新增平行 OS / Protocol / Schema / Contract。

## 1. 产品定位升级

新版定位从“AI 投放服务台与任务运行工作台”升级为“面向游戏发行体系的 AI 服务平台”。这次升级不是把 Chat 改成另一个后台系统，而是在现有 `Planner-first, tool-grounded, contract-guarded` 主链路上，将能力收敛为五大中心：

| 能力中心 | 产品含义 | 架构承接 |
|---|---|---|
| Conversation OS | 统一服务入口、服务分诊、任务承接、证据披露、下一步动作 | Request Understanding、Task Planner、Capability Discovery、Answer Composer、Frontend Presentation |
| Data Intelligence | 查数、复合指标拼表、报表模板、定时报表、结果保存 | Metric Catalog、Report Catalog、Tool/MCP、Evidence Ledger、ResponseContract |
| Intelligence Center | 行业情报、竞品/广告情报、创意表现分析、策略建议 | Public Web、Knowledge、Evidence Policy、SourceRef、Risk Disclaimer |
| Delivery & Integration | 取包、包状态、联调、上报检查、媒体配置检查 | Workflow、MCP Tool Contract、Execution Policy、Trace |
| AI Service Runtime | 自动任务、巡检、诊断、运行记录、失败重试、资产沉淀 | Automation Task、Operation Safety Policy、Task Artifact、Admin Control Plane |

五大中心只作为 `ServiceCatalog`、`CapabilityManifest`、Admin 治理和前端信息架构分类。任何真实执行仍必须经过语义理解、能力发现、工具契约、执行门禁、证据账本和结果安全检查。

## 2. 当前实现边界

| 平面 | 已具备基础 | 主要阻断 |
|---|---|---|
| 运行面 | `/api/chat` pipeline、问数、多工具拼表、公开联网、包查询、诊断、Evidence Ledger、Guardrail 雏形 | 真实登录态 E2E、MCP 入参与 Evidence 一致性、内存增长、fallback 假成功风险 |
| 控制面 | Prompt、MCP、路由、能力、自动任务等 Admin 基础 | Capability / Tool Contract / Evidence Policy / Safety Policy / Feature flags 治理入口不足 |
| 展示面 | 会话工作台、资料与结果、自动任务、右侧运行过程 | 需要持续保持 AI 会话工作台形态，避免退回传统后台 |
| 观测面 | Trace、planner shadow、二轮验收记录 | Evidence 需按 case 和 stage 形成跨链路证据链 |
| 配置面 | Prompt、runtime、MCP、report capability、glossary 配置 | 指标、报表域、字段解释、权限必须来自受治理目录，不能散落在 Chat Core |

## 3. P0：平台定位收口与可信主链路

目标：让 VNext 定位进入现有架构真源，并优先保证“统一服务入口 + 可信数据入口”。

### 3.1 架构和契约

- 将五大能力中心写入 Enterprise AI Chat OS，作为 capability/service taxonomy。
- 冻结 `ServiceCatalog + CapabilityManifest` 最小扩展：`center`、`serviceLine`、`automationLevel`、`riskLevel`、`owner`、`toolContractRefs`、`evidenceNeed`、`outputSurface`、`approvalPolicy`。
- 明确治理字段不能直接授权执行；真实执行仍由 semantic frame、route policy、capability contract、execution policy 和 ContractSafety 共同决定。
- Metric / Report domain 进入 Metric Catalog / Report Catalog，禁止在通用 stage 内硬编码指标域、媒体名或客户样例。

### 3.2 可信主链路

- 刷新登录态后重跑 MIG-050~068，校验 intent、slot、tool、MCP 入参、Evidence、SourceRef、ToolCallTrace、最终回答和 UI 展示。
- 禁止日报 fallback 冒充留存、复合查询或真实报表成功。
- Evidence Ledger 至少支持 case、conversation、stage 维度；事实、推断、未验证内容必须可区分。
- Output Guardrail 需要可阻断或降级最终响应，不能只写 metadata。
- 失败说成功、无证据业务断言、raw params 泄露、shadow 伪装执行必须阻断。

### 3.3 产品形态

- 首屏维持 AI 会话工作台。
- “资料与结果”“自动任务”“处理进展”作为用户语言入口。
- 资产、自动任务和运行过程是任务承接面，不是传统后台看板。
- 用户页面不得出现工程边界、契约字段、内部接口名或联调状态说明。

## 4. P1：五大能力中心 MVP 产品化

目标：把已有链路产品化为可被用户理解、可被运营治理、可被 QA 验收的服务中心。

| 中心 | P1 范围 | 不做 |
|---|---|---|
| Conversation OS | 服务分诊、任务承接、澄清确认、CaseFrame、证据披露、下一步动作、右侧运行过程一致契约 | 不让前端自行解释工具状态 |
| Data Intelligence | 查数、复合指标拼表、报表模板、定时报表、结果保存 | 不在 stage 内写死指标或报表域 |
| Delivery & Integration | 取包、包状态、联调、上报检查、媒体配置检查收敛为交付 SOP Workflow | Chat 不生成“可投放”假结论 |
| AI Service Runtime | 自动任务中心扩展为 Task Center 基座，支持巡检、诊断、定时报表、交付任务状态和运行记录 | 不让自动任务绕过审批和风险等级 |
| Admin Control Plane | Capability、Tool Contract、Evidence Policy、Safety Policy、Planner metrics、Trace sampling、Feature flags 可视化治理 | 不把 Admin 做成业务用户首页 |

## 5. P2：决策智能与主动服务

目标：让智能建议进入有限 MVP，但只作为证据辅助，不替代内部数据和人工决策。

- Intelligence Center 提供行业情报、竞品/广告情报、创意表现分析、策略建议。
- Forecast / Strategy Advisor 以 shadow 模式上线，必须展示输入数据、模型版本、置信区间和不可用原因。
- 主动巡检覆盖 ROI 异常、回传延迟、创意衰退、包状态异常、调度/入库异常。
- 系统可自动生成诊断任务或 Case。
- 自动化开放到 L3：系统可生成配置、工单和操作方案，但必须人工确认。
- 预算、出价、暂停广告、回传规则变更不得自动执行。

## 6. P3：受控自动化运行系统

目标：在低风险、可回滚、长期评测稳定的场景开放 L4/L5，形成组织级运营闭环。

- L4/L5 仅限低风险、可回滚、已有长期评测证据的动作。
- 高风险动作始终需要审批、审计和回滚方案。
- 形成跨媒体经营中枢：统一项目、媒体、素材、预算、数据、交付、自动任务视图。
- 前台仍以会话驱动任务，不退回传统后台。
- Capability / Workflow / Skill 具备版本、owner、健康度、评测集、上线记录、失败率、回滚策略。
- AI 服务渗透率、自动化覆盖率、人效提升率、任务成功率、证据完整率、风险动作拦截率进入治理看板。

## 7. 多角色评审 Gate

| 角色 | P0 Gate | P1 Gate | P2/P3 Gate |
|---|---|---|---|
| 产品/业务 | 统一服务入口和可信数据入口可用 | 五大中心有清晰用户任务和下一步动作 | 不提前承诺全自动投放 |
| 架构 | 五大中心只作为分类，不新增平行体系 | 契约字段进入 catalog/manifest/admin | L4/L5 不绕过 Execution Policy |
| 数据/数仓 | 指标口径、报表域、字段解释、数据权限来自受治理目录 | 报表模板和保存结果可追溯 | 预测输入和模型版本可解释 |
| MCP/旧智投 | Tool Contract、错误码、权限失败、样本冻结 | Workflow 状态和回滚能力稳定 | 自动动作可审计、可回滚 |
| 前端体验 | 会话工作台、Ant Design X 语义组件、UISchema/golden、移动端决策流 | 任务承接、证据披露、资料保存顺畅 | 经营视图仍能回到会话处理 |
| 风险合规 | L3+ 动作确认，L4/L5 审批/审计/回滚 | 风险等级贯穿任务和操作 | 高风险动作不自动执行 |
| QA/观测 | `/api/chat`、SSE、页面回放、Trace、Evidence、乱码、非硬编码补测通过 | 端到端服务中心验收通过 | 评测集、失败率、回滚演练通过 |

## 8. 验收计划

### 8.1 静态验收

- `npm.cmd run ts-check`
- `npm.cmd run validate:ad-ui`
- `git diff --check`
- 乱码扫描
- Prompt 变量扫描
- 非硬编码扫描

### 8.2 真实链路验收

- 刷新登录态后跑 MIG-050~068。
- 查数、复合拼表、取包、联调、诊断、定时报表、资料引用、自动任务创建各至少 1 条端到端用例。
- 覆盖无权限项目、工具失败、空数据、低相关公开来源、模型失败、内存护栏、取消/重试、移动端展示。

### 8.3 阶段评审输出

每个 P 阶段结束必须输出 review docket，至少包含：

- 产品结论
- 架构结论
- 数据/数仓结论
- MCP/旧智投结论
- 前端体验结论
- 风险合规结论
- QA/观测结论
- 未通过项和下一阶段准入判断
