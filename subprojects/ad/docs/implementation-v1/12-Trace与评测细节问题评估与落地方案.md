# Trace 与评测细节问题评估与落地方案

## 1. 文档定位

本文承接 `docs/design-v1/14-连弩Trace评测接入系统设计.md`，明确小乔与连弩之间的职责边界。

用户已明确：Trace 与评测主要接连弩 SDK，发送 trace、记录证据规则等到连弩测试平台，小乔后台不做评测平台。

## 2. 职责边界

小乔负责：

- 生成业务执行 Trace。
- 记录路由、项目解析、权限、能力发现、预检、工具调用、结果解析、错误分类。
- 按连弩 SDK 标准发送。
- 本地记录发送状态和失败摘要。

连弩负责：

- 完整回放。
- 评测用例管理。
- 路由误判样本进入规则候选。
- 需求域评测拆分。
- 闭环成功、部分成功、失败闭环成功的评测判定。
- 证据规则和评测报告。

## 3. 字段标准

每次路由必须记录哪些字段，以连弩提供的标准对接文档为准。小乔不得自行定义一套评测口径替代连弩。

小乔侧至少要保证能提供：

- trace_id。
- conversation_id。
- message_id。
- user_id / role_id。
- route decision。
- project resolution。
- permission result。
- capability discovery / preflight。
- tool calls。
- result parse status。
- evidence refs。
- case refs。
- completion status。

## 4. 工具错误字段

用户已确认错误字段：

```json
{
  "tool_error_raw": "原始错误，内部可见",
  "tool_error_safe": "脱敏错误，前端/用户可见",
  "tool_error_type": "权限错误 / 参数错误 / 网络错误 / 服务错误 / 数据为空 / 超时",
  "tool_error_stage": "鉴权 / 参数构造 / 调用 / 解析 / 展示"
}
```

展示规则：

- 前台用户只展示 `tool_error_safe`。
- 研发、测试、连弩回放可看 `tool_error_raw`。
- 所有错误必须有 type 和 stage，方便定位。

## 5. 权限变化与回放

当前版本不处理历史回放随权限变化动态收敛的问题。连弩评测回放仅作为研发与测试环境的内部调试资产，不作为面向普通业务用户的可见内容。

因此：

- 普通用户前台不展示完整 Trace 回放。
- 权限变化后的会话和资产前台按项目权限过滤。
- 连弩内部回放保留完整执行上下文，用于研发测试复盘。

## 6. 不由小乔实现的内容

以下由连弩负责，小乔不做：

- 路由误判样本进入规则候选。
- 评测用例按路由、项目、权限、包、报表、异常、知识库拆分。
- 一次闭环成功、部分成功、失败闭环成功的评测判定。
- 评测报告和评分。

小乔只发送可被评测的事实链路。

## 7. 验收规则

- 每次业务请求有 trace_id。
- 工具错误同时记录 raw、safe、type、stage。
- 前台不展示原始错误。
- Trace 发送失败不阻断主回答，但要记录发送失败状态。
- 小乔不内建连弩评测平台能力。
- 闭环成功等评测结论不由小乔自行判定。
