# 问数 P0 实施清单 V2

> Historical archive / 非当前实施真源。
>
> 本文是早期问数 P0 清单的二次提炼，保留用于历史追溯，不再作为当前问数实施、提交范围或验收门禁的权威依据。当前问数链路必须以 `docs/architecture/report-domain/report-domain-protocol.md`、`docs/architecture/capability-orchestration/*`、`docs/architecture/runtime/*`、`docs/architecture/semantic-contract/*` 以及 `docs/architecture/ENTERPRISE_AI_CHAT_OS_SPEC.md` 为准。
>
> 文中的“日报 / 小时报表 / ROI / 留存 / 素材”等类型清单只是历史覆盖视角，不得被用作 Chat Core 硬编码分支。当前实现应通过 Capability Manifest、Tool Contract / Schema Adapter、Resolver Chain、MCP preflight、business error normalization 和 ResponseContract 自然覆盖工具能力。

> 本文是对 `docs/prd-v2.2/`、`docs/design-v1/`、`docs/implementation-v1/` 中“问数”相关内容的二次提炼版本。  
> 版本递增：在既有第一批最低闭环基础上，继续往后追加为 **V2**，聚焦“可发布的真实问数闭环”。

## 1. 这次提炼的范围

本次只保留与“问数”强相关的内容，包含：

- 自由对话进入真实问数执行的路由与项目解析
- 问数能力发现、MCP 绑定、slot / schema / 字典解析
- 问数结果展示、保存、转报表、转模板、定时报表入口
- Trace / Evidence / 连弩评测回放
- P0 验收门禁、失败分类、测试集映射

不纳入本次主清单的内容：

- 包交付、联调、异常排查、需求沟通、指标解释等非问数主线
- 市场、预测、自动投放等二期及以后能力

## 2. 来源文档中提炼出的问数主结论

### 2.1 PRD 层结论

来自 `docs/prd-v2.2/06-数据查询报表与定时报表PRD.md`、`15-工程实施清单.md`、`16-需求覆盖矩阵与待澄清事项.md` 的核心结论是：

1. **数据查询是一期 P0 主闭环**，不是“以后再补”的附属功能。
2. 问数要走 **真实 MCP / 智投接口**，不能由 Prompt 伪造数据。
3. 查询结果默认 **不入资产**，用户主动保存后才形成资产。
4. 查询结果必须能继续承接到 **报表、模板、定时报表、诊断候选**。
5. 问数测试集的作用是反推真实产品需求，但它必须落到 **路由、slot、字典、tool、解析、后处理、UI、Trace**，而不是直接变成生产路由。

### 2.2 设计层结论

来自 `docs/design-v1/04-数据查询与报表系统设计.md`、`04A-MCP能力发现与问数归属矩阵.md`、`05-问数系统性问题决策台账.md`、`06-问数知识策略与配置治理系统设计.md`、`07-问数编排与结果呈现系统设计.md`、`07A-问数闭环与测试集验收细化设计.md` 的核心结论是：

1. `report_query` 已经有真实执行基础，但 **能力发现、项目解析、slot 补齐、字典调用、结果解释、UI 契约、Trace 回放** 还没有完全闭环。
2. 生产路由必须先生成 **`ReportCapabilityManifest`**，再做能力发现；不能直接拿 `mcp-servers.json` 或测试集映射代替生产事实。
3. 问数意图要细分到报表域：
   - 日报 / 周报 / 月报
   - 小时报表
   - ROI / 留存 / 素材
   - 字典查询
   - 诊断候选
4. 字典能力必须真实调用，不能在代码里手写媒体、终端、团队、应用类型等 ID。
5. 路由前只允许轻量术语归一化，**不做重型 RAG**；知识库只负责术语、口径、SOP、案例，不可覆盖真实执行事实。
6. 结果解释必须基于结构化结果、Evidence、质量检查与模板约束生成，不能编造数据。

### 2.3 实施层结论

来自 `docs/implementation-v1/02-第一批最低闭环实施清单.md`、`15-第一批代码实施任务拆解与验收门禁.md`、`17-第一批代码落地执行计划与文件边界.md`、`18-第一批验收矩阵与自测门禁.md`、`19-第一批代码实施任务看板.md` 的核心结论是：

1. 第一批已经把最小闭环拆成：
   - 路由主链路收敛
   - 项目权限执行底座
   - 全局能力发现最小版
   - 问数 MCP 真实执行
   - 问数 UI 闭环
   - Trace 基础发送
   - 第一批验收集
2. 当前最大风险不是“没有 MCP”，而是：
   - 生产能力事实来源不稳定
   - 项目解析仍可能回退到顶部项目
   - Testcase 映射容易被误用为生产事实
   - Trace 字段与连弩 SDK 尚未最终冻结
   - UI / Evidence / Trace 的边界还未彻底闭合

## 3. 问数 P0 实施清单 V2

### P0-1 路由与项目上下文收敛

**目标**：保证自由对话能稳定进入真实问数链路，并且项目不再静默回退到顶部项目。

**必须完成**

- 统一 `RouteDecision`、`ProjectResolution`、`CapabilityPreflight`
- 问数意图细分到报表域
- 项目解析使用 `effective_project_refs`
- 明确多项目冲突、无权限、缺项目、补项目的追问和阻断规则
- 路由结果进入 Trace

**验收要点**

- 用户说“昨天这个项目 ROI 怎么样”，能进入 ROI 报表域
- 用户说“这个项目”时，先基于上下文解析，再决定是否追问
- 无权限项目不能静默展示

### P0-2 能力发现最小版本

**目标**：让生产路由以真实能力事实为准，而不是以关键字或测试集映射为准。

**必须完成**

- 从运行态 MCP / Tool schema 生成 `ReportCapabilityManifest`
- Manifest 支持版本、生成时间、tool 名称、输入输出 schema、错误码、权限字段
- 路由、slot、预检、Trace 都引用 Manifest 版本
- 支持后台刷新、配置变更后重建能力事实

**验收要点**

- 当前可用报表 tool 能被列出
- 某条问数用例命中的能力可被审计
- 不允许把测试集映射当成生产事实来源

### P0-3 问数 MCP 执行链路

**目标**：把问数从自然语言转换为真实可执行的结构化请求，并稳定拿到真实结果。

**链路**

`用户输入 -> 术语归一化 -> 问数类型 -> 项目解析 -> slot 补齐 -> 字典调用 -> tool 选择 -> schema adapter -> MCP 调用 -> 结果解析 -> 后处理 -> UI 契约`

**必须覆盖**

- 日报 / 周报 / 月报
- 小时报表
- ROI / 累计 ROI / 区间 ROI
- 留存
- 素材
- 字典查询
- 诊断候选

**必须补齐**

- `timeType` 映射
- `promotionSource` 映射
- `subGroup` 映射
- `dataType` / `retentionType` 追问
- 排序、TopN、对比、环比、同期、总计核对
- 失败分类：`route_error`、`slot_error`、`dictionary_error`、`tool_selection_error`、`mcp_call_error`、`result_parse_error`、`postprocess_error`、`ui_contract_error`、`permission_error`、`data_empty_or_unavailable`

**验收要点**

- P0 问数用例至少每类有一条可执行样本
- 字典失败时不继续调用报表 tool
- 工具真实失败时状态不能伪装成 success

### P0-4 问数 UI 闭环

**目标**：让用户看到的是“可理解、可继续操作”的结果，而不是纯文本或假展示。

**至少支持**

- 成功结果
- 空结果
- 失败结果
- 部分成功

**结果卡必须包含**

- 最终查询项目
- 时间范围
- 筛选条件
- 数据来源
- 工具调用摘要
- 下一步建议

**必须保留的动作**

- 保存到我的资产
- 转报表
- 转模板
- 创建定时报表入口

**验收要点**

- 成功结果不是纯文本
- 空结果与工具失败要区分
- 下一步建议必须随结果状态变化

### P0-5 Trace 基础发送与回放

**目标**：把问数链路的真实执行过程沉淀成可回放、可评测、可追踪的结构化 Trace。

**最小字段**

- `trace_id`
- `conversation_id`
- `message_id`
- `user_id`
- `role_id`
- `route_context`
- `project_context`
- `capability_context`
- `execution_context`
- `result_context`
- `completion_status`

**必须记录**

- 路由候选与最终意图
- 项目冲突与最终项目
- slot 补齐过程
- 字典调用结果
- tool 选择与真实调用
- 结果解析与后处理
- Evidence refs、case refs

**验收要点**

- 每次真实问数都有 `trace_id`
- 工具未真实调用时，Trace 不能标记 completed
- Trace 发送失败不影响用户回答，但要可重试、可告警

### P0-6 问数测试集与发布门禁

**目标**：把问数测试集从“验证素材”变成“发布门禁”。

**必须完成**

- 测试集映射只用于测试、评测、诊断和门禁
- 生产路由不依赖测试集映射
- P0 tool mismatch / not selected 直接阻断发布
- P0 用例必须覆盖渲染、证据、Trace

**验收要点**

- P0 问数测试集可回放到路由、项目、slot、字典、tool、解析、后处理、UI、Trace
- 每条失败样本都能归类到责任层
- 不能只验最终答案

## 4. 问数相关的版本化实施顺序

建议按以下顺序推进本次 V2：

1. **先定事实来源**
   - Manifest
   - 项目解析
   - 权限校验

2. **再打通真实执行**
   - slot
   - 字典
   - 报表 tool
   - 结果解析
   - 后处理

3. **同步补齐 UI / Trace**
   - 结果卡
   - Evidence
   - Trace
   - 回放

4. **最后固化门禁**
   - 测试集映射
   - P0 验收矩阵
   - 发布阻断

---

## 5. V2 版本结论

如果把第一批理解为“问数最低闭环”，那么本 V2 的定位就是：

- 从“能跑”升级到“**真事实、真执行、真展示、真回放**”
- 从“测试集可用”升级到“**生产事实可审计**”
- 从“结果可见”升级到“**结果可继续操作**”

换句话说，V2 不再是再造一个问数能力，而是把已有问数能力补成一个可发布、可验收、可追溯的 P0 闭环。
