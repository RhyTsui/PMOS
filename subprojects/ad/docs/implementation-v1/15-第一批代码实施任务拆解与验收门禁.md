# 第一批代码实施任务拆解与验收门禁

## 1. 文档定位

本文承接：

- `02-第一批最低闭环实施清单.md`
- `14-AgentRuntimeContract与总控运行链路实施方案.md`

本文目标是把第一批“自由对话到真实问数执行最低闭环”拆成代码阶段可排期、可验收、可阻断的实施任务包。

本文不扩展包交付、定时报表、资产落库、个人知识库 Key、异常排查 Workflow。那些模块进入第二批或第三批。

## 2. 第一批交付目标

第一批只解决一个主链路：

```text
用户自然语言问数
  -> 运行时总控
  -> 项目和权限解析
  -> 能力发现和预检
  -> slot 和字典解析
  -> 真实调用问数 MCP
  -> 解析结果
  -> 前端四态展示
  -> Trace 记录
```

闭环最低标准：

1. 正确路由到问数域。
2. 正确处理顶部项目和用户明示项目冲突。
3. 真实发现 MCP 能力。
4. 能力预检后再追问或执行。
5. 真实调用字典和报表 MCP。
6. 正确解析成功、空结果、权限失败、schema mismatch。
7. 前端不伪造“已查询”。
8. Trace 可回放关键链路。

## 3. 任务包总览

| 任务包 | 名称 | 目标 | 阻断条件 |
|---|---|---|---|
| C1 | Runtime 类型与主入口 | 定义运行时输入输出和主入口 | 类型未冻结不得进入链路改造 |
| C2 | MiddlewarePipeline 最小版 | 固定项目、权限、上下文、能力预检顺序 | 项目权限未接入不得调用 MCP |
| C3 | ProjectResolution 与权限底座 | 明示项目优先，生成 effective_project_refs | 无权限仍请求工具则阻断 |
| C4 | CapabilityRegistry 最小版 | 发现报表和字典 MCP 能力 | MCP 已披露但未命中必须可解释 |
| C5 | 问数 MCP 执行链路 | slot、字典、报表 tool、schema adapter、parser | 字典失败不得调用报表 tool |
| C6 | ToolCallEnvelope 与错误分类 | 统一工具调用状态和错误字段 | 前端状态不得脱离 envelope |
| C7 | ResponseContract、MessagePart 与 UI 四态 | 成功、空结果、失败、部分成功、Timeline/Card 展示协议 | 仅自然语言回复不得通过 |
| C8 | Trace 与验收门禁 | 记录路由、项目、能力、调用、解析 | 无 trace_id 不得通过验收 |
| C9 | 前端页面保护约束 | 保持现有聊天页面布局和渲染体系稳定 | 不得重构页面布局、路由和全局状态 |

## 4. C1 Runtime 类型与主入口

### 4.1 实施目标

新增或收敛运行时主入口，形成统一 `AgentRuntime` 调用。

现有 `routing.py` 只能作为候选 intent 生成器，不再作为最终执行决策。

### 4.2 必须定义的类型

```ts
type AgentRuntimeInput = {
  conversation_id: string
  message_id: string
  user_id: string
  role_id: string
  raw_text: string
  ui_selected_project_ref?: string
  attachments?: RuntimeAttachment[]
  client_context?: RuntimeClientContext
}

type AgentRuntimeOutput = {
  runtime_id: string
  trace_id: string
  route_status: RuntimeRouteStatus
  task_plan: TaskPlan
  project_resolution: ProjectResolution
  permission_result: PermissionCheckResult
  capability_preflight: CapabilityPreflightResult
  execution_results: RuntimeExecutionResult[]
  response_contract: ResponseContract
  persistence_results: RuntimePersistenceResult[]
}
```

### 4.3 改造要求

- `service.py` 保留会话、消息、任务创建能力。
- 新增 runtime 执行结果挂到消息或任务结果上。
- 原有 `intent_type` 继续保留兼容，但不能作为唯一事实。
- 失败状态必须结构化返回，不得只返回自然语言。

### 4.4 验收

- 每次业务消息都有 `runtime_id` 和 `trace_id`。
- Runtime 输出包含 TaskPlan、ProjectResolution、CapabilityPreflight。
- 非业务普通问答可返回 `general_answer`，但不能访问内部项目数据。

## 5. C2 MiddlewarePipeline 最小版

### 5.1 第一批固定顺序

```text
InputNormalize
  -> ControlledGlossaryNormalize
  -> ProjectResolution
  -> PermissionCheck
  -> ContextMerge
  -> TaskPlanBuild
  -> CapabilityPreflight
  -> RiskGate
  -> TraceStart
```

### 5.2 第一批最小范围

必须实现：

- 输入清洗。
- 项目/APPID/项目别名解析。
- 顶部项目与明示项目冲突处理。
- 项目权限校验。
- 问数 TaskPlan 生成。
- 问数 CapabilityPreflight。
- Trace 初始化。

暂不实现：

- 包交付 Workflow 中间件。
- 异常排查 Workflow 中间件。
- 复杂上下文压缩。
- 个人知识库 Key 同步。

### 5.3 验收

- 项目权限未通过时不进入 MCP 调用。
- 能力不可用时不继续追问业务执行字段。
- Middleware 输出能写入 Trace。

## 6. C3 ProjectResolution 与权限底座

### 6.1 规则

必须写死：

- 用户明示项目优先于顶部项目。
- 用户明示项目无权限时阻断，不回退顶部项目。
- 跨项目问数必须逐项目校验权限。
- 包交付不在第一批；但单项目约束应保留为后续扩展规则。

### 6.2 输出结构

```ts
type ProjectResolution = {
  ui_selected_project_ref?: string
  explicit_project_mentions: ProjectMention[]
  effective_project_refs: string[]
  resolution_source:
    | 'explicit_user_project'
    | 'ui_selected_project'
    | 'cross_project_compare'
    | 'history_inherited'
    | 'clarification_required'
  conflict_detected: boolean
  clarification_needed: boolean
  permission_status: 'allowed' | 'partial_allowed' | 'denied' | 'unknown'
}
```

### 6.3 工具调用约束

所有问数 MCP 入参只能使用 `effective_project_refs` 派生出的 appId 或项目参数。

禁止：

- 使用顶部项目覆盖用户明示项目。
- 使用未经权限校验的项目。
- 项目不明确时伪造默认项目。

### 6.4 验收

- 顶部 A，用户问 B，调用 B。
- 顶部 A，用户问无权限 B，阻断，不调用 A。
- 用户问“这个项目”，没有明示项目时可使用顶部项目。
- 项目别名多候选时追问。

## 7. C4 CapabilityRegistry 最小版

### 7.1 能力来源

第一批只纳入：

- MCP `tools/list`。
- 报表能力 manifest。
- 字典能力 manifest。
- admin override。
- `general_answer` 兜底能力。

### 7.2 输出结构

```ts
type CapabilityRecord = {
  capability_id: string
  domain: 'data_report' | 'dictionary' | 'general_answer'
  display_name: string
  binding_type: 'mcp_tool' | 'internal_api' | 'model_answer'
  binding_ref: string
  status: 'available' | 'degraded' | 'unavailable' | 'missing'
  schema_version?: string
  required_slots: string[]
  optional_slots: string[]
  project_scope: 'none' | 'single_project' | 'multi_project_allowed'
  health: 'healthy' | 'warning' | 'down' | 'unknown'
  source: 'runtime_discovery' | 'admin_override'
}
```

### 7.3 缺口分类

问数失败必须归类：

| 类型 | 含义 |
|---|---|
| `mcp_native_chat_mapping_gap` | MCP 已披露，Chat 未映射 |
| `slot_resolution_gap` | slot 未补齐 |
| `dictionary_resolution_gap` | 字典未调用或失败 |
| `schema_adapter_gap` | schema adapter 缺失 |
| `ui_contract_gap` | UI 未支持展示 |
| `trace_gap` | Trace 未记录 |
| `mcp_capability_missing` | MCP 真实缺失 |

### 7.4 验收

- 报表 MCP 已披露 tool 能出现在能力清单。
- 字典 tool 能出现在能力清单。
- MCP 已披露但 Chat 未命中时，归类为 Chat 映射缺口。
- 禁用 tool 后，CapabilityPreflight 返回 unavailable。

## 8. C5 问数 MCP 执行链路

### 8.1 执行顺序

```text
TaskPlan
  -> ReportQuestionType
  -> Project appId
  -> SlotResolver
  -> DictionaryToolCall
  -> ReportToolSelect
  -> SchemaAdapter
  -> MCP ToolCall
  -> ResultParser
  -> ResponseContract
```

### 8.2 第一批支持的问题类型

- 日报。
- 小时报表。
- ROI。
- 留存。
- 素材。
- 字典查询。

### 8.3 字典规则

必须先走字典或已验证 alias：

- 媒体。
- 终端。
- 团队。
- 应用类型。
- 账户。
- 包体。
- 优化师。

字典失败不得继续调用报表 tool。

### 8.4 验收

- 日报、小时、ROI、留存、素材至少各有一条 P0 可执行路径。
- 字典空结果、多候选、不可用都不调用报表 tool。
- MCP 调用失败时 result_status 不得为 success。
- 解析失败时生成 `parse_failed`。

## 9. C6 ToolCallEnvelope 与错误分类

### 9.1 统一结构

```ts
type ToolCallEnvelope = {
  call_id: string
  trace_id: string
  capability_id: string
  binding_type: 'mcp_tool' | 'internal_api'
  binding_ref: string
  input_summary: Record<string, unknown>
  started_at: string
  ended_at?: string
  result_status:
    | 'success'
    | 'partial_success'
    | 'empty'
    | 'permission_denied'
    | 'schema_mismatch'
    | 'timeout'
    | 'service_error'
    | 'parse_failed'
  output_summary?: Record<string, unknown>
  evidence_refs: string[]
  tool_error_raw?: string
  tool_error_safe?: string
  tool_error_type?: 'permission' | 'parameter' | 'network' | 'service' | 'empty' | 'timeout'
  tool_error_stage?: 'auth' | 'parameter_build' | 'call' | 'parse' | 'display'
}
```

### 9.2 前端文案绑定

| 前端文案 | 后端条件 |
|---|---|
| 已查询 | 至少一个问数 ToolCallEnvelope 完成，且状态为 success、partial_success 或 empty |
| 查询失败 | ToolCallEnvelope 为 timeout、service_error、schema_mismatch、parse_failed |
| 无权限 | ToolCallEnvelope 或 PermissionCheck 为 permission_denied |
| 已保存 | PersistenceResult 保存成功 |

### 9.3 验收

- 工具失败时同时有 `tool_error_raw` 和 `tool_error_safe`。
- 前端不展示 raw error。
- schema mismatch 能和 service_error 区分。

## 10. C7 ResponseContract、MessagePart 与 UI 四态

### 10.1 输出结构

```ts
type ResponseContract = {
  response_type:
    | 'clarification'
    | 'business_result'
    | 'partial_result'
    | 'blocked'
    | 'case_draft'
    | 'general_answer'
  user_message: string
  cards: RuntimeCard[]
  evidence_refs: string[]
  recommended_actions: RecommendedAction[]
  source_summary: SourceSummary[]
  message_parts?: MessagePart[]
}
```

### 10.2 MessagePart Protocol

`MessagePart` 是前端展示协议，不替代现有 message schema、conversation store 或 send message API。

第一批问数闭环最小支持：

| type | 用途 | 来源 |
|---|---|---|
| `text` | 最终结论、解释、阻断原因 | `ResponseContract.user_message` |
| `timeline` | 展示执行过程 | `AgentProcessEvent`、`ToolCallEnvelope`、`CapabilityPreflight` |
| `tool_call` | 展示真实工具调用摘要 | `ToolCallEnvelope` |
| `table` | 展示问数表格 | `ReportQueryResult.rows/columns` |
| `chart` | 展示图表 | `ReportQueryResult.viz_spec` |
| `action_list` | 展示下一步建议 | `recommended_actions` |
| `source_refs` | 展示来源证据 | `evidence_refs`、`source_summary` |

禁止：

- 用自然语言反推 `MessagePart` 的业务成功状态。
- 用前端本地状态伪造“已查询”“已检查”“已保存”。
- 把模型内部推理或伪 CoT 展示为 Timeline。

### 10.3 UI 四态

| 状态 | 必须展示 |
|---|---|
| 成功 | 查询项目、时间、筛选条件、表格、来源、下一步建议 |
| 空结果 | 空结果类型、查询条件、放宽条件建议 |
| 失败 | 失败阶段、脱敏原因、可执行下一步 |
| 部分成功 | 成功部分、失败部分、缺失影响 |

### 10.4 Timeline / Stepper 验收

Timeline 只展示用户可理解的结构化事件：

```text
识别意图
-> 解析项目
-> 检查权限
-> 能力预检
-> 调用字典
-> 调用报表
-> 解析结果
-> 生成建议
```

不展示：

- 模型内部推理。
- “我正在思考”。
- 未脱敏工具入参和原始后台日志。
- 和真实调用状态不一致的过程文案。

### 10.5 验收

- 成功结果不得只有自然语言。
- 空结果不得展示为失败。
- 失败不得展示为成功卡。
- 下一步建议必须根据状态变化。
- 有 `message_parts` 时，前端优先按 `MessagePart` 渲染。
- 无 `message_parts` 时，前端兼容旧消息和旧结果卡。
- `tool_call` 必须绑定真实工具调用事件或 envelope。
- `table` / `chart` 必须来自真实问数结果。

## 11. C8 Trace 与验收门禁

### 11.1 Trace 最小字段

Trace 字段最终以连弩 SDK 为准。第一批小乔至少要提供：

- trace_id。
- conversation_id。
- message_id。
- user_id。
- role_id。
- route_context。
- project_context。
- capability_context。
- execution_context。
- result_context。
- completion_status。

### 11.2 发送策略

- 本地开发允许关闭。
- 测试/生产发布前必须配置。
- 发送失败不阻断用户回答。
- 发送失败必须记录本地状态。

### 11.3 第一批验收门禁

必须全部通过：

- 顶部项目冲突用例不请求错误项目。
- P0 问数用例不出现 tool mismatch。
- 字典失败不调用报表 tool。
- 无真实 tool call 不输出数据结论。
- 前端四态齐全。
- Trace 覆盖 route、project、capability、tool call、parse、response。

## 12. C9 前端页面保护约束

### 12.1 任务目标

本约束用于保护第一批最低闭环实施期间的现有聊天页面，不在本批次引入新的第三方聊天渲染框架，也不新增独立渲染适配层。

第一批的前端重点是让问数执行结果、失败状态、空结果、部分成功和下一步建议真实展示出来，而不是替换聊天渲染框架。

### 12.2 禁止改动范围

本任务明确禁止替换或重构：

- Header。
- Sidebar。
- Workspace。
- Drawer。
- 路由。
- 全局状态。
- conversation store。
- send message API。
- 现有 message schema。

任何消息渲染体验优化都不得混入第一批最低闭环主线。如后续确需替换渲染框架，必须重新进入单独需求、设计和验收评审。

### 12.3 允许改动范围

仅允许：

- 在现有聊天渲染体系内补齐 UI 四态展示。
- 在现有消息组件体系内展示 `ResponseContract`、`ToolCallEnvelope`、`RuntimeCard` 等结构化结果。
- 保持现有 message schema 不变。
- 保持现有 conversation store 不变。
- 保持现有 send message API 不变。
- 保持现有 `ChatContainer` 外层布局、输入区、历史会话入口、项目选择和右侧工作区关系不变。

### 12.4 样式保护要求

新增样式必须局部作用于现有聊天内容区域或具体结果卡组件。

禁止：

- 修改全局 antd 样式。
- 覆盖 `body`、`html`、`.ant-*`、全局 button/input/table 样式。
- 引入影响 Header、Sidebar、Workspace、Drawer 的布局样式。
- 用全局样式重置消息列表、输入区、侧边栏或工作区。

必要时使用局部 CSS Module 或现有组件 class 控制范围。

### 12.5 数据与状态保护规则

前端展示必须继续消费现有：

- message schema。
- conversation store。
- send message API。
- `ResponseContract`。
- `ToolCallEnvelope`。

不得新增独立消息状态源，不得绕过现有发送 API，不得以新的前端本地状态伪造“已查询”“已保存”“已检查”等业务结论。

### 12.6 验收

- Header、Sidebar、Workspace、Drawer 布局没有变化。
- 路由行为没有变化。
- conversation store 没有替换。
- send message API 入参和返回结构没有变化。
- 现有 message schema 没有破坏性变更。
- 全局 antd 样式无变化。
- 旧消息、用户消息、助手消息、结构化结果卡仍能通过现有渲染体系展示。
- UI 四态仍由 `ResponseContract` 和 `ToolCallEnvelope` 驱动，不由前端自行判断业务状态。

## 13. 第一批代码实施顺序

建议按以下顺序排期：

1. C1 Runtime 类型与主入口。
2. C3 ProjectResolution 与权限底座。
3. C4 CapabilityRegistry 最小版。
4. C2 MiddlewarePipeline 最小版。
5. C5 问数 MCP 执行链路。
6. C6 ToolCallEnvelope 与错误分类。
7. C7 ResponseContract、MessagePart 与 UI 四态。
8. C8 Trace 与验收门禁。
9. C9 前端页面保护约束。

原因：

- 项目权限和能力发现是调用 MCP 前置条件。
- Middleware 需要调用项目权限和能力发现。
- 问数执行需要依赖 slot、字典、schema adapter 和 ToolCallEnvelope。
- UI 和 Trace 必须消费执行结果和 MessagePart，不应先行伪造状态。
- 第一批不替换聊天渲染框架，只在现有渲染体系内补齐真实状态展示。

## 14. 阻断缺口

| 缺口 | 阻断影响 | 处理 |
|---|---|---|
| 报表 MCP 返回样本不足 | 解析器和 UI 四态无法验收 | 补成功、空结果、权限失败、schema mismatch 样本 |
| 能力发现快照不足 | CapabilityRegistry 无法验收 | 补 MCP server/tool/schema/health 快照 |
| 字典 tool 映射不足 | 中文筛选无法转 MCP 参数 | 补字段到字典 tool 映射 |
| 连弩字段未冻结 | Trace 只能本地记录，不能最终验收 | 等连弩 SDK 文档冻结 |
| UI 四态组件契约不足 | 前端可能继续只显示自然语言 | 补四态组件契约和截图验收 |
| MessagePart 派生规则不足 | 前端仍依赖散落 metadata 和自然语言判断 | 补 Result Protocol 到 MessagePart 的派生规则 |

## 15. 明确不做

第一批不做：

- 包交付状态机和联调触发。
- 异常排查 Workflow。
- 定时报表调度。
- 我的资产真实落库。
- 个人知识库 Key 配置。
- Case 真实创建。
- 市场情报、预测、广告投放自动执行。
- Header、Sidebar、Workspace、Drawer、路由、全局状态重构。
- conversation store、send message API、message schema 替换。

这些不应混进第一批代码任务，否则最低闭环会失焦。
