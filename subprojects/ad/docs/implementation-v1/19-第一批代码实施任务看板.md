# 第一批代码实施任务看板

> Historical archive / 非当前实施真源。
>
> 本文是早期第一批代码任务拆解记录，保留用于追溯历史决策，不再作为当前 P0 实施、提交范围或验收门禁的依据。当前 Chat OS 实施必须以 `docs/architecture/ENTERPRISE_AI_CHAT_OS_SPEC.md`、`docs/architecture/00_SPEC_INDEX.md` 及其下级架构文档为准。
>
> 文中的 P0-1 到 P0-6、允许修改文件、禁止修改文件、验收命令和阻断条件均为历史计划口径。后续不得据此硬编码报表类型、工具选择、Prompt 规则或 UI 展示；应按 Capability Manifest、Tool Contract、Resolver Chain、MCP preflight、Evidence Ledger、ResponseContract 等当前架构协议实施。

## 1. 文档定位

本文承接：

- `17-第一批代码落地执行计划与文件边界.md`
- `18-第一批验收矩阵与自测门禁.md`

本文目标是把第一批代码实施拆成可分配、可跟踪、可验收的任务卡。

本文不是需求文档，也不是设计文档。它是进入编码前的执行看板。

## 2. 第一批实施原则

第一批只做问数最低闭环。

必须遵守：

- 先项目权限，后工具调用。
- 先能力预检，后 slot 补齐。
- 先真实 MCP 调用，后前端展示。
- 先 Result Protocol，后 Timeline / Card 体验。
- 不重构现有页面框架。

禁止混入：

- 包交付状态机。
- 异常排查 Workflow。
- 资产真实落库。
- 个人知识库 Key 配置。
- Case 真实创建。
- 市场情报、预测、广告投放自动执行。
- assistant-ui 或其他聊天渲染框架。

## 3. 实施顺序

```text
P0-1 项目解析与权限冲突
  -> P0-2 能力发现与预检
  -> P0-3 问数 MCP 执行链路
  -> P0-4 ResponseContract / MessagePart
  -> P0-5 前端 UI 四态与 Timeline
  -> P0-6 Trace 与发布门禁
```

不得先做前端视觉体验，也不得绕过项目权限直接调 MCP。

## 4. 任务看板

### P0-1 项目解析与权限冲突

| 字段 | 内容 |
|---|---|
| 任务目标 | 修正顶部项目与用户明示项目冲突，确保 MCP 入参只来自权限校验后的 effective project |
| 关联文档 | 04、15、17、18 |
| 允许修改文件 | `intent-router.ts`、`intent-route-engine.ts`、`context-compiler.ts`、`conversation-context.ts`、`report-query-orchestrator.ts` |
| 谨慎修改 | `useConversation.ts`，只允许传递上下文，不重写发送 API |
| 禁止修改 | Header、Sidebar、Workspace、Drawer、全局路由、conversation store 主 schema |

输入契约：

- 用户原始问题。
- 顶部项目。
- 会话项目上下文。
- 用户可访问项目列表。
- 历史消息中可继承项目。

输出契约：

- `explicit_project_mentions`
- `ui_selected_project_ref`
- `effective_project_refs`
- `permission_status`
- `clarification_needed`
- `blocked_reason`

验收用例：

- 顶部 A，用户问 B，调用 B。
- 顶部 A，用户问无权限 B，阻断。
- 用户问“这个项目”，使用顶部项目。
- 用户问 A 和 B 对比，逐项目校验权限。

自测命令：

```text
npm run ts-check
npm run test:report-query
```

阻断条件：

- 无权限仍调用 MCP。
- 用户明示项目被顶部项目覆盖。
- 项目不明确时伪造默认项目。

完成定义：

- P0 项目冲突用例全部通过。
- MCP 入参只使用 `effective_project_refs`。
- 阻断场景前端不展示数据事实。

### P0-2 能力发现与预检

| 字段 | 内容 |
|---|---|
| 任务目标 | 将报表 MCP、字典 MCP、override 和 policy 统一进入问数 preflight |
| 关联文档 | 06、13、15、17、18 |
| 允许修改文件 | `report-capability-manifest.ts`、`report-capability-override-store.ts`、`report-query-policy-store.ts`、`mcp-server-store.ts`、`mcp-discovery.ts`、`report-query-orchestrator.ts` |
| 谨慎修改 | admin report capability API，仅补输出字段，不破坏兼容 |
| 禁止修改 | MCP 协议本身、MCP server 管理主流程 |

输入契约：

- MCP server config。
- MCP tools/list。
- report capability override。
- report query policy。
- 问数类型。
- 已解析项目和 slot。

输出契约：

- `CapabilityPreflightResult`
- `capability_checks`
- `missing_capabilities`
- `missing_context_fields`
- `selected_capability_id`
- 缺口归因：Chat 映射、slot、字典、schema、UI、Trace、MCP 真实缺失。

验收用例：

- 报表 tool 能进入 manifest。
- 字典 tool 能进入 manifest。
- 禁用关键 tool 后 preflight 标记 missing。
- MCP 已披露但 Chat 未映射时，不归因为 MCP 缺失。

自测命令：

```text
npm run test:report-query:mapping
npm run test:report-query
```

阻断条件：

- 字典能力缺失仍调用报表。
- 把 Chat 映射缺口误判为 MCP 缺失。
- capability id 无法追溯到 server/tool。

完成定义：

- P0 测试集中能力映射无错误命中。
- 缺失能力能被结构化解释。
- preflight 结果能进入 response metadata。

输入契约：

- 字典解析结果。

- `empty_diagnosis`

验收用例：

### P0-4 ResponseContract / MessagePart

| 字段 | 内容 |
|---|---|
| 任务目标 | 将真实执行结果派生为稳定前端展示协议 |
| 关联文档 | 14、15、16、17、18 |
| 允许修改文件 | `types/index.ts`、`agent-runtime.ts`、`report-query-orchestrator.ts`、`report-answer-composer.ts` |
| 谨慎修改 | 消息 metadata 挂载逻辑，只允许兼容新增字段 |
| 禁止修改 | message 主 schema、conversation store 主结构、send message API 入参 |

输入契约：

- `ReportQueryResult`
- `ToolCallEnvelope`
- `AgentProcessEvent`
- `recommended_actions`
- `source_summary`
- `evidence_refs`

输出契约：

- `metadata.response_contract`
- `metadata.message_parts`
- `metadata.tool_call_envelopes`
- `process_events`

最小 MessagePart：

```ts
type MessagePart =
  | { type: 'text'; data: { text: string } }
  | { type: 'timeline'; data: { events: AgentProcessEvent[] } }
  | { type: 'tool_call'; data: ToolCallEnvelope }
  | { type: 'table'; data: { columns: string[]; rows: Record<string, unknown>[] } }
  | { type: 'chart'; data: { viz_spec: unknown } }
  | { type: 'action_list'; data: { actions: string[] } }
  | { type: 'source_refs'; data: { refs: SourceRef[] } }
```

验收用例：

- 成功结果生成 text/table/chart/action/source。
- 失败结果生成 text/timeline/tool_call/action。
- 空结果生成 text/table empty/action/source。
- 部分成功生成成功部分和失败部分。

自测命令：

```text
npm run ts-check
npm run test:report-query
```

阻断条件：

- 前端需从自然语言反推业务状态。
- `tool_call` 无真实调用来源。
- `chart` 无真实数据来源。

完成定义：

- 新消息可带 `message_parts`。
- 旧消息不带 `message_parts` 仍兼容。
- MessagePart 与执行状态一致。

| 字段 | 内容 |
|---|---|
| 任务目标 | 在现有聊天渲染体系内展示 MessagePart、问数四态、Timeline 和来源 |

输入契约：

- `ReportQueryResult`
- `process_events`
- `source_refs`

输出契约：

- 空结果态。

验收用例：

自测命令：

完成定义：

- 历史会话可回看。

| 字段 | 内容 |
|---|---|
| 任务目标 | 保证第一批链路可追踪、可自测、可发布前阻断 |

输入契约：

输出契约：

- `trace_id`

完成定义：

- 第一批发布门禁全部通过。
- 自测脚本全部通过。
- 未通过项有清单和责任归属。

## 5. 跨任务依赖

| 任务 | 依赖 | 说明 |
|---|---|---|
| P0-2 | P0-1 | 未完成项目权限前不得真实调用 MCP |
| P0-3 | P0-1、P0-2 | 问数执行依赖项目和能力预检 |
| P0-4 | P0-3 | MessagePart 必须由真实结果派生 |
| P0-5 | P0-4 | 前端四态依赖展示协议 |
| P0-6 | P0-1 到 P0-5 | Trace 和发布门禁覆盖全链路 |

可并行：

- P0-2 的 manifest 自测可与 P0-1 的项目解析并行。
- P0-5 的旧消息兼容梳理可与 P0-4 类型设计并行。
- P0-6 的本地 trace 字段梳理可提前进行，但不能替代主链路验收。

不可并行：

- 前端“已查询”文案不得先于 ToolCallEnvelope。
- 图表展示不得先于真实 `ReportQueryResult`。
- 发布门禁不得先于 P0-1 到 P0-5。

## 6. 第一批完成定义

第一批代码实施完成必须满足：

- P0-1 到 P0-6 均完成。
- `npm run ts-check` 通过。
- `npm run validate:ad-ui` 通过。
- `npm run test:report-query` 通过。
- `npm run test:report-query:mapping` 通过。
- `npm run test:role-mapping` 通过。
- `npm run build` 通过。
- P0 人工验收用例通过。
- 项目权限冲突用例通过。
- 无权限用例没有 MCP 调用。
- MCP 失败不展示“已查询”。

- 页面布局无结构性变化。

## 7. 看板状态字段

执行时每张任务卡建议维护以下状态：

| 字段 | 可选值 |
|---|---|
| status | `todo`、`in_progress`、`blocked`、`ready_for_review`、`done` |
| owner | 负责人 |
| risk | `low`、`medium`、`high` |
| blocker | 阻断说明 |
| evidence | 自测输出、截图、日志、Trace 样本 |
| linked_pr | PR 或提交 |
| acceptance | 验收结论 |

## 8. 明确不做

第一批任务看板不包含：

- 包交付状态机。
- 联调触发。
- 异常排查 Workflow。
- 定时报表调度。
- 资产真实落库。
- 个人知识库 Key 配置。
- Case 真实创建。
- 市场情报。
- 预测。
- 广告投放自动执行。

这些后续应单独建第二批或第三批任务看板。
