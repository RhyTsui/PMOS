# 对话路由细节问题评估与落地方案

## 1. 文档定位

本文承接 `docs/design-v1/01-对话路由系统设计.md`、`docs/design-v1/13-能力发现与服务绑定执行闭环系统设计.md` 和 inbox 文档《对话路由细节问题和解决方案.md》，用于把对话路由从“意图分类”落到“任务拆解、上下文继承、能力预检、真实执行闭环”。

核心目标不是让 Chat 猜用户想法，而是让系统在真实能力边界内完成：

1. 理解用户输入。
2. 拆解可能的多任务。
3. 解析项目、指标、包、媒体、时间等业务对象。
4. 调用能力发现结果确认是否可执行。
5. 能执行则执行，不能执行则追问、阻断或生成 Case。

## 2. 总体结论

对话路由器不是单点 intent 分类器，而是任务编排器。

一句用户输入可能包含多个任务，例如“查一下 B 项目昨天消耗，顺便做成日报”。系统应拆成“数据查询任务”和“日报生成任务”，并建立任务依赖。只要后续动作涉及外发、写操作、投放变更、预算调整、批量操作，都必须进入确认流。

路由阶段可以追问，但追问的职责是补齐能决定路由和预检的关键输入；下游能力也可以继续追问，但只能追问执行该能力所需的细项。

## 3. 任务拆解规则

路由输出应从单 intent 升级为 `TaskPlan`：

```json
{
  "user_utterance": "查一下 B 项目昨天消耗，顺便做成日报",
  "tasks": [
    {
      "task_id": "T1",
      "intent": "data_query",
      "slots": {
        "project": { "value": "B项目", "source": "explicit", "confidence": 0.96 },
        "metric": { "value": "spend", "source": "explicit", "confidence": 0.98 },
        "date_range": { "value": ["2026-05-25", "2026-05-25"], "source": "relative_time_resolved", "confidence": 0.99 }
      },
      "capability": "ad_data_query",
      "risk_level": "read_only",
      "status": "ready"
    },
    {
      "task_id": "T2",
      "intent": "report_generate",
      "depends_on": ["T1"],
      "slots": {
        "report_type": { "value": "daily_report", "source": "explicit", "confidence": 0.95 }
      },
      "capability": "daily_report_generate",
      "risk_level": "content_generation",
      "status": "ready"
    }
  ],
  "need_user_confirmation": false
}
```

常见任务关系：

| 关系 | 触发词 | 处理 |
|---|---|---|
| 顺序依赖 | 然后、顺便、做成、基于这个 | 前一任务结果作为后一任务输入 |
| 并行动作 | 同时、另外、再查一下 | 多任务并行或顺序执行后合并展示 |
| 条件动作 | 如果、要是、低于就 | 先执行判断任务，再触发后续动作 |
| 复合动作 | 查一下并给建议 | 查询、分析、建议生成分任务执行 |

## 4. 上下文继承规则

上下文可以继承，权限不能继承。

上下文分四层：

| 层级 | 示例 | 继承规则 |
|---|---|---|
| 业务实体上下文 | 项目、包、账户、素材 | 可继承；高风险动作需确认 |
| 指标上下文 | 消耗、CPA、D1 ROAS | 可继承；指标歧义需追问 |
| 时间上下文 | 昨天、最近 7 天、上周 | 可继承；必须解析成绝对日期 |
| 知识主题上下文 | ROAS 下降原因 | 只能继承为分析主题，不能自动补项目 |

继承优先级：

1. 当前句子显式 slot。
2. 上一轮用户确认过的 slot。
3. 最近一次成功执行任务的主对象。
4. 当前工作台或顶部项目上下文。
5. 用户偏好。
6. 历史会话记忆，仅在用户说“上次”“之前那个”时启用。

显式输入永远覆盖继承上下文。顶部项目只是默认上下文，不是用户本轮显式项目。

## 5. 纠错和重跑规则

用户纠正系统理解时，必须根据纠正类型决定是否重跑路由和覆盖 slot。

| 纠正类型 | 示例 | 是否重跑路由 | 处理 |
|---|---|---|---|
| 实体纠正 | 不是 B，是 C | 是 | 覆盖项目 slot，重跑受影响任务 |
| 时间纠正 | 不是昨天，是上周 | 是 | 覆盖时间，重查数据和下游分析 |
| 指标纠正 | 不是消耗，是 ROI | 是 | 覆盖 intent/metric，重新匹配能力 |
| 输出纠正 | 日报太长，改成三段 | 否 | 不重查数据，只重渲染输出 |

每个 slot 需要记录 `value`、`source`、`confidence`、`version`、`confirmed_by_user`、`expires_at`。用户显式纠正优先级最高，只覆盖被纠正的 slot，不删除旧结果，保留版本和审计链路。

## 6. 引用解析规则

系统需要维护 `ReferenceLedger`，记录当前会话中出现过的项目、包、指标、媒体、报表、任务和结果。

引用解析优先级：

1. 当前页面选中对象。
2. 最近一轮明确提到的同类型对象。
3. 最近一次成功执行任务的主对象。
4. 当前业务工作台默认对象。
5. 历史会话或任务记录。

“刚才那个项目”如果最近只有一个主项目，可自动解析并在回复中明示；如果最近对比过多个项目，必须追问。“上次那个包”只能解析成包，不能把项目强行当成包。“这个指标”如果上一轮展示多个指标，必须追问。

引用置信度建议：

| 分数 | 行为 |
|---|---|
| >= 0.85 | 自动解析，并明示理解 |
| 0.70-0.85 | 可执行低风险查询，但展示假设 |
| 0.55-0.70 | 追问确认 |
| < 0.55 | 不执行，要求用户明确对象 |

## 7. 路由置信度与追问

不使用单一总分决定全部动作。路由置信度至少拆成：

- `intent_confidence`
- `entity_confidence`
- `slot_confidence`
- `capability_confidence`
- `context_confidence`

自动执行阈值：

| 场景 | 自动执行阈值 | 必须确认 |
|---|---:|---|
| 只读数据查询 | >= 0.80 | 否 |
| 报表生成 | >= 0.78 | 外发时需要 |
| 归因诊断 | >= 0.82 | 否 |
| 预算、出价、暂停、开启 | >= 0.90 | 必须 |
| 批量操作 | >= 0.95 | 必须 |
| 修改回传口径 | >= 0.95 | 必须 |

无论总分多高，以下情况必须追问：项目/包/账户多候选、时间影响结论但不明确、指标口径不唯一、写操作、使用“全部/所有/一键处理”、系统能力部分缺失且继续执行会误导。

## 8. 多能力命中优先级

同一意图命中多个能力时，先判断是互补能力还是竞争能力。涉及数值事实时，可信数据源优先；涉及专业诊断时，专业 Agent/Workflow 优先；通用 LLM 只能做解释、归纳、补充和语言组织。

能力优先级：

1. 权限与风控。
2. 业务实体解析。
3. 可信数据源。
4. 专业 Agent / Workflow。
5. 报表或内容生成。
6. 通用 LLM / RAG。
7. Case / 人工流转。

## 9. 部分可用时的处理

| 情况 | 动作 |
|---|---|
| 缺用户才能提供的信息 | 追问 |
| 缺非关键参数且有默认值 | 先执行并明示假设 |
| 数据源部分不可用 | 返回部分结果，标明缺失，必要时生成 Case |
| 权限不足 | 返回可访问范围或阻断，不绕过权限 |
| 回传延迟 | 返回当前值并标注延迟风险 |
| 写操作部分可执行 | 不自动部分执行，必须确认 |
| 合规能力不可用 | 阻断高风险输出 |
| 目标不可实现 | 生成 Case 或替代方案 |

## 10. 验收规则

- 顶部选 A，用户明确问 B，最终不能请求 A。
- 用户问无权限项目，必须阻断，不回退顶部项目。
- 多意图输入必须生成多个任务和依赖关系。
- 用户纠错后只重跑受影响任务。
- “刚才那个项目”“这个指标”多候选时必须追问。
- 未通过能力预检时不得输出执行完成口吻。
- 数值事实必须来自工具、MCP、Workflow 或可信数据源。
