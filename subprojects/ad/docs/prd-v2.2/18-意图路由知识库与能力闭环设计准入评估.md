# 意图路由、知识库调用与能力闭环设计准入评估

## 1. 文档目的

本文件用于补齐 V2.2 文档包中最容易导致半成品的部分：用户意图如何被正确理解，广告业务受控术语词典如何被调用，能力发现如何早于信息补齐，提示词、代码、配置、Workflow、Skill、MCP 的边界如何划分。

结论先行：当前产品方向已经清楚，但还不能直接进入工程实施。第三阶段系统设计必须先把本文件中的准入项落成接口、配置、评测样本和验收规则，否则容易出现“Chat 看起来会回答，但没有真实业务闭环”的问题。

## 2. 当前实现核对

### 2.1 已有基础

当前系统已经具备以下基础：

- `intent-router`：通过代码规则识别 `report_query`、`diagnosis`、`debugging`、`get_delivery_packages`、`demand`、`monitor`、`help`、`general` 等意图。
- `intent-route-rules`：已有可配置路由规则结构，支持关键词、排除词、优先级、灰度状态等字段。
- `context-compiler`：可以编译角色、偏好、业务上下文、slot 状态、追问策略和渲染提示。
- `slot-resolver`：为数据查询、异常诊断、联调、监控、需求、包交付等意图定义了部分必填 slot。
- `prompt-store`：已有提示词配置、版本、绑定和管理能力。
- `report_query`：当前最完整的真实执行链路，会创建 Workflow Task / Run，调用报表查询步骤，写入结果并发送 Trace。
- `广告业务受控术语词典-2026-05-25.md`：已经沉淀受控术语、别名、低置信度追问规则和禁止归一化规则。

### 2.2 主要缺口

当前实现仍存在以下缺口：

- 受控术语词典目前是知识资产，不是稳定的路由前置服务。
- 主 Chat 链路最终路由时没有完整传入角色、偏好、规则配置和能力发现结果。
- 可配置路由规则存在，但不是所有主链路都真正读取和执行。
- slot schema 主要写在代码中，还没有和能力注册表、Workflow 入参完全打通。
- 提示词库存在，但路由主链路不是提示词治理链路，提示词没有成为可追踪的路由判断来源。
- 除 `report_query` 外，其它业务意图多数没有真实 Workflow / Skill / MCP 调用闭环。
- Trace 已有基础，但还需要补齐术语归一化、能力发现、追问、路由候选、工具调用、失败 case 的事件明细。

### 2.3 当前业务理解程度

| 领域 | 产品理解 | 工程细节掌握 | 结论 |
|---|---:|---:|---|
| 数据查询与报表 | 较高 | 中等 | 可进入系统设计，但需补接口字段 |
| 定时报表 | 较高 | 中等 | 可进入系统设计 |
| 包交付与联调 | 较高 | 偏低 | 可做流程设计，需接口方确认返回模型 |
| 项目权限与资产过滤 | 较高 | 中等 | 可进入系统设计 |
| 异常排查 | 中等 | 偏低 | 需补诊断 Skill / Workflow 契约 |
| 需求沟通 | 中等 | 偏低 | 需补结构化需求输出模型 |
| 指标解释 | 中等 | 偏低 | 必须先接内部口径库 |
| 意图路由与术语词典 | 中等 | 偏低 | 必须先补本文件定义的路由闭环设计 |

## 3. 目标处理链路

每轮用户输入应按以下链路处理：

1. 接收用户输入。
2. 编译用户、角色、项目、权限、会话、资产和页面上下文。
3. 调用受控术语归一化能力。
4. 生成候选意图。
5. 查询能力注册表。
6. 判断能力状态、阶段开放、角色权限、项目权限。
7. 判断是否需要路由前最小澄清。
8. 判断是否需要路由后 slot 补齐。
9. 调用 Workflow / Skill / MCP。
10. 解析结构化执行结果。
11. 生成业务结论、证据来源和下一步建议。
12. 写入 Trace、Evidence、Asset 或 Case。

路由引擎不能直接给业务最终结论。它只输出“用户可能要做什么、当前能不能做、缺什么、该调什么、不能做时怎么闭环”。

## 4. 受控术语词典调用方案

### 4.1 定位

受控术语词典不是普通 RAG 知识库召回，也不是让大模型自由扩展解释。它是路由前置的轻量归一化能力，用于解决内部专业术语、简称、行业表达差异导致的误路由。

### 4.2 调用方式

建议新增 `business-term-normalizer` 能力。该能力可以先用本地结构化词典实现，后续再接知识库服务。

输入：

```ts
type BusinessTermNormalizeRequest = {
  raw_text: string
  user_id: string
  role_id: string
  project_refs: string[]
  conversation_id?: string
  dictionary_version: string
  context_terms?: string[]
}
```

输出：

```ts
type BusinessTermNormalizeResult = {
  raw_text: string
  normalized_text: string
  dictionary_version: string
  normalized_terms: Array<{
    raw: string
    standard: string
    category:
      | 'business_object'
      | 'media_channel'
      | 'event'
      | 'metric'
      | 'attribution'
      | 'dimension'
      | 'issue_type'
      | 'action'
      | 'internal_process'
    confidence: number
    source: 'standard_term' | 'alias' | 'abbreviation' | 'context_rule'
    need_clarification: boolean
  }>
  ambiguous_terms: Array<{
    raw: string
    candidates: string[]
    reason: string
  }>
  clarification_questions: string[]
  confidence: number
}
```

### 4.3 使用规则

- 只使用受控词典中的标准词、别名、简称、上下文规则。
- 不在归一化阶段解释业务原因。
- 不把未录入词典的行业知识扩展成标准业务结论。
- 低置信度时先追问，不进入下游执行。
- 归一化结果必须进入 Trace，用于后续评测路由是否正确。

## 5. 路由规则引擎设计

候选意图由三类来源共同生成：

- 代码内置规则：用于 P0 高频、稳定、低歧义意图。
- 配置化路由规则：用于业务方可调整的关键词、别名、排除词、优先级和灰度。
- LLM 结构化分类：仅用于复杂上下文、弱表达和多意图冲突。

候选结果必须包含：

```ts
type IntentCandidate = {
  intent_key: string
  confidence: number
  source: 'builtin_rule' | 'route_rule' | 'llm_classifier' | 'context_bias'
  matched_terms: string[]
  normalized_terms: string[]
  reason: string
}
```

最终路由不能只看意图置信度，还必须看能力可用性：

```ts
type RouteDecisionV2 = {
  intent_key: string
  confidence: number
  is_business_related: boolean
  candidates: IntentCandidate[]
  capability_id?: string
  capability_status?: 'available' | 'partially_available' | 'planned' | 'disabled' | 'missing'
  workflow_id?: string
  skill_id?: string
  mcp_service_ids?: string[]
  required_slots: string[]
  missing_slots: string[]
  clarification_needed: boolean
  clarification_stage: 'pre_route' | 'post_route' | 'workflow_runtime' | 'none'
  execution_allowed: boolean
  blocked_reason?: string
  next_actions: RecommendedAction[]
}
```

## 6. 能力发现前置

能力发现必须早于 slot 补齐。原因是用户体验上不能先追问一堆字段，最后才说系统不能做。

处理顺序：

1. 先判断候选意图。
2. 再查能力注册表。
3. 如果没有任何可承接能力，进入未接入闭环。
4. 如果能力 `partially_available`，只追问可执行部分所需字段。
5. 如果能力 `available`，再根据能力定义的 required slots 追问。

能力未接入时的行为：

- 不说“已查询”“已检查”“已生成”。
- 可以整理用户已提供信息。
- 可以生成 `capability_not_connected` Case。
- 可以沉淀为路由样本和能力缺口。

## 7. 提示词设计

提示词不能承担全部正确性，只能服务结构化判断和表达生成。

### 7.1 术语归一化提示词

- 只输出 JSON。
- 只使用给定词典。
- 不解释复杂业务原因。
- 不新增标准词。
- 低置信度必须输出追问问题。

### 7.2 意图分类提示词

输入必须包含：

- 用户原文。
- 归一化术语。
- 当前项目上下文。
- 可用能力列表。
- 规则候选意图。

输出必须包含：

- 候选意图。
- 置信度。
- 是否业务域。
- 是否可执行。
- 缺失字段。
- 不能执行原因。

### 7.3 追问提示词

- 一次最多问 1-2 个关键问题。
- 不重复询问上下文已有信息。
- 不能询问不会影响执行的字段。
- 能力不可用时不继续追问执行字段。

### 7.4 结果解释提示词

- 只解释工具返回事实。
- 必须展示证据来源。
- 必须展示下一步建议。
- 不能补造内部数据、包状态、联调结论和指标口径。

## 8. 代码、配置、Prompt、服务边界

### 8.1 写进代码

- 路由流水线顺序。
- 能力发现早于 slot 补齐。
- 权限检查和项目过滤。
- 失败闭环状态机。
- 工具调用结果解析协议。
- Evidence、Trace、Asset、Case 的写入规则。
- 防假功能红线。

### 8.2 写进配置

- 受控术语、别名、简称、歧义规则。
- 路由规则的 include / exclude terms。
- 意图优先级和灰度开关。
- 能力注册表。
- slot schema 和追问文案。
- prompt 版本和绑定关系。
- 连弩评测用例集。

### 8.3 由 Workflow / Skill / MCP 承接

- 取数、拼表、报表生成。
- 定时报表任务创建、执行和结果归档。
- 包状态查询、上报检查、媒体后台更新检测、智投后台更新检测、联调检查。
- 异常诊断、需求结构化、指标口径解释。
- 资产写入和 Case 生成。

## 9. 闭环最低标准

一个意图只有同时满足以下条件，才能算闭环：

- 正确路由。
- 自动补齐可继承上下文。
- 缺失关键字段时追问。
- 确认真实能力可用。
- 调用真实 Workflow / Skill / MCP / 智投接口。
- 正确解析执行结果。
- 给出下一步建议。
- 提供证据来源。
- 记录 Trace。
- 需要时沉淀资产、Case 或评测样本。

## 10. 失败也闭环

系统无力完成时不应过早兜底。失败闭环的流程是：

1. 判断是否只是表达不清。
2. 能追问就先追问。
3. 多轮后仍无法明确，或能力确实不存在，再进入失败闭环。
4. 生成 Case 或能力缺口记录。
5. 告知用户已记录、等待处理或给出替代路径。

失败类型包括：

- `intent_unclear`：多轮后仍无法判断基本意图。
- `capability_missing`：没有可执行能力。
- `capability_disabled`：能力被关闭或未开放。
- `permission_denied`：用户无项目或动作权限。
- `tool_failed`：工具调用失败。
- `result_unparseable`：工具返回无法解析。
- `evidence_missing`：缺少可支撑结论的证据。

## 11. 连弩评测与证据要求

小乔不重建评测平台，但必须向连弩发送可回放记录。

每轮至少记录：

- 用户原文。
- 上下文摘要。
- 术语归一化结果。
- 候选意图和最终意图。
- 能力发现结果。
- slot 继承和缺失情况。
- 追问问题。
- Workflow / Skill / MCP 调用。
- 工具返回摘要。
- Evidence 引用。
- 最终回答。
- 用户是否继续、保存、创建任务或生成 Case。

评测集至少覆盖：

- 查数和指标解释混淆。
- 查包状态和触发联调混淆。
- 数据异常和包异常混淆。
- 内部简称和行业术语差异。
- 项目权限变化。
- 能力未接入。
- 工具失败。
- 多轮追问后仍无法明确。

## 12. 第三阶段设计准入条件

进入第三阶段系统设计前，必须满足：

- 每个 P0 / P1 意图都有路由规则。
- 每个可执行意图都有能力注册项。
- 每个能力都有输入、输出、错误码、证据和下一步建议模型。
- 每个能力都有可执行状态。
- 每个未接入能力都有失败闭环。
- 受控术语词典有可调用形式和版本号。
- Prompt 有版本、绑定、输入、输出和验收样例。
- 连弩评测集覆盖核心混淆场景。
- 当前实现缺口已经映射到工程实施清单。

未满足以上条件时，不能把页面展示、前台按钮或 Chat 文案写成业务已经完成。
