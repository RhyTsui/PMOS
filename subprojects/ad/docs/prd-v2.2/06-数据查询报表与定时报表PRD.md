# 数据查询、报表与定时报表 PRD

## 1. 总体定位

数据与报表是一期最重要的完整闭环。当前系统已经有 `report_query` 真实执行基础，也已有报表模板、报表草稿、定时任务等对象基础，因此这一组需求应该优先从“已有实现”升级为“可信产品闭环”。

报表 MCP / 广告 BI 数据分析服务本身不是空白能力，已有上线和其它 Chat 复用基础。本 PRD 的重点不是重新建设 MCP，而是把已有基础服务完整接入小乔智投 Chat，补齐路由、项目权限、字段补全、真实调用、结果解析、Evidence、资产沉淀和下一步建议。

本需求覆盖：

- 数据查询。
- 数据分析。
- 拼报表。
- 报表草稿。
- 报表模板。
- 定时报表。
- 查询结果保存。
- 数据延迟策略。

## 2. 数据查询

### 2.1 用户目标

用户查数据不是为了看一堆原始行，而是为了快速判断投放表现，并决定下一步动作。

典型问题：

- 昨天这个项目 ROI 怎么样？
- 近 7 天消耗和回收如何？
- 巨量和快手哪个效果更好？
- 按项目和媒体拆一下数据。

### 2.2 当前实现基础

当前系统已经具备问数意图识别和 `report_query` 真实执行链路，会创建 Workflow Task / Run，调用报表查询步骤，记录结果和 Trace。

已有报表 MCP 能力应被视为一期基础服务。小乔侧需要确认 MCP server、tool schema、授权、入参字段、返回字段和错误码契约，而不是把数据查询写成“待建设能力”。

### 2.3 当前缺口

需要补齐：

- 小乔 Chat 对已有报表 MCP 的稳定绑定。
- MCP 入参、出参、错误码和权限失败结构契约。
- 项目权限过滤。
- 查询结果保存规则。
- 数据来源和更新时间展示。
- 指标口径 Evidence。
- 从查询结果转报表、模板、定时报表。
- 基于 `E:\AI\ai-os\docs\sources\inbox\智投Chat_广告业务（问数）测试集_预期精简版_v3.xlsx` 的取数服务自测，以及前端组件、可视化渲染、下一步建议的端到端验收。

从问数测试集反推，还必须补齐以下需求。注意：以下不是默认判定为 MCP 缺失。多数报表、指标、维度、字典和取数能力应优先核对当前已绑定 MCP 的 tool / schema；只有核对后仍不支持的部分才进入 MCP 缺口。进入工程拆解时，每项必须标注为 `mcp_native`、`chat_mapping_required`、`orchestrator_postprocess`、`ui_required` 或 `unknown_or_gap`。

- 报表类型识别：日报、周报、月报、广告小时报表、媒体报表、自然量报表。优先归属 `mcp_native` + `chat_mapping_required`。
- 日期语义解析：自然日期、标准日期、连续区间、紧凑日期、上周、二月、同期、环比、小时段和无效日期。优先归属 `chat_mapping_required`。
- 多维筛选：项目、媒体、团队、应用类型、终端、小游戏平台，以及多维组合拆分。优先归属 `mcp_native` + `chat_mapping_required`。
- 派生指标：ROI、累计 ROI、30 日 ROI、第 2 日 ROI、留存、激活成本、转化率等必须由真实字段或明确公式计算。基础指标优先归属 `mcp_native`，派生指标归属 `orchestrator_postprocess`。
- 分析型问法：最高、最低、topN、对比、环比、高多少等必须基于结构化结果计算。优先归属 `orchestrator_postprocess`。
- 多轮上下文：支持槽位继承、条件分支和后续补查。优先归属 `chat_mapping_required` + `orchestrator_postprocess`。
- 总计核对：支持明细与总计一致性核对。优先归属 `orchestrator_postprocess`。
- 边界处理：无权限、无效日期、不存在媒体、空结果、大范围超时和无法解析分别闭环。归属 MCP 错误结构、Chat 解析和 Case 生成共同负责。
- 问数转诊断：ROI 下降、数据异常类问题可从查数进入诊断流程。归属路由 / Workflow 编排，必要时调用诊断 MCP。
- 可解释调用：展示 MCP tool、关键入参、返回摘要、筛选条件和数据来源。归属 Trace / Evidence / UI。

### 2.4 反推需求的产品化定义

问数测试集反推出的不是一个笼统“问数能力”，而是一组必须落地的产品化能力。

路由层必须把 `report_query` 细分到可执行报表域：

- `ad_daily_report`：日报、周报、月报、按日期 / 周 / 月趋势。
- `ad_hour_report`：小时、实时、分时段、截至某小时。
- `ad_roi_report`：ROI、回收、回本、累计 ROI、区间 ROI。
- `ad_retention_report`：留存、次留、注册留存、设备留存、首日付费账号留存。
- `ad_material_report`：素材、创意、素材标签、素材状态和素材投放表现。
- `ad_dictionary_lookup`：媒体、终端、团队、应用类型、账户、包体、优化师等字典补参。
- `report_diagnosis_candidate`：ROI 下降、数据异常、不一致、无数据等需要从查数进入诊断候选。

Slot 层必须把用户自然语言转为 MCP 可执行字段：

- 项目名、游戏名、应用名、简称和 appId 统一解析为 `appId`。
- 日期语义统一解析为 `startDate`、`endDate`、`timeType`，小时问题补 `dh` 或小时口径。
- 媒体、终端、团队、应用类型、账户、包体和优化师必须先查字典，再填 MCP 识别值。
- ROI 的区间 / 累计、留存类型、自然量 / 广告量等无法判断时必须追问。

Schema Adapter 层必须补齐 MCP 入参转换：

- 日报、周报、月报映射 `DAY`、`NATURAL_WEEK`、`NATURAL_MONTH`。
- 广告量、广告量+自然量、单独自然量映射 `promotionSource` 和必要的媒体规则。
- 按媒体、团队、应用类型及组合拆分映射 `subGroup`。
- 小时报表区分 `EVENT_TIME` 累计口径和 `REGISTER_TIME` 时段新增口径，避免重复累计。
- `dataType`、`retentionType` 等字段必须有确定来源。

编排后处理层必须支持：

- TopN、最高、最低、排序。
- 环比、同期、差值、差异比例。
- 明细与总计一致性核对。
- 多轮槽位继承。
- 条件分支执行。
- 从问数结果进入诊断候选。

前端和结果解释层必须支持：

- 结构化结果卡片。
- 表格、图表和可读格式。
- 数据来源、更新时间、筛选条件和指标口径。
- 空结果、超时、权限失败、解析失败的差异化提示。
- 基于结果状态生成下一步建议。
- 保存资产、转报表、转模板、创建定时报表入口。

失败闭环必须支持：

- 区分 MCP 未配置、endpoint 不通、tool 未发现、权限失败、入参不匹配、返回为空、返回结构变化、解析失败。
- 多轮追问后仍无法完成时生成 Case。
- 失败 Case 记录用户问题、候选能力、缺失 slot、已调用 tool、错误码、返回摘要和建议处理人。

评测层必须按链路节点验收，不只验最终回答：

- 意图识别。
- 项目解析。
- Slot 解析。
- 字典调用。
- Tool 选择。
- 真实 MCP 调用。
- 结果解析。
- 后处理计算。
- UI 契约。
- Evidence / Trace。

失败分类至少包括 `route_error`、`slot_error`、`dictionary_error`、`tool_selection_error`、`mcp_call_error`、`result_parse_error`、`postprocess_error`、`ui_contract_error`、`permission_error`、`data_empty_or_unavailable`。

### 2.5 Chat 职责

Chat 负责识别数据查询意图，提取项目、时间、指标、维度和筛选条件。当前项目明确时可直接使用当前项目；用户说“这个项目”时使用当前项目上下文；时间缺失时可给默认时间范围并提示可调整。

Chat 在调用前必须检查用户项目权限。跨项目查询允许存在，但每个项目都必须过滤。无权限项目不能展示。

### 2.6 Skill / MCP 职责

数据查询 Skill 负责把 Chat 识别出的指标、时间、维度、项目和筛选条件转为结构化请求。MCP / 智投接口返回真实数据、数据来源、数据更新时间、完整性信息和指标口径引用。

Chat 只解释结构化结果，不生成真实数据。

### 2.7 资产规则

一次性查询结果默认不进入资产。用户点击保存后才写入我的资产。

如果用户继续生成报表、保存报表模板或创建定时报表，则进入对应报表流程。

### 2.8 验收标准

数据查询闭环必须满足：

- 能识别查数意图。
- 能追问缺失项目、时间或指标。
- 能调用真实数据能力。
- 能展示数据来源和更新时间。
- 能展示指标口径来源。
- 能按项目权限过滤。
- 能保存为资产。
- 能转报表或定时报表。
- 能通过问数测试集 P0 用例的取数自测。
- 能通过前端结果卡片、表格、图表、来源展示和下一步建议验收。

## 3. 拼报表

### 3.1 用户目标

用户希望把多个指标、多个维度或多次查询结果组织成可阅读、可复用、可发送的报表。

典型问题：

- 帮我生成昨天的投放日报。
- 把这个结果按项目和媒体拼一张表。
- 生成一个周报模板。

### 3.2 报表草稿

报表草稿是临时工作态，不是资产。它用于多轮调整指标、维度、展示形式、排序和结论。

默认规则：

- 草稿默认不保存。
- 用户明确保存后，才成为报表资产或报表模板。
- 草稿可以作为创建定时报表的基础，但创建前必须确认正式配置。

### 3.3 报表模板

报表模板记录指标、维度、筛选、展示结构、时间窗口和说明，不绑定死单个项目。

模板可以跨项目复用，但运行时必须：

- 绑定项目。
- 校验项目权限。
- 校验数据源是否支持。
- 记录运行结果和 Evidence。

### 3.4 Workflow / Skill 职责

报表生成可以由报表 Workflow 承接。Workflow 调用数据查询 Skill 和报表生成 Skill，生成报表草稿或正式报表。

Chat 负责解释报表内容、承接用户调整、提供保存、模板化和定时入口。

## 4. 定时报表

### 4.1 一期定位

定时报表是一期 P0，不是未来自动化的附属功能。

### 4.2 用户目标

用户希望系统周期性生成报表，减少重复查数和拼表。

典型问题：

- 以后每天 10 点生成这个日报。
- 每周一给我一份项目投放周报。
- 这个报表每天自动产出并保存。

### 4.3 创建必填信息

创建定时报表必须确认：

- 项目范围。
- 指标和维度。
- 报表模板或报表结构。
- 周期。
- 执行时间。
- 时区。
- 数据延迟策略。
- 数据不完整时的处理方式。
- 产物保存规则。

### 4.4 数据延迟策略

创建定时报表时必须确认数据延迟策略。可选策略包括：

- T+1 数据。
- 使用数据源最新可用时间。
- 数据不完整时生成带告警报表。
- 数据不完整时等待并重试。
- 数据不完整时跳过本次。

如果用户未确认数据延迟策略，任务不能进入启用状态。

### 4.5 产物规则

定时报表产物默认进入我的资产，并绑定项目。用户权限变化后，历史产物按项目动态过滤。

### 4.6 失败规则

定时报表失败时必须记录：

- 失败时间。
- 失败原因。
- 数据是否未就绪。
- 是否重试。
- 本次是否生成产物。
- 下一步建议。

失败不能只显示“执行失败”，必须有可追溯 Evidence 或错误码。
