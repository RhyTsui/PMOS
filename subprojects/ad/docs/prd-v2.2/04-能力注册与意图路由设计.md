# 能力注册与意图路由设计

## 1. 设计背景

当前系统已经有意图路由，但用户指出一个关键问题：如果不先进行能力发现，系统可能会补全一堆信息，最后才发现无法执行。这会让用户体验变差，也会诱导 Chat 输出假功能。

因此 V2.2 必须引入能力注册表。路由命中只说明“系统理解了用户想做什么”，能力注册才说明“系统是否有真实服务可以执行”。

## 2. 意图和能力的区别

意图是用户想做什么，例如：

- 查数据。
- 生成报表。
- 查包状态。
- 排查异常。
- 解释指标。
- 提需求。

能力是系统能真实调用什么，例如：

- 数据查询 Skill。
- 定时报表 Workflow。
- 包交付 Workflow。
- 上报检查 MCP。
- 联调检查 Skill。
- 口径解释 Skill。

一个意图可以对应多个能力，一个能力也可以服务多个意图。
例如“这个包能投吗”命中包交付意图，但最终需要包交付 Workflow、包状态查询 Skill、上报检查 Skill、联调检查 Skill、媒体后台更新检测 MCP 共同承接。

## 3. 能力状态

能力注册表必须记录能力当前状态：

| 状态 | 含义 | Chat 行为 |
|---|---|---|
| available | 已接入真实服务，可以执行 | 正常调用并返回结果 |
| partially_available | 部分环节已接入 | 调用可用部分，说明缺口 |
| planned | 已规划，未接入 | 不假装执行，可生成 Case 或需求 |
| disabled | 当前不可用 | 告知原因，提供替代建议 |

## 4. 路由处理流程

每轮 Chat 应按以下顺序处理：

1. 接收用户消息。
2. 标准化表达。
3. 编译上下文。
4. 轻量术语识别。
5. 路由意图。
6. 查询能力注册表。
7. 检查阶段是否开放。
8. 检查角色权限。
9. 检查项目权限。
10. 检查必填槽位。
11. 判断是否需要追问。
12. 判断是否可调用 Workflow / Skill。
13. 调用真实能力。
14. 解释结果。
15. 记录 Trace。

## 5. 路由层是否负责追问

追问需要分层：

### 路由前最小澄清

当用户表达无法判断基本意图时，Chat 可以先追问。
例如用户只说“这个不对”，系统无法判断是数据不对、包不对、素材不对还是需求不对，就应先问“你是想查数据异常、包状态，还是提交需求？”

### 路由后槽位补齐

当意图明确，但执行信息不足时，由对应能力定义必填槽位，Chat 承载追问。
例如数据查询缺项目、时间或指标；包交付缺项目、媒体或包版本。

### Workflow 深水区追问

当执行中发现业务条件不足，由 Workflow 返回 `waiting_input`，Chat 继续问用户。
例如异常诊断发现需要活动 ID 或具体异常时间段。

## 6. 内部术语识别策略

用户经常使用内部专业术语，且这些术语可能和行业表达不同。为了避免误判意图，路由前可以做轻量识别：

- 受控术语词典。
- 指标别名。
- 项目别名。
- 媒体别名。
- 包类型别名。
- 内部流程词。

但不建议路由前做重型 RAG。正式知识检索应由路由后的口径解释 Skill 或知识库能力完成。这样可以避免路由链路变慢，也避免知识库召回结果直接污染意图判断。

路由前术语识别必须调用受控术语词典或其结构化服务，不允许让大模型凭常识自由扩展。归一化结果应包含标准词、原始表达、类别、置信度、歧义项和是否需要追问。低置信度且会影响路由时，Chat 应先追问；低置信度但不影响路由时，可以进入后续能力并在结果中提示口径不确定。

详细调用方式、输入输出模型和准入条件见 `18-意图路由知识库与能力闭环设计准入评估.md`。

## 7. 大模型自身能力使用边界

大模型能力可以用于：

- 自然语言理解。
- 追问表达。
- 结构化整理。
- 行业通用知识解释。
- 外部资料总结。
- 结果转业务话术。

大模型不能替代：

- 内部项目数据。
- 内部指标口径。
- 包状态。
- 联调结果。
- 上报检查。
- 权限判断。
- 资产写入。
- Case 写入。

## 8. 示例

### 今天天气如何

如果企业策略允许通用问答，Chat 可作为通用问题回答，并标注外部来源；不进入业务资产，不调用业务 Workflow。

### 2026 年投放最新方法论

属于行业通用知识与业务融合问题。可联网获取行业资料，再结合内部业务约束输出建议。不能伪造内部数据，不能进入一期核心闭环验收。

### ROI 怎么算

属于指标解释。必须优先调用内部口径库。外部解释只能作为补充，冲突时以内部门径为准。

### 这个包能投吗

属于包交付。Chat 必须先确认项目、媒体、包版本，并检查包交付 Workflow 是否 available。未接入真实 Workflow 时不能直接回答“能投”。

## 9. 代码、配置和提示词边界

路由能力不能全部写成 prompt，也不能全部硬编码。边界如下：

- 代码负责路由流水线顺序、权限检查、能力发现前置、失败闭环、Evidence / Trace / Asset / Case 写入和防假功能红线。
- 配置负责受控术语、别名、路由关键词、排除词、优先级、灰度、能力注册、slot schema、追问文案和 prompt 绑定。
- Prompt 负责结构化分类、追问表达和结果解释，但必须基于词典、规则、能力注册和工具返回事实。
- Workflow / Skill / MCP 负责真实业务执行，Chat 不能用自然语言假装执行。

当前实现中，`intent-router`、`intent-route-rules`、`context-compiler`、`slot-resolver` 和 `prompt-store` 已经具备部分基础，但主 Chat 链路还没有把受控术语词典、能力发现、规则配置、prompt 版本和全量可执行能力贯穿起来。因此第三阶段系统设计必须先补齐路由闭环，而不是直接扩展前台展示。
