# 会话上下文核对与遗漏补丁

## 1. 文档目的

本文件是在 PRD V2.2 文档包已生成后，继续按本轮会话上下文反查得到的补丁文档。

前 00-16 文档已经覆盖主体需求，但仍有一些确认点存在“写到了方向，但没有写成强约束”“写在某个场景里，但没有作为独立产品判断固化”“当前系统实现细节未完全点名”的问题。本文件用于补齐这些遗漏，后续系统设计和工程实施必须与本文件一起读取。

## 2. 兜底的目的与失败闭环

会话中曾明确讨论：“当系统无力完成时，什么算失败也闭环”。这不是普通客服兜底，也不是一句“我做不了”。

兜底的目的有四个：

1. 避免系统在能力不足时输出虚假确定性。
2. 最大化收集可执行信息，减少人工接手成本。
3. 把失败沉淀为 Case、Trace、Evidence 和后续能力建设样本。
4. 给用户明确预期：当前卡在哪里、谁处理、下一步是什么。

因此失败闭环必须遵守：

- 不要过早兜底。
- 先继续追问确认。
- 再尝试缩小范围。
- 多轮后仍无法完成，生成 Case。
- 告知用户等待处理。
- 记录已确认事实、未确认问题、已调用能力、失败原因、证据和建议处理角色。

这条规则适用于：

- 能力未接入。
- MCP / 智投接口不可用。
- 数据不完整。
- 上报检查失败。
- 联调失败。
- 异常诊断无法定位。
- 用户需求需要人工跟进。

## 3. 获取包与联调入口的产品纠偏

此前需求曾从“主动提问触发联调”调整为“获取包的联调状态和记录，打印出聊天截图等信息”。这一点在包交付文档中只写了状态和证据，但还需要明确：

包交付的一期主入口不是让用户直接操作联调，而是让用户问：

- 哪些包能投。
- 这个包为什么不能投。
- 这个包当前卡在哪。
- 新包是否已更新。
- 联调失败原因是什么。
- 历史检查记录在哪里。

系统返回时必须包含：

- 当前包状态。
- 上报检查报告。
- 联调结果。
- 联调日志。
- 联调截图或聊天截图等证据引用。
- 包下载地址或 APK。
- 历史包记录。
- 下一步建议。
- Case 入口。

这里的“聊天截图”不是前台装饰，而是证据材料的一种。它应作为 `EvidenceRef` 的一种来源，可以归类为：

- `integration_screenshot`
- `workflow_event`
- `user_confirmation`
- 或后续新增 `chat_snapshot`

工程设计阶段需要确认现有 Debug Automation、聊天记录和联调记录是否能生成截图、图片链接或可回放证据引用。

## 4. 单独触发联调的边界

包交付主链路中，联调是包交付 Workflow 的一部分。但用户也可能单独触发联调。

产品边界应定义为：

- 单独触发联调是可调用能力，但不是一级产品叙事。
- 单独触发联调前，必须确认上报检查已通过。
- 单独触发联调默认面向优化师角色。
- 不额外设计显式权限弹窗，但必须走现有会话权限和角色策略。
- 如果用户角色不是优化师，Chat 应按角色响应策略处理：只读解释、转 Case、或提示找有权限角色处理。
- 联调失败自动生成 Case。

当前系统已有 role profile 和会话权限处理基础，但主 Chat 链路是否完整贯穿角色仍需工程核查并补齐。这一点已经写入 `02` 和 `15`，此处强化为验收约束。

## 5. 包服务归属：Workflow、Skill、MCP 的拆分

会话中曾确认：联调发起可能来自包管理 Workflow，也可能来自 Skill / MCP 中的包服务。V2.2 的最终拆分应更明确：

- 包交付 Workflow：负责流程状态、等待、分支、旧包替代、Case 和业务结论。
- 包状态 Skill：负责封装包基础状态、版本、下载地址、历史记录。
- 上报检查 Skill：负责封装数据上报报告解析。
- 联调检查 Skill：负责触发或读取联调结果。
- MCP / 智投接口：负责真实上报报告、媒体后台更新、智投后台更新、联调日志、截图、APK / 下载地址。

如果开发已经提供“包管理 Workflow”，Chat 应优先绑定 Workflow。
如果开发只提供了包查询 Skill 或 MCP，Chat 可以展示部分能力，但必须标记为 `partially_available`，不能输出完整可投结论。

## 6. 我的资产入口位置

会话中确认：我的资产已经在左下角弹窗中有入口。

V2.2 不应把“我的资产”写成一个必须新增的全新入口。正确表述是：

- 保留当前左下角弹窗入口。
- 在现有入口基础上增强资产类型、项目字段、项目筛选、动态权限过滤和来源追溯。
- 在 Chat 结果卡中提供“保存到我的资产”“查看资产”“从资产继续处理”等动作。
- 不需要为了 V2.2 重新设计一个孤立资产后台。

后续前端实施时，必须复用当前入口形态，除非另有 UI 评审结论。

## 7. 知识库价值需要进入战略和需求两层

会话中曾追问“知识库哪些地方会用到，战略文档是否需要说明知识库的价值，需求文档肯定要写清楚”。当前文档已写指标解释和术语识别，但战略层价值还需要补强。

知识库在小乔智投中的价值包括：

1. 提高意图识别准确性
   通过术语词典、指标别名、项目词典和流程词，降低内部表达与行业表达差异带来的误路由。

2. 保证指标解释可信
   内部指标、字段、口径、数据源优先从内部口径库获取。

3. 降低外部知识污染内部事实
   外部联网只能补充行业知识，不能覆盖内部事实。

4. 形成组织记忆
   Case、失败原因、常见问法、口径差异、包交付问题可逐步沉淀为知识资产。

5. 支撑后续规则沉淀
   自动学习规则暂不定义为 Agent 自学习，而应先定义为规则、样本、案例和评测数据沉淀。

因此，知识库不只是指标解释功能的一部分，也是一层公共基础能力。后续系统设计应将其拆成：

- 路由前轻量词典。
- 口径解释库。
- 业务知识库。
- Case / 失败样本库。
- 评测样本沉淀。

## 8. 自动学习规则与成熟 Agent 框架问题

会话中曾问：“自动学习规则是什么，类似成熟模型网关？为什么是裸开发 agent，没有基于成熟框架？”

V2.2 当前不应承诺自动学习型 Agent。原因：

- 当前一期目标是可信服务闭环，不是自主学习 Agent。
- 自动学习如果没有审批、评测和回滚，容易污染路由规则和业务结论。
- 当前更缺的是能力注册、状态流、证据、权限和真实工具调用，而不是先引入复杂 Agent 框架。
- 是否采用成熟框架属于系统架构选型，应在系统设计阶段结合已有智投接口、Workflow、Skill、MCP 和连弩 Trace 再评估。

一期建议把“自动学习”改名并限定为：

- 路由失败样本沉淀。
- 追问缺失字段样本沉淀。
- Case 原因沉淀。
- 常见术语别名沉淀。
- 评测用例沉淀。
- 能力注册规则变更建议。

这些沉淀不能自动生效，必须经过评审、测试和发布。

## 9. 十大需求与五大主链路的关系

会话中指出“十大需求场景、五大主链路”是早期归纳，中间已经调整。V2.2 不应机械沿用早期说法。

当前应采用：

- 六个前台服务入口：看数据、拼报表、查异常、验流程、提需求、问逻辑。
- 三条后端闭环：数据与报表闭环、包交付与流程状态闭环、异常 / 需求 / 指标逻辑轻闭环。
- 两个公共基础：我的资产、低风险自动化任务中心。
- 十类需求场景作为展开维度，而不是强行绑定早期五大主链路。

其中“获取可用包与联调”应归入包交付闭环；“市场情报”归二期；“预测”归三期；“广告投放执行”归四期。

## 10. 前台体验不应暴露工程分层

PRD 文档需要写 Chat / Workflow / Skill / MCP 分层，但用户可见前台不应直接把这些工程词当成页面文案。

用户侧应看到：

- 当前进展。
- 检查结果。
- 证据来源。
- 下一步建议。
- 保存资产。
- 生成 Case。

而不是看到：

- Workflow 已运行。
- Skill 调用成功。
- MCP 返回。
- contract / schema。

这些词可以出现在开发文档、接口文档、Trace、评审记录里，不应直接作为真实用户页面文案。
