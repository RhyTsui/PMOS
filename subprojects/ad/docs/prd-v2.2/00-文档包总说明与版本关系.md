# 文档包总说明与版本关系

## 1. 为什么 V2.2 必须成为文档包

小乔智投已经不是单页 Demo，也不是从零开始的新需求。当前系统已经具备 Chat 入口、推荐问题、Agent 能力域、意图路由、上下文编译、Slot 解析、角色映射、问数真实执行、Workflow Task、报表模板、定时任务、Debug Automation、Trace、我的资产入口等基础。

但是这些能力并不等于产品闭环已经完成。当前真实执行最完整的是 `report_query` 问数链路，其他很多入口仍处于“能识别、能展示、能路由，但不一定有真实中间服务承接”的阶段。如果继续只写“用户问什么、系统答什么”的 PRD，很容易让前台做出假功能，和开发提供的 Workflow / Skill / MCP 对接不上。

因此 V2.2 必须拆成文档包，分别回答：

- 产品为什么做，阶段边界是什么。
- 当前系统已经实现了什么，哪些要保留，哪些要纠偏。
- Chat、Workflow、Skill、MCP / 智投接口分别负责什么。
- 受控术语词典、路由规则、Prompt、能力注册和真实执行如何形成闭环。
- 每个需求场景的用户流程、系统流程、数据模型、状态流转和验收标准是什么。
- 哪些是一期 P0，哪些只是后续规划。

## 2. 与 V2 / V2.1 的关系

V2 的价值是提出了需求场景，但问题是更像场景清单，缺少对象模型、状态机、权限、证据、验收和系统边界。

V2.1 的价值是开始补对象、流程和多角色视角，但仍然容易把 Chat 产品体验、中间服务执行能力、MCP 原子能力混在一起。

V2.2 的修订目标是：

- 保留 V2 / V2.1 的业务场景，不再重新发明需求。
- 把当前已经实现的系统能力纳入正式需求。
- 把本轮确认的分层产研模式写入核心定义。
- 把每个需求拆成 Chat 责任、Workflow 责任、Skill 责任、MCP / 智投接口责任。
- 把权限、资产、Trace、Evidence、Case、状态流转作为统一底座。

## 3. 当前产研模式

当前产研模式不是“Chat 里直接实现全部业务逻辑”，而是：

1. 开发或业务系统提供 MCP / 智投接口，作为真实数据和原子动作来源。
2. 开发封装 Skill，把业务能力变成稳定可调用服务。
3. Workflow 编排多步骤流程，管理状态、等待、失败、证据和结论。
4. Chat 绑定能力，负责用户对话、追问、调用、解释和沉淀。
5. 调试通过后，能力进入注册表，成为可被路由调用的正式能力。

这意味着 PRD 不能写成“Chat 直接判断包可投”“Chat 直接完成联调”“Chat 直接生成正式报表”。Chat 只能调用真实能力并解释真实结果。

## 4. 文档阅读顺序

建议阅读顺序：

1. 先读 `01-战略与产品定位修订版.md`，确认产品路线。
2. 再读 `02-当前系统实现盘点与纠偏.md`，确认不是推倒重来。
3. 再读 `03-系统分层责任与产研对接契约.md` 和 `04-能力注册与意图路由设计.md`，确认系统边界。
4. 再读 `05-项目角色权限与跨项目设计.md`，确认所有场景的安全前提。
5. 再读 `06` 到 `09`，进入具体需求场景。
6. 最后读 `10` 到 `15`，作为研发建模、状态、Trace、验收和实施依据。
7. 进入第三阶段系统设计前，必须读 `18-意图路由知识库与能力闭环设计准入评估.md`，确认路由、知识库调用、Prompt 和能力发现已经具备设计准入条件。
8. 单个复杂需求域需要单独阅读专项 PRD，例如 `19-个人记忆与知识库用户隔离需求设计.md` 和 `20-对话路由需求PRD.md`。

## 5. 关键原则

V2.2 之后，所有设计和实现都必须遵守：

- Chat 不做业务假执行。
- 意图命中不等于能力完成。
- 受控术语词典必须以可调用能力进入路由前置链路，不能只作为散落知识。
- 能力发现必须早于 slot 补齐和执行追问。
- Prompt 不能替代能力注册、权限检查和真实 Workflow / Skill / MCP 调用。
- 能力未注册或未接入时，不能输出已完成口吻。
- 内部项目数据只查内部。
- 内部指标口径优先查内部口径库。
- 外部联网只作为行业通用知识和方法论补充。
- 包交付必须单项目。
- 定时报表是一期 P0。
- 市场情报是二期。
- 预测是三期。
- 受控自动化投放执行是四期。
- Trace 和评测在连弩平台，小乔只发送结构化记录。
