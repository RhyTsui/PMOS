# 异常排查、需求沟通与指标解释 PRD

## 1. 总体定位

异常排查、需求沟通和指标解释属于一期轻闭环。它们不一定都能自动解决，但必须做到：

- 正确识别用户意图。
- 自动补齐上下文。
- 信息不足时追问。
- 调用已接入的真实能力。
- 输出证据、结论和下一步建议。
- 无法完成时生成 Case。

## 2. 异常排查

### 2.1 用户目标

用户希望快速知道异常原因，而不是手动在多个系统中查数据、查包、查联调和问人。

典型问题：

- 为什么没量？
- 为什么没回传？
- ROI 为什么掉了？
- 数据为什么对不上？
- 联调为什么失败？

### 2.2 Chat 行为

Chat 需要识别异常类型，并提取项目、媒体、活动、包、时间等字段。信息不足时只追问影响诊断的关键字段。

Chat 不直接编造异常原因。它必须调用异常诊断 Workflow 或诊断 Skill。

### 2.3 Workflow / Skill 行为

异常诊断 Workflow 可以调用：

- 数据查询 Skill。
- 包状态查询 Skill。
- 联调检查 Skill。
- 媒体状态查询。
- 历史基线查询。
- Case 生成 Skill。

如果证据充分，返回最可能原因、置信度、已检查项、证据和下一步建议。
如果证据不足，返回 `waiting_input` 或 `partial`，由 Chat 继续追问。

### 2.4 失败闭环

系统无力完成时，不应一次失败就兜底。建议规则：

1. 第一次缺信息：追问。
2. 第二次仍不充分：缩小排查范围。
3. 多轮后仍无法定位：生成 Case。

Case 必须包含：

- 原始问题。
- 已确认事实。
- 未确认问题。
- 已调用能力。
- 返回结果。
- 失败原因。
- Evidence。
- 建议处理角色。

## 3. 需求沟通

### 3.1 用户目标

用户经常提出模糊需求，例如：

- 帮我提一个数据需求。
- 这个报表以后想固定看。
- 帮我整理一个素材需求。
- 这个包处理流程帮我跟一下。

系统目标不是直接假装完成，而是把模糊需求整理成可执行事项。

### 3.2 Chat 行为

Chat 需要识别需求类型，提取背景、目标、对象、期望产出、时间和优先级。缺字段时追问。

### 3.3 Workflow 行为

需求协同 Workflow 负责：

- 生成结构化需求草案。
- 等待用户确认。
- 用户确认后生成 Case 或任务。
- 记录原始对话和整理后的需求。

### 3.4 需求类型

一期支持：

- 数据需求。
- 报表需求。
- 素材需求。
- 包处理需求。
- 异常协查需求。
- 产品能力建议。

复杂需求可以进入 Case，不要求一期自动分发到所有业务系统。

## 4. 指标解释

### 4.1 用户目标

用户希望理解指标、口径、字段和内部术语。

典型问题：

- ROI 怎么算？
- 激活口径是什么？
- 回收为什么和媒体后台不一样？
- 内部说的某个词是什么意思？

### 4.2 知识来源顺序

指标解释必须优先接内部口径库：

1. 内部口径库。
2. 内部知识库。
3. 外部资料补充。
4. 大模型通用解释。

外部联网只作为补充，不能覆盖内部口径。内部与外部冲突时，内部优先，并明确提示差异。

### 4.3 路由前知识策略

路由前可以做轻量术语识别，例如内部简称、指标别名、项目词典、媒体词典。
不建议路由前做重型 RAG。正式检索由口径解释 Skill 负责。

受控术语词典应作为路由前置归一化能力调用。它只负责把“回收”“激活”“付费”“成本”“ROI”“数据不对”等表达映射到内部标准词和歧义项，不负责生成指标最终解释。最终口径解释仍由内部口径库和指标解释 Skill 返回。

### 4.4 输出要求

指标解释必须展示：

- 内部口径。
- 适用范围。
- 数据来源。
- 计算方式。
- 与外部行业解释的差异。
- Evidence。
