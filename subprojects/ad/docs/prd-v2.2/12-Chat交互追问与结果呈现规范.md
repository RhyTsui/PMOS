# Chat 交互、追问与结果呈现规范

## 1. Chat 标准处理流程

每轮对话应按以下流程处理：

1. 接收用户消息。
2. 标准化表达。
3. 编译上下文。
4. 轻量术语识别。
5. 路由意图。
6. 查询能力注册表。
7. 权限预检。
8. 检查必填槽位。
9. 判断是否追问。
10. 调用 Workflow / Skill。
11. 展示过程状态。
12. 展示结果。
13. 提供下一步建议。
14. 记录 Trace。

## 2. 什么时候必须追问

必须追问的情况：

- 查数缺项目、时间或指标，且无法从上下文推断。
- 定时报表缺项目、频率或数据延迟策略。
- 包交付缺项目、媒体或包版本。
- 异常排查缺项目、异常时间或异常对象。
- 需求沟通缺目标、对象或期望产出。
- 指标解释中术语歧义会影响口径。
- 用户表达无法判断基本意图。

## 3. 什么时候不应追问

不应追问的情况：

- 当前项目已明确。
- 最近上下文已经确认。
- 时间可用默认值并且风险低。
- 用户只是问通用概念。
- 能力未接入，追问不会改变结果。

能力未接入时，应先说明边界，再决定是否整理信息生成 Case。

## 4. 追问分层

路由前追问用于确认基本意图。
路由后追问用于补齐必填槽位。
Workflow 运行中追问用于补齐执行中发现的业务信息。

所有追问都由 Chat 承载，但追问字段可以来自路由器、能力注册表、Workflow 或 Skill。

追问之前必须先做能力发现。能力未接入时，不应继续追问一批执行字段，因为这些字段不会改变“不能执行”的事实。此时 Chat 应说明边界，整理已有事实，并在需要时生成 Case。

路由前追问只问会影响基本意图判断的问题。路由后追问只问能力 required slots。Workflow 运行中追问只问下游返回的 `waiting_input` 字段。

## 5. 结果结构

业务结果必须统一包含：

- 一句话结论。
- 当前状态。
- 关键事实。
- Evidence。
- 下一步建议。
- 资产操作。
- Case 操作。
- Trace 引用。

## 6. 包交付结果卡

包交付结果应展示：

- 项目。
- 媒体。
- 包名。
- 版本号。
- 流程状态。
- 业务结论。
- 下载地址或 APK 地址。
- 上报检查结果。
- 联调检查结果。
- 风险提示。
- Evidence。
- 历史包入口。
- Case 入口。

## 7. 报表结果卡

报表结果应展示：

- 项目范围。
- 时间范围。
- 指标。
- 维度。
- 数据更新时间。
- 数据完整性。
- 报表预览。
- 保存资产。
- 生成模板。
- 创建定时报表。

## 8. 异常诊断结果卡

异常诊断结果应展示：

- 异常类型。
- 诊断结论。
- 置信度。
- 已检查项。
- 未确认项。
- Evidence。
- 下一步建议。
- 生成 Case。

## 9. 指标解释结果卡

指标解释结果应展示：

- 内部口径。
- 计算方式。
- 适用范围。
- 数据来源。
- 外部补充说明。
- 冲突提示。
- Evidence。

## 10. 能力未接入口径

能力未接入时不能说“已查询”“已检查”“已完成”。

推荐口径：

> 当前还没有接入可执行服务，不能直接给出最终结论。我可以先帮你整理已知信息，并生成 Case 继续跟进。

## 10.1 Prompt 使用边界

Chat 可以使用 prompt 生成追问和结果表达，但 prompt 必须遵守以下边界：

- 术语归一化 prompt 只能使用受控术语词典，不能新增标准词。
- 意图分类 prompt 必须读取可用能力列表，不能把未接入能力判断成可执行。
- 追问 prompt 一次最多问 1-2 个关键问题，不能重复询问上下文已有信息。
- 结果解释 prompt 只能解释 Workflow / Skill / MCP 返回事实，不能补造内部数据、包状态、联调结果和指标口径。
- 指标解释必须先接内部口径库；外部联网只能作为补充，并且必须标注来源和冲突处理。

## 11. 无权限口径

无权限时应明确：

> 你当前没有该项目权限，无法查看相关数据。如果需要查看，请联系项目管理员开通权限。

跨项目内容部分无权限时：

> 这条结果包含多个项目，其中部分项目因权限变化不可见，以下仅展示你当前有权限的部分。
