## 二、五大严峻问题及根因

### 问题1：报表查询超时率 49.5%（48条）

**现象**：MIG-001 到 MIG-077 大量报表查询用例触发超时（80-125s），无 SSE 响应返回。

**根因分析**：
1. **MCP 报表工具执行超时**：`report-query-orchestrator.ts` 中 `executeReportQueryStep` 调用 MCP 数据服务，但该服务在复杂查询（跨日期范围、多维度）时未能在 120s 内返回结果。
2. **无超时保护机制**：chat route 的 stream 在等待工具执行期间没有发送心跳或 phase 事件，导致客户端检测不到活跃连接。
3. **长链路叠加**：路由判断 → 能力发现 → MCP 调用 → 知识库回退，每步都有网络开销，但无并行优化。
4. **从 MIG-065 开始几乎全部超时**：说明系统在长时间运行后可能存在内存或连接池泄漏，导致后续请求全部卡死。

**trace 佐证**：超时用例全部无 traceId（未进入到 done 事件），说明请求在 MCP tool execution 阶段阻塞。

### 问题2：报表工具未被选中（"候选工具还不能直接完成"）— 26条

**现象**：系统返回 "当前候选工具还不能直接完成这次查询，已整理能力缺口"。

**根因分析**（MCP 工具存在但未被用上）：
1. **`selectCapabilityForRequirement` 匹配过严**：`buildDataCoverage()` 对 dimensions/metrics/filters 做严格全覆盖检查，用户查询中包含的维度/指标不在 capability 的 `supports` 配置中时，`dataCoverage.covered = false`，导致 `selected = undefined`，即使工具实际可以执行。
2. **`scoreCapabilityMatch` 分数为 0**：`inferRouteTerms` 只从 tool name 拆分和固定域映射生成 route_terms，tool.description 中的中文业务词未被利用，导致评分命中不了有效项。
3. **`hasStrongReportQueryIntent` 排除过激**：包含"下降"、"异常"等词的查询直接被判定为非报表意图（返回 false），但用户可能只是在描述数据背景。
4. **自动推断链路不充分**：`buildReportCapabilityManifest` 从 tool 的 name/description/input_schema 自动推断 route_terms、report_domains 等，但推断规则覆盖有限（如 tool description 中的中文关键词、schema property keys 暗示的业务领域未被识别）。

**修复**：
- `selectCapabilityForRequirement` 增加 partial_match 选择逻辑
- `scoreCapabilityMatch` 增加 description 文本匹配和 baseline score
- `inferRouteTerms` 从 description 提取中文词、从 property keys 推断业务域
- `hasStrongReportQueryIntent` 区分纯诊断和包含数据需求的查询

### 问题3：参数缺失阻断执行（"还需要补充…后才能继续"）— 12条

**现象**：返回 "还需要补充retentionType后才能继续" 或 "还需要补充应用类型解析输出后才能继续"。

**根因分析**（用户意图完整时不应阻断）：
1. **`missingRequiredKeysBeforeCall` 一律阻断**：当前逻辑直接将 `tool.input_schema.required` 中空值字段全部视为阻断条件，不区分"用户意图核心参数"和"有合理默认值的参数"。
2. **默认值未被应用到对应场景**：`adapterDefaults()` 根据 `question_type` 选择 schema_adapter 填充默认值。如果 `inferQuestionTypeFromTerms` 未将查询分类为 'retention'，则 retention 的默认 `retentionType: 'REG_RETENTION'` 不会被填入。
3. **应以用户意图是否完整为判断标准**：用户说"看下留存"时意图已完整（查留存大盘），缺少 `retentionType` 应使用工具推荐默认值（设备留存/注册留存）执行，而非阻断追问。

**修复**：
- 新增 `classifyAndFillMissingKeys` 将缺失参数分为 critical（appId 等用户意图核心）和 auto-fillable
- Auto-fillable 参数从 policy adapters 和 tool schema 的 enum/default 自动填充
- 只有 critical 参数缺失才阻断追问

### 问题4：模型服务不可用（2条直接失败 + 间接影响通用回答）

**现象**：MIG-000 "你好"、"cost字段是什么意思" 返回 "当前模型服务暂时不可用，无法完成这次普通对话回答"。

**根因分析**（`route.ts:1451` → `model_unavailable`）：
1. **模型调用失败触发 fallback**：`chatAnswerAssist.participation.status === 'failed_fallback'`，模型 API 调用失败。
2. **可能的模型配置问题**：测试环境（10.236.14.27:8002）的模型 API Key 过期、配额耗尽、或网络不通。
3. **无重试机制**：模型调用失败时直接返回 fallback 模板消息，未尝试 retry 或 fallback 模型。

---

### 问题5：数据时间错位（日期解析错误）

**现象**：MIG-027/030/031/034/059 等用例，查询历史日期（如 2026-03-25、2026年2月），但返回 2026-06-09 当天数据。

**根因分析**：
1. **日期解析未生效或被覆盖**：MCP 报表工具收到的日期参数为当天日期（2026-06-09）而非用户指定日期。
2. **可能是 slot 解析器提取了日期但 MCP 调用时使用了默认值**：工具调用层面存在日期参数覆盖 bug。
3. **或 MCP 服务忽略了日期参数**：从返回的数据看，MCP 总是返回"今天"的数据。

## 八、结论

**当前状态：系统不具备上线条件。** 核心数据查询能力（占测试集 90%+ 的场景）全部失败，根因集中在：

1. MCP 报表工具存在但选择流程未能匹配（`selectCapabilityForRequirement` 严格全覆盖 + `scoreCapabilityMatch` 评分不足）
2. 参数缺失阻断逻辑过于严格（有默认值的参数也一律阻断，不区分用户意图是否完整）
3. 规则引擎业务术语覆盖不全（retention/roi/hour 的 include_terms 和 route_terms 自动推断不充分）
4. 模型服务连接不稳定
5. 超时保护机制完全缺失
6. 日期参数传递存在 Bug

建议 **至少完成 Phase 1 + Phase 2 修复，通过 Round 2B 验证（通过率 > 60%）后，再评估上线时间线**。
