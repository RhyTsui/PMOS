  # Chat Presentation Layer 完整上线计划

  ## Summary

  不新增平行的 Presentation OS，直接在现有 Enterprise AI Chat OS 下补齐 Chat Presentation Layer：把消息返回展示域收口为 SemanticResultContract /
  MessageContract -> regions[] -> componentBinding -> Component Registry -> Renderer。
  本次目标不是“再做一个页面”，而是把正文、结果、过程与依据全部改成契约驱动渲染，删除 ChatContainer 里的临时 preview strip、旧式手工拼接和渲染层兼容
  兜底，形成可上线的统一消息展示架构。

  ## Key Changes

  ### 2) 统一契约模型：正文、结果、过程与依据都从总纲派生

  - SemanticResultContract 继续作为最终业务结果真源，不再新增平行 UI schema。
  - screenType 负责页面级语义与默认 region 排序，不负责选具体组件。
  - regions[] 继续作为唯一结构化承载；如需更细颗粒度，只允许作为内部 block 结构，不进入旧式手工拼接路径。
  - componentBinding 作为唯一渲染挂载入口，负责把 region/block 绑定到具体 renderer。
  - MessageDisclosureView 继续作为过程与依据唯一消费对象，不允许正文/结果层直接读取 tool_calls / raw_result / process_events 来拼 UI。
  - ActionContract / EvidenceRef / SourceRef / RuntimeRef 继续保持分层，禁止 renderer 私有定义这些结构。

  ### 3) 消息渲染链路重做：ChatContainer 退回壳层，正文改为区域化渲染

  - ChatContainer 只保留消息列表编排、消息壳、动作挂载、抽屉挂载，不再做业务结果重组。
  - 删除 DisclosurePreviewStrip 这类临时预览条，不保留“正文里先塞一个轻量过程入口”的过渡方案。
  - MessageSurface 只负责消息 frame + region tree 渲染，不再从 workflow_result / report_query_result / structured_payload 反推业务结论。
  - MessageActionBar 只负责消息级动作入口，不承载正文结果。
  - MessageDisclosureDrawer 继续作为侧边过程与依据面板，不并入正文渲染。
  - 旧的兼容读法在渲染路径里全部清掉：正文/结果展示不再直接读取 workflow_result / report_query_result / tool_calls / process_events / raw_result。

  ### 4) 组件注册与批量渲染：把现有部署的组件库直接接入注册矩阵

  - registry-spec.md 定义统一注册、解析、validate、fallback、telemetry 规则。
  - autonomous-rendering-engine.md 定义从 SemanticResultContract -> regions -> componentBinding -> registry -> renderer -> React tree 的声明式管线。
  - 已部署的表格、图表、Markdown、运行态、动作、空态、错误态组件库不逐个散写在页面里，而是通过 registry preset 批量注册。
  - 统一补齐并收口这些 renderer family：
      - markdown-renderer
      - data-visualization-renderer
      - runtime-renderer
      - action-renderer
      - empty-error-state-renderer
  - data-visualization-renderer 作为唯一业务图表/表格入口，内部再按数据形态选择已部署的具体实现。
  - markdown-renderer 只处理正文类内容，不混表格、图表、动作、来源解释。
  - runtime-renderer 只处理运行态摘要与过程可视化，完整 trace 仍归 disclosure / runtime 协议。
  - 所有 renderer 必须具备 validate、fallback、性能声明和 telemetry，不允许页面层临时判断组件类型。

  ### 5) UX / 体验 / 性能：把总纲 UI 规范真正落到消息展示域

  - screen-type-spec.md 补齐页面类型与布局策略：对话、分析、报告、仪表盘、指标解释、工作流结果、错误/空态、权限受限等。
  - streaming-state-spec.md 补齐流式输出、打字机节奏、partial / recovered / failed / paused 等状态展示。
  - virtualization-spec.md、performance-spec.md、responsive-system.md 补齐长会话、大表格、长 markdown、移动端抽屉化、滚动稳定性和性能预算。
  - feedback-system.md、progressive-disclosure-ux.md、result-consumption-ux.md 补齐反馈、逐级披露、结果继续追问、证据查看、导出等交互。
  - 视觉系统现有规范只作为 token 来源，不在这次任务里重做风格。

  ### 6) 历史包袱清理：只保留规范入口，不保留展示兼容

  - 删除或收口所有只为旧展示形态服务的分支、旧卡片和旧重组逻辑。
  - ReportQueryResultCard、旧 ResultPanel、旧报表兼容卡如果仍存在，只能作为 renderer-backed region 的实现细节，不能继续在页面里重复承载结果。

  # 正文渲染架构（当前态）

  ## 1. 定位

  正文渲染不是单独的文案展示层，而是 AI 会话结果的主承载层。

  它负责把一次对话的输出拆成三类可见内容：

  - 正文：给用户直接看的结论、摘要、说明
  - 结果：结构化数据、图表、表格、下一步动作
  - 过程与依据：来源、执行、字段、质量检查、原始信息

  当前实现上，这三类内容已经开始分层，但还没有完全做到由总纲契约自动驱动，仍存在少量硬编码入口和过渡组件。

  ---

  ## 2. 当前链路

  ```txt
  Message
  → MessageSurface
  → MessageContract / workflow_result / semantic_result
  → 正文展示
  → 结果展示
  → MessageActionBar
  → MessageDisclosureDrawer
  → DisclosurePanelRenderer

  对应到当前代码，主要入口在：

  - frontend/src/src/components/cognitive/ChatContainer.tsx
  - frontend/src/src/components/cognitive/MessageActionBar.tsx
  - frontend/src/src/components/cognitive/MessageDisclosureDrawer.tsx
  - frontend/src/src/renderers/disclosure/DisclosurePanelRenderer.tsx
  - frontend/src/src/contracts/semantic/semantic-result-contract.ts

  ———

  ## 3. 三层正文模型

  ### 3.1 正文层

  正文层只负责“用户第一眼看到的自然语言内容”。

  当前来源优先级：

  1. MessageContract.answer_markdown
  2. message.content
  3. 兼容性的 workflow_result.answer

  当前渲染位置：

  - MessageSurface
  - MarkdownRenderer
  - 长文本折叠与展开逻辑

  当前规则：

  - 正文只保留短摘要、结论、说明
  - 工程字段、工具调用、原始 JSON 不应直接进正文
  - 超长内容会自动折叠
  - 对消息正文中的 inline 来源段，会进行清理或剥离

  当前实现里，正文渲染仍然有一部分硬编码逻辑在 MessageSurface 内，例如：

  - 长文折叠
  - inline 来源段剥离
  - 文本类型区分渲染

  这些逻辑是合理的，但还没有完全上升为总纲里的统一正文协议。

  ———

  ### 3.2 结果层

  结果层负责“正文下面的结构化结论”。

  它承载的是已经抽象过的业务结果，而不是执行细节。

  当前输入来源：

  - MessageContract.visualizations
  - MessageContract.business_summary
  - MessageContract.next_actions

  当前渲染位置：

  - SafeDataVizRenderer
  - BusinessSummaryCard
  - ActionsRenderer

  当前目标：

  - 表格、图表、下一步动作属于结果层
  - 结果层和正文层要分离
  - 结果层不再回写为正文里的重复说明

  当前状态：

  - 已经有 MessageContract 作为结果真源
  - 但页面里仍有少量兼容型逻辑，过去会从 workflow_result 或 report_query_result 反推结果
  - 这部分正在收口到 message_contract

  ———

  ### 3.3 过程与依据层

  过程与依据层负责“为什么得出这个结果”。

  当前投影对象是：

  - MessageDisclosureView

  当前渲染入口：

  - frontend/src/src/components/cognitive/MessageDisclosureDrawer.tsx
  - frontend/src/src/renderers/disclosure/DisclosurePanelRenderer.tsx

  当前页签结构：

  - 概览
  - 执行
  - 依据
  - 字段
  - 质量
  - 原始信息

  这个层的职责是：

  - 展示来源，不展示内部实现细节
  - 展示执行，不把执行细节塞回正文
  - 展示字段，不靠字段名硬猜业务含义
  - 展示原始信息，但必须脱敏并受权限控制

  ———

  ## 4. 当前正文渲染职责边界

  ### 4.1 MessageSurface

  MessageSurface 是正文的主渲染器。

  它当前负责：

  - 根据消息角色选择展示样式
  - 识别长文本并折叠
  - 渲染 Markdown
  - 剥离正文里的 inline 来源段

  它不应该负责：

  - 结果图表生成
  - 来源面板组装
  - 执行链拼装
  - 业务字段解释

  ———

  ### 4.2 MessageActionBar

  MessageActionBar 是正文的动作入口补充。

  它当前负责：

  - 引用
  - 过程与依据
  - 复制链接
  - 调用链

  它的职责不是结果内容本身，而是让用户从正文快速跳到下一步。

  当前状态里，它已经从纯菜单入口，升级成了带“过程与依据”按钮的可见入口。

  ———

  ### 4.3 Disclosure Preview Strip

  消息体内现在有一条轻量的过程预览条。

  它的作用是：

  - 让用户在正文下方直接看到这条结果里有哪些来源、执行、下一步和能力
  - 作为抽屉的前置入口
  - 减少“必须先去右侧面板”的跳转成本

  它属于过渡态入口，作用明确，但不应成为长期唯一方案。长期目标还是由总纲契约驱动区域布局。

  ———

  ## 6. 当前还在硬编码的地方

  这部分是你后面要按总纲继续收口的重点。

  ### 6.1 正文内的临时入口

  当前 ChatContainer 里仍然直接插入了：

  - DisclosurePreviewStrip
  - MessageActionBar
  - MessageDisclosureDrawer

  这意味着正文区的某些布局仍然是组件级硬编码，而不是完全由契约生成。

  ### 6.2 结果与过程的并列挂载

  当前页面里，结果层和过程与依据层是并列挂载的：

  - 正文消息里有结果摘要
  - 右侧面板里有过程与依据
  - 消息下方有预览条

  这已经能用，但还不是最终的总纲态。

  ### 6.3 旧兼容入口仍存在

  虽然已经收口了很多旧逻辑，但系统里仍然存在兼容读取：

  - workflow_result
  - report_query_result
  - tool_calls
  - process_events

  这些现在主要留在适配层，不应继续扩散到渲染层。

  ———

  ## 7. 按总纲继续完善时的目标形态

  未来正文渲染应收敛成三块：

  SemanticResultContract
  → 正文区域
  → 结果区域
  → 过程与依据区域

  推荐的长期原则：

  1. 正文只负责自然语言摘要
  2. 结果只负责结构化呈现
  3. 过程与依据只负责来源、执行、字段、质量和原始信息
  4. 所有区域都应该通过 regions[].componentBinding 映射
  5. ChatContainer 只做编排，不做业务解释
  6. MessageSurface 只做正文渲染，不做结果再组装
  7. MessageDisclosureView 作为过程与依据的唯一消费对象

  ———

  ## 8. 建议的正文总纲落点

  如果你要把正文按总纲继续完善，下一步应把正文从“消息组件渲染”升级为“契约区域渲染”。

  也就是：

  - 正文区使用 screenType + regions + componentBinding 决定布局
  - 正文摘要、表格、图表、证据、动作各自进入不同 region
  - MessageSurface 逐步退化为 markdown-result 的默认渲染器
  - DisclosurePreviewStrip 作为过渡态，后续可以并入统一区域布局
  - 右侧 MessageDisclosureDrawer 继续保留为详细过程面板，而不是正文的唯一入口

  ———
