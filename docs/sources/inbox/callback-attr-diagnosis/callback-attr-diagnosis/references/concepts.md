# Common Concepts

这些概念在 Android/iOS 两边都出现，但证据权重和解释口径不同。统一 skill 必须先做平台分支，再决定这些证据怎么用。

## 基础证据

- `attr-res`
  - 表示归因结果已经产出。
  - 通俗讲：系统已经认为“这次激活/注册/付费应该算到某次广告点击上”。

- `feedback-res`
  - 表示 API 回推结果已经沉淀。
  - 通俗讲：不是只算出来了，而且已经形成了“要不要给媒体回推”的结果记录。

- `sdk_income`
  - 表示 SDK 侧的回推任务、发送记录或闭环轨迹。
  - 通俗讲：更偏“SDK 这条链到底有没有动起来”。

- `804`
  - 某类 SDK/闭环回执参考状态。
  - 通俗讲：它像“回执/回声”，能证明某些下游动作发生过，但不能脱离平台语义单独当结论。

- `finishedInit`
  - 融合归因相关配置开关。
  - 通俗讲：表示这条链路是否要求设备初始化侧的身份信息足够完整，再决定怎么归因。

## 业务概念

- `虚拟回推 / 虚拟回推参考`
  - 在当前系统里，更适合理解成“没有完全走 Android 那种真实 SDK 回推闭环，但系统仍会产出一层可用于解释激活闭环是否成立的参考证据”。
  - 在 iOS `ACTIVATION` 场景里，常见主链是 `attr-res -> d_c_init_i -> 虚拟激活/804参考`。
  - 它的意义不是替代真实回推结果，而是告诉排查者：
    - 激活归因可能已经成立
    - SDK 初始化链路可能已经到位
    - 但不能仅凭这层参考就断言“媒体一定已经收到最终回推”

- `融合归因`
  - 表示归因不只看单一标识，而是综合多个设备身份字段和上下文做命中判断。
  - 在当前数据解释里，iOS 重点关注：
    - `idfv`
    - `caid1`
    - `caid2`
    - `os_version`
    - `app_version`
    - `sdk_version`
  - 通俗讲：不是“只靠一个设备号命中”，而是“多组身份和环境信息一起判断这次归因像不像同一个人”。

- `精准归因`
  - 更像身份字段充分、命中证据直接的归因。
  - 通俗讲：证据比较硬，能较明确解释“为什么是这次点击命中”。
  - 在工具或样本解释里，通常伴随较清晰的身份字段和点击链匹配。

- `模糊归因`
  - 更像身份不完整、需要更多规则或融合信息兜底的归因。
  - 通俗讲：系统认为“高度疑似是它”，但解释链没那么硬。
  - 这类场景更依赖平台规则、lookback、融合字段和配置判断，不适合只看最终 `attr-res` 数量。

## 平台化理解

- Android
  - `804` 往往更接近主闭环证据之一。
  - `PAY` 常能沿着 `sdk_income + 804` 继续解释。

- iOS
  - `ACTIVATION` 更偏 `attr-res -> d_c_init_i -> 虚拟激活/804参考`
  - `REGISTER / PAY / KEY_ACTION` 更偏 `attr-res -> feedback-res`
  - 不应把 Android 的 `PAY -> d_c_order_i -> 804` 直接迁移过来
