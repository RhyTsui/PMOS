本轮任务：开放式回答链路 Planner-first 收口治理审计与完整方案输出

本轮性质：只读审计 + 架构方案 + Prompt 方案 + 变量治理方案 + 工程实施拆分。

本轮不要修改任何代码、配置、Prompt、runtime JSON、文档、测试文件，不要提交，不要打补丁。即使发现一行可修的问题，也不得直接修。必须先输出完整审计结果、目标架构、Prompt 模板、变量治理方案、P0/P1 实施计划和验收命令，最后等待用户确认。

本轮目标不是新增功能，而是把开放式问题回答链路从旧范式彻底收回到 Planner-first + Evidence-first 主链路：

UserMessage
→ RequestUnderstanding
→ PlannerOutput
→ ContractPreflight
→ KnowledgeDiscovery / CapabilityDiscovery
→ ExecutionPolicy
→ EvidenceCollection
→ EvidenceLedger
→ AnswerComposition
→ ContractSafety
→ ResponseProjection

核心问题定义：

当前卡点不是“不能提交代码”，而是开放式回答链路仍残留旧范式：

1. 早期规则硬编码关键词。
2. 后来改成纯上下文聚合。
3. 又补了提示词里的关键词、证据、路由约束。
4. 现在又发现部分“蒸馏规则”仍用关键词判断。
5. 知识库检索、工具调用、实时搜索、模型自有知识之间的边界还没有完全用 Contract / Evidence 收口。
6. 某些回答可能跳过 EvidenceLedger，直接由 chat_answer / knowledge_answer / fallback_answer / report fallback 生成 answer_markdown。

这些方式看起来比硬编码更优雅，但本质仍可能绕开 Planner / Contract / Evidence 主链路。因此，本轮治理对象不是“关键词”本身，而是所有可能绕开 Planner-first 主链路的隐形决策权，包括：

* 关键词路由
* 正则路由
* 蒸馏规则
* prompt if/else
* 上下文聚合隐式分类
* 知识库检索结果直接生成答案
* 知识库 source_count=0 后 fallback 编造
* 工具候选由 LLM 直接拍板
* fallback early return
* Composer 自行判断能力
* answer_markdown 直接生成
* sourceRefs / evidenceRefs / evidence_mode 缺失但仍输出答案
* 主消息泄露 query_contract、slot_validation、tool_args、raw params、trace、prompt

一、业务背景与架构边界

本项目定位是：

通用 Chat 服务底座 + 广告业务 Domain Pack + 工具/MCP/知识库/Web/File 能力接入。

它不是广告报表专用脚本系统，也不是把广告业务规则写死进通用 Chat Core。

广告业务 Chat 的典型场景包括但不限于：

1. 普通开放式问答。
2. 内部知识问答：指标口径、投放规范、归因逻辑、平台文档、项目资料、历史复盘、操作手册。
3. 实时公开信息：天气、行业资讯、媒体公告、政策更新、公开网页。
4. 问数与报表：消耗、激活、ROI、留存、付费、分媒体/分项目/分素材/分日期查询。
5. 数据分析：趋势、汇总、排名、对比、诊断、路径分析。
6. 数据诊断：ROI 下滑、回传异常、归因差异、数据延迟、权限缺失、口径差异。
7. 包与联调：包列表、包详情、下载地址、联调状态、步骤截图、日志。
8. 文件与 Excel：上传模板、识别表头、按模板取数、多表拼接、导出 artifact。
9. 自动化任务：定时日报、ROI 异常监控、投前包检查、条件触发提醒。
10. 需求与协作：需求收集、PRD 草稿、评审纪要、任务拆解。

这些业务语义可以作为 Domain Pack / Capability Manifest / Knowledge Dataset / Entity Catalog / Prompt Seed 的配置输入，但不得硬编码到通用 Chat Core。

通用 Chat Core 只识别通用概念：

* task_type
* answer_mode
* evidence_requirements
* capability_hints
* knowledge_source_hints
* sourceRefs
* evidenceRefs
* actionRefs
* semantic_result
* contract_status
* response_projection

广告业务知识应来自：

* Domain Pack
* Knowledge Base Dataset
* Entity Catalog
* Metric / Dimension Catalog
* Capability Manifest
* MCP Tool Contract
* Prompt Store
* Admin Runtime Config

不得来自：

* 通用 Chat Core 里的 if/else
* 通用 Chat Core 里的关键词表
* Composer prompt 里的业务路由逻辑
* UI 展示层兜底
* fake golden fixture

二、必须遵守的总原则

1. 禁止开放式回答绕过 Planner / Contract / Evidence。
2. 禁止关键词硬编码、正则、蒸馏规则、prompt if/else、上下文聚合隐式分类直接决定最终路径。
3. LLM 只能做理解、候选规划、表达合成、失败解释、检索查询改写，不能直接决定工具、权限、事实、MCP 参数或数据结论。
4. Planner 不生成最终回答。
5. Planner 不输出最终工具名。
6. Planner 不生成工具参数。
7. Planner 只输出意图、任务类型、证据需求、候选能力提示、候选知识源提示、是否需要澄清。
8. KnowledgeDiscovery 根据知识库配置、dataset metadata、source authority、freshness policy 发现候选知识源。
9. CapabilityDiscovery 根据 manifest / contract 找候选能力。
10. ExecutionPolicy 不调用 LLM，由规则、契约、权限、manifest、knowledge source policy、preflight 共同决定执行路径。
11. Composer 不选择工具、不选择知识库、不补事实、不发明建议。
12. Composer 只能基于 EvidenceLedger + ActionContract 表达最终答案。
13. Knowledge retrieval 不是最终证据，只有通过 EvidenceFilter / EvidenceLedger 接受的 chunk / document 才能用于回答。
14. 工具结果不是最终答案，必须进入 EvidenceLedger 后由 Composer 表达。
15. Web 搜索结果不是最终答案，必须进入 EvidenceLedger，且实时信息必须有 source_ref 和 fetched_at。
16. Explainer 不猜失败原因、不创造替代方案。
17. Explainer 只能基于 FailureContract 解释失败。
18. EvidenceLedger 必须成为所有回答的输入来源。即使是 smalltalk，也要标记 evidence_mode = model_only / no_external_evidence_required。
19. ContractSafety 必须检查 answer path 是否具备 sourceRefs / evidenceRefs / evidence_mode。
20. 主消息只展示用户可理解的最终回答；Planner、Contract、Tool Args、KB Chunks、Trace、Prompt、Evidence 明细进入右侧“过程与依据”。
21. 不得修改 MCP schema。需要补充能力时，通过 Capability Manifest / Adapter / Contract 扩展。
22. 不得为单个测试样例写 if/else。
23. 不得把广告业务关键词写死进通用 Chat Core。
24. 不得用 Prompt 代替 Tool Contract、权限校验、Schema 校验、MCP 执行、Knowledge Source Policy 或 Evidence 校验。
25. 不得让 UI 层兜底修复后端业务逻辑。
26. 不得让 Trace / CozeLoop / 连弩 SDK 失败影响 Chat 主流程。
27. 不得把 fake golden 当成真实上线验收。
28. 输出结论必须区分运行面、控制面、展示面、观测面、配置面。

三、知识库治理原则

知识库是 Evidence Source，不是路由旁路。

必须把知识库纳入 EvidenceCollection / EvidenceLedger，而不是让 knowledge_answer 直接绕过主链路生成最终答案。

知识库适合回答：

1. 内部业务文档。
2. 指标口径。
3. 归因逻辑。
4. 数据字典说明。
5. 投放规范。
6. 平台操作手册。
7. 历史复盘。
8. 项目资料。
9. FAQ。
10. 稳定的行业方法论。

知识库不适合直接回答：

1. 天气、新闻、媒体公告、政策更新等实时公开信息。
2. 昨天消耗、昨天激活、实时 ROI、账户余额、包状态等业务数据。
3. 权限判断。
4. 工具参数生成。
5. MCP 执行结果。
6. 需要调用系统 API 的状态查询。
7. 文件上传后的真实解析结果。
8. 需要最新网页事实的问题。

当用户问题属于实时事实，应进入 Web / Realtime Public Info capability，而不是知识库。

当用户问题属于业务数据查询，应进入 Tool-First MCP 链路，而不是知识库。

当用户问题属于内部知识问答，应进入 KnowledgeDiscovery + KB Retrieval + EvidenceLedger。

当知识库 source_count = 0：

* 不得编造。
* 不得把 source_count=0 伪装成“没有问题”。
* 不得自动 fallback 到模型自有知识回答内部事实。
* 应生成 evidence_mode = insufficient_evidence。
* 应通过 FailureContract / Composer 说明当前知识库没有找到可靠资料。
* 如 ActionContract 提供可恢复动作，可以提示用户补充文档、换检索范围、选择数据源。

当知识库命中文档但证据不充分：

* 不得强行回答。
* 必须说明证据不足或来源不明确。
* 可输出已找到的相关材料摘要。
* 不得把低分 chunk 当成事实依据。

七、目标架构设计

请输出新的开放式回答链路目标架构图，必须包含：

UserMessage
→ RequestUnderstanding
→ PlannerOutput
→ ContractPreflight
→ KnowledgeDiscovery / CapabilityDiscovery
→ ExecutionPolicy
→ EvidenceCollection
→ EvidenceLedger
→ AnswerComposition
→ ContractSafety
→ ResponseProjection

同时说明每一层职责边界：

1. RequestUnderstanding

   * 只做轻量语义理解、上下文摘要、语言识别、项目上下文归一化。
   * 不做最终路由。
   * 不直接选择工具。
   * 不直接选择知识库 dataset。
   * 不生成答案。

2. PlannerOutput

   * 由 LLM 生成结构化 JSON。
   * 只表达用户目标、任务类型、证据需求、候选能力提示、候选知识源提示、是否需要澄清。
   * 不输出最终工具名。
   * 不输出工具参数。
   * 不输出最终知识库 dataset id。
   * 不输出最终回答。

3. ContractPreflight

   * 检查 PlannerOutput 是否符合 schema。
   * 检查是否存在越权字段。
   * 检查是否缺少必要意图字段。
   * 检查是否把工具名、工具参数、最终答案塞进 PlannerOutput。
   * 失败时进入 FailureContract。

4. KnowledgeDiscovery

   * 基于 Knowledge Source Policy、Dataset Metadata、Domain Pack、source authority、freshness policy 发现候选知识源。
   * 不依赖硬编码关键词。
   * 不由 LLM 直接决定最终 dataset。
   * 产出 candidate_knowledge_sources，而不是最终答案。

5. CapabilityDiscovery

   * 基于 Capability Manifest、Tool Contract、业务域协议发现候选能力。
   * 不依赖关键词硬编码。
   * 不由 LLM 直接决定最终工具。

6. ExecutionPolicy

   * 不调用 LLM。
   * 基于 manifest、权限、项目、工具可用性、知识源可用性、数据权限、freshness、source authority、preflight 选择执行路径。
   * 产出 selected_capability / selected_knowledge_source / execution_plan / clarify_required / unsupported / blocked。

7. EvidenceCollection

   * 调用 KB / Web / MCP / File / System Config / Model-only evidence builder。
   * 只负责收集证据，不负责表达答案。
   * KB retrieval 结果必须经过 source authority、freshness、score、权限和 evidence filter。
   * 工具结果必须归一化为 tool_result evidence。
   * Web 结果必须归一化为 web evidence。
   * 文件结果必须归一化为 file evidence。

8. EvidenceLedger

   * 统一承载所有证据。
   * 所有答案必须从 EvidenceLedger 读取。
   * smalltalk 也必须生成 model_only evidence。
   * 实时信息必须具备 source_ref 和 fetched_at。
   * 知识库证据必须具备 dataset_id、document_id、chunk_id 或 source_ref。
   * 工具结果必须具备 tool_result evidence。
   * 文件结果必须具备 file/artifact evidence。
   * evidence_status = failed / blocked / empty / stale 时不得当成成功事实使用。

9. AnswerComposition

   * 由 Composer LLM 基于 EvidenceLedger 生成用户可见答案。
   * 不选择工具。
   * 不选择知识库。
   * 不补事实。
   * 不发明建议。
   * 只有 ActionContract 提供 allowed_actions 时才能表达下一步动作。

10. ContractSafety

* 检查答案是否存在证据外事实。
* 检查实时信息是否缺 source_ref / fetched_at。
* 检查 KB 答案是否缺 dataset/document/chunk/sourceRef。
* 检查 answer path 是否缺 evidence_mode。
* 检查是否泄露内部字段。
* 检查是否把 planner / tool args / raw trace / prompt / raw KB chunk 暴露到主消息。

11. ResponseProjection

* 主消息展示最终回答。
* 右侧展示过程、证据、工具、Prompt、Trace、原始信息。
* 不允许主消息展示内部 query_contract、slot_validation、raw params、appId、tool args、prompt、trace、raw KB chunk。
* 内部知识来源可以展示为用户可理解的来源标题、文档名、更新时间、来源类型，不展示内部 dataset 密钥或权限细节。
