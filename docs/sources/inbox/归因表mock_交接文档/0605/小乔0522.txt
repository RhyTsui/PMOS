1. 先把上下文分层定死
  把现有数据源归位到四层，不再混用：
  - 会话上下文：最近消息、临时角色、临时约束、追问状态
  - 任务上下文：task / run / result / evidence / blocker / next_action
  - 项目上下文：项目可用能力、口径、开关、MCP/模型可用性
  - 用户偏好画像：默认角色、主动偏好、输出风格、分析重点、风险偏好、解释深度、决策风格
  这一步的关键不是新增功能，而是先把“谁负责什么”分清。

2.新增 UserPreferenceProfile
  这份对象只存稳定偏好，不存原始记忆、不存全量对话。
  建议字段保留你给的结构，并补两个必要项：
  - currentRole：当前生效角色
  - roleHistory：角色来源和切换痕迹
  原则：
  - 只保留高置信、跨任务复用、长期稳定的偏好
  - 不把每天对话直接写进偏好
  - 偏好是软约束，不能覆盖任务和项目边界先不让用户填写和查看

3.新增 context-compiler
    做一个统一编译器，把分散来源编成一份消费包：
    - 输入：会话上下文、任务上下文、项目上下文、用户记忆、提示词、skill、开关、工具可用性
    - 输出：CompiledContextPackage

4. 结果要有可感知收益
    所以偏好注入要影响这几件事：

    - 路由前置：默认把问题引向合适角色/视角
    - 回答生成：结论优先、证据优先、风险优先、简洁/详细
    - 结果渲染：默认展示哪些块
    - 追问策略：问一个关键问题还是一次性补全
    - 快捷入口：按用户习惯排序

5. 偏好提炼要有节制
    更新机制不要实时写偏好，采用“原始记录 -> 周期蒸馏 ”的方式：
    - 对话/行为先写原始记忆或行为日志
    - 每日或每周生成偏好候选
    - 按置信度和稳定性筛选
    - 只更新高置信偏好

6.先在后台的用户列表增加偏好查看，后续考虑给用户看和管理。

7.登录时获取用户的角色，把角色和项目一样注入默认的上下文，然后后台增加角色提示词管理，定义角色如何影响后续的服务、解释方式和结果模板。以及角色：用于默认工作方式和入口文案，快捷入口：用于初始意图引导

8.角色化体验路由系统：让用户默认进入最适合自己的服务范围，减少 MCP 风控拦截，提升对话成功率和专业感。投 Chat 支持角色化体验路由。系统会在用户进入会话时自动加载项目、角色和默认数据视角，并基于角色决定欢迎页入口、问题语义、Agent / Workflow / Skill 路由和回答风格。
