三、按总纲对应的设计方案
1. 消息生命周期设计

新增或统一：

MessageLifecycle

标准流程：

createUserMessage()
  ↓
createAssistantRuntimeMessage()
  ↓
appendRuntimeEvents()
  ↓
assembleSemanticResultContract()
  ↓
replaceRuntimeWithFinalResult()
  ↓
renderSemanticRegions()

核心规则：

用户消息必须立即展示且不被 assistant placeholder 替代。
assistant 的 “...” 只能作为 assistant runtime 占位，不得替代用户提问。
2. Runtime 和 Result 分离

按照总纲，必须拆清：

RuntimeDisplayProtocol = 执行过程
SemanticResultContract = 最终结果

执行中可以显示：

问数分析中
正在解析需求
正在选择能力
正在查询数据
正在生成图表

执行完成后，默认只保留轻量状态：

问数分析 · 已完成

旧的思维链、调用、来源组件必须移除或迁移到：

RuntimeDisplayProtocol

并且默认折叠。

3. SemanticResultContract 统一正文

最终消息正文只能来自：

SemanticResultContract.regions[]

推荐结构：

{
  screenType: "report-trend-comparison",
  regions: [
    {
      regionType: "summary",
      componentBinding: "markdown-result",
      data: {

    },

            metricKey: "first_day_roi",

            yAxis: "left",
            formatter: "percent-2"
          },
          {
            metricKey: "cash_cost_amount",
            displayName: "消耗",
            yAxis: "right",
            formatter: "currency-2"
          }
        ]
      }
    },
    {
      regionType: "table",
      componentBinding: "data-table",
      visibility: {
        defaultState: "collapsed"
      }
    },
    {
      regionType: "actions",
      componentBinding: "action-list",
      data: {
        actions: [
          {
            actionType: "follow_up",
            label: "继续追问维度"

            label: "导出结果"
          },

“已取回 30 行数据”

所有按钮必须走：

ActionContract

并统一在：

message footer

渲染。

不能让不同组件自己渲染：

导出
排查
查看来源

否则以后每个 MCP、每个报表卡都会长得不一样。

5. 数据可视化必须走 VizSpec 子结构，但不能成为独立总协议

数据可视化仍然挂在：

SemanticResultContract.regions[].componentBinding = "data-visualization"

region.data 里可以有：

VizSpec

但 VizSpec 只是局部 data shape。

通用流程应该是：

Tool Raw Result
  ↓
DataFrameNormalizer
  ↓
Metric / Dimension Resolver
  ↓
ChartSpecFactory
  ↓
validateVisualizationRegion()
  ↓
DataVisualizationRenderer

不能让 MCP 返回什么字段，前端就直接画什么字段。

6. 指标格式必须由 MetricCatalog 驱动

新增或接入：

MetricCatalog

例如：

{
  metricKey: "first_day_roi",
  aliases: ["roi270", "首日ROI", "首日 roi"],
  displayName: "首日 ROI",
  valueType: "ratio",
  formatter: "percent-2"
}
{
  metricKey: "cash_cost_amount",
  aliases: ["cash_cost_amount", "消耗", "花费"],
  displayName: "消耗",
  valueType: "currency",
  formatter: "currency-2"
}

图表和表格统一调用：

formatMetricValue(metricKey, value)

不要在图表里单独写格式化。

7. 图表生成需要校验

趋势图必须校验：

1. 必须存在 date / time 维度
2. 至少有 2 个不同日期点
3. 每个 series 必须有合法 metricKey
4. 不同单位指标必须双轴或拆图
5. 空值必须有处理策略
6. 字段 alias 必须能解析到 canonical metric

如果校验失败，不应该画空图，而应该展示：

当前数据不足以形成趋势图。
可查看明细表，或调整时间范围后重试。

八、其它已确认设计决策

建议从下面 5 个点，让 Codex CLI 按这个方向执行。

1. Runtime 展示策略

建议：

普通用户：
只展示状态标签，不展示旧思维链和详细工具调用。

管理员 / Debug：
可展开 Runtime Trace。

建议默认：

双 Y 轴折线图
左轴：首日 ROI
右轴：消耗

3. 明细表格展示策略

建议：

默认折叠
按钮：查看明细
导出结果

不要默认把 30 行明细全铺出来。

4. row count 展示策略

建议：

普通正文不展示“已取回 N 行数据”
表格 footer 或 debug 面板可展示
5. 旧组件处理策略

建议：

旧思维链 / 调用 / 来源组件不改样式，直接从最终正文链路移除。不需要保留。

九、最终结论

这次应该定性为：

消息渲染链路没有完成从旧 MessagePart 到 Enterprise AI Chat OS 总纲架构的迁移。

不是：

图表样式问题
某个 MCP 字段问题
某个 prompt 文案问题

10 分方案应该是：

MessageLifecycle
+ RuntimeDisplayProtocol
+ SemanticResultContract
+ Result Assembly
+ Metric/Dimension Catalog
+ ChartSpecFactory
+ Component Registry
+ ActionContract Footer
+ Golden Cases
+ Guardrails

一起落地。

确认后，建议第一轮 Codex CLI 不做视觉美化，先做结构治理：

1. 禁用旧思维链 / 调用来源直接渲染
2. 最终正文只走 SemanticResultContract
3. 删除 row count 和查询完成卡片
4. ActionContract 统一底部渲染
5. 修复 chart spec 生成和 metric formatter
6. 增加趋势图 golden cases

这样才能保证不是为了某个 MCP 修补，而是让所有外挂 MCP 都进入统一的通用 Chat OS 渲染链路。
