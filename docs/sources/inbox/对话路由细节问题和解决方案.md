# 对话路由细节问题和解决方案

# 问题

*   用户一句话包含多个意图时怎么处理：例如“查一下 B 项目昨天消耗，顺便做成日报”。
    
*   用户先问通用问题，后续接业务动作时如何继承上下文。
    
*   用户纠正系统理解时，是否重跑路由、是否覆盖上一轮 slot。
    
*   用户说“刚才那个项目”“上次那个包”“这个指标”时，引用解析规则。
    
*   路由置信度低到什么程度必须追问。
    
*   同一意图命中多个能力时的优先级。
    
*   能力部分可用时，是返回部分结果、生成 case，还是继续追问。
    

# 解决方案

## 1. 总体设计原则

### 1.1 一句话不是一个 intent，而是一组任务

例如：

> “查一下 B 项目昨天消耗，顺便做成日报”

系统不应只路由到“报表生成”或“数据查询”，而应拆成：

1.  **数据查询任务**：查询 B 项目昨天的消耗数据。
    
2.  **日报生成任务**：基于第 1 步结果生成日报。
    
3.  **可选动作判断**：是否仅生成草稿，还是外发到群/邮件。如果涉及外发，需要二次确认。
    

### 1.2 上下文可以继承，但权限不能继承

用户上一轮提到的项目、包、指标、时间范围，可以作为候选上下文；但凡涉及预算调整、计划暂停、投放创建、报表外发、批量操作，都必须重新确认关键 slot。

### 1.3 数值事实只能来自数据源，不能由大模型编造

广告系统里的“消耗、ROAS、CPA、D1 留存、付费率、回传延迟”等数据，必须来自 BI、MMP、媒体 API、内部归因表等可信数据源。LLM 只能做解释、归纳、诊断建议和文本生成，不能直接生成事实数值。这一点尤其重要，因为 AI 广告产品的上限取决于归因链路和数据质量。

### 1.4 低风险自动执行，高风险人类确认

报表、查询、诊断、总结可以自动执行；预算修改、计划暂停、素材上线、回传口径变更、外部发送必须进入确认流。AI 在优化师工作中可以接管盯盘、调价、报表等机械环节，但商业目标权衡、合规、跨部门资源协调仍应保留人类控制。

# 2. 系统架构：对话路由器不是单点分类器，而是任务编排器

建议设计为 8 个模块：

|  **模块**  |  **作用**  |
| --- | --- |
|  1. 输入标准化 Normalizer  |  处理口语、省略、别名、错别字、相对时间  |
|  2. 上下文管理 Context Manager  |  维护项目、包、指标、日期、最近任务、当前看板状态  |
|  3. 意图拆解 Intent Decomposer  |  把一句话拆成多个子任务  |
|  4. 实体与 slot 解析 Entity & Slot Resolver  |  识别项目、包、媒体、账户、指标、时间、动作参数  |
|  5. 引用解析 Reference Resolver  |  解析“刚才那个项目”“上次那个包”“这个指标”  |
|  6. 风险与权限引擎 Policy Engine  |  判断是否可自动执行，是否需要确认  |
|  7. 能力路由 Capability Router  |  匹配数据查询、归因诊断、日报生成、创意 Agent、执行 Agent  |
|  8. 响应生成 Response Composer  |  输出任务理解、结果、缺失项、风险提示、下一步建议  |

这与“数字优化师多智能体协作中枢”的设计一致：前台是自然语言交互，后台是多个 Agent 与工作流协同，而不是传统菜单式工具。

# 3. 标准路由输出结构

每次用户输入后，系统内部应生成一个结构化 `TaskPlan`：

    {
      "user_utterance": "查一下 B 项目昨天消耗，顺便做成日报",
      "tasks": [
        {
          "task_id": "T1",
          "intent": "data_query",
          "business_object": "project",
          "slots": {
            "project": {
              "value": "B项目",
              "source": "explicit",
              "confidence": 0.96
            },
            "metric": {
              "value": "spend",
              "source": "explicit",
              "confidence": 0.98
            },
            "date_range": {
              "value": ["2026-05-25", "2026-05-25"],
              "source": "relative_time_resolved",
              "confidence": 0.99
            }
          },
          "capability": "ad_data_query",
          "risk_level": "read_only",
          "status": "ready"
        },
        {
          "task_id": "T2",
          "intent": "report_generate",
          "depends_on": ["T1"],
          "slots": {
            "report_type": {
              "value": "daily_report",
              "source": "explicit",
              "confidence": 0.95
            },
            "template": {
              "value": "default_project_daily_template",
              "source": "system_default",
              "confidence": 0.80
            }
          },
          "capability": "daily_report_agent",
          "risk_level": "content_generation",
          "status": "ready"
        }
      ],
      "need_user_confirmation": false
    }

关键点是：每个 slot 都要记录 `value、source、confidence、version、confirmed_by_user、expires_at`。这样后续用户纠正时，系统才知道应该覆盖哪个 slot、重跑哪些任务。

# 4. 问题一：用户一句话包含多个意图时怎么处理？

## 4.1 设计结论

采用**多意图拆解 + 任务依赖编排**，而不是单 intent 分类。

一句话中常见的多意图关系有四类：

|  **关系**  |  **触发词**  |  **处理方式**  |
| --- | --- | --- |
|  顺序依赖  |  “然后”“顺便”“做成”“基于这个”  |  前一个任务结果作为后一个任务输入  |
|  并行动作  |  “同时”“另外”“再查一下”  |  多任务并行执行  |
|  条件动作  |  “如果低于”“要是异常就”  |  先执行判断任务，再触发动作  |
|  复合动作  |  “查一下并给建议”  |  查询 + 分析 + 建议生成  |

## 4.2 示例：查消耗 + 生成日报

用户说：

> “查一下 B 项目昨天消耗，顺便做成日报”

系统内部拆解：

|  **子任务**  |  **intent**  |  **slot**  |  **能力**  |
| --- | --- | --- | --- |
|  T1  |  查询消耗  |  项目=B，日期=昨天，指标=消耗  |  数据查询能力  |
|  T2  |  生成日报  |  报告类型=日报，数据来源=T1  |  报表 Agent  |
|  T3，可选  |  发送日报  |  发送对象=未说明  |  若用户要求外发，则追问或确认  |

产品交互建议：

> 已识别为两个任务：

如果“B 项目”唯一匹配、用户有权限、日报模板存在，则不需要追问；如果 B 项目匹配到多个项目，比如“B-国内版”“B-海外版”“B-小游戏版”，必须追问。

# 5. 问题二：用户先问通用问题，后续接业务动作时如何继承上下文？

## 5.1 上下文分四层

|  **上下文层级**  |  **示例**  |  **是否可继承**  |
| --- | --- | --- |
|  业务实体上下文  |  B 项目、某包、某账户、某素材  |  可继承，但高风险动作需确认  |
|  指标上下文  |  消耗、ROAS、CPA、D7 回收  |  可继承  |
|  时间上下文  |  昨天、最近 7 天、上周  |  可继承，但必须转成绝对日期  |
|  知识主题上下文  |  “ROAS 下降原因”“回传延迟”  |  只能继承为分析主题，不能自动补项目/时间  |

## 5.2 通用问答不能自动生成业务实体

例如用户第一轮问：

> “ROAS 下降一般是什么原因？”

这是通用知识问题，系统只能建立一个**主题上下文**：`topic = ROAS下降诊断`。

用户第二轮说：

> “那帮我查一下我们项目是不是这样。”

此时可以继承“ROAS 下降诊断”这个主题，但不能自动知道“我们项目”是哪一个项目。系统应该这样处理：

> 你要检查哪个项目？我会按刚才的 ROAS 下降诊断框架，重点排查消耗、付费率、回传延迟、素材疲劳和渠道结构变化。

如果用户第一轮是：

> “B 项目昨天 ROAS 掉了多少？”

第二轮说：

> “那帮我分析原因。”

这时可以继承：

*   项目：B 项目
    
*   时间：昨天，即 2026-05-25
    
*   指标：ROAS
    
*   动作：归因诊断分析
    

不需要再问项目和时间。

## 5.3 继承优先级

建议使用以下优先级：

1.  当前句子显式 slot
    
2.  上一轮用户确认过的 slot
    
3.  最近一次成功执行任务的主对象
    
4.  当前工作台/看板选中的项目或包
    
5.  用户默认偏好，例如默认日报模板、默认平台
    
6.  历史会话记忆，仅在用户说“上次”“之前那个”时启用
    

关键规则：**显式输入永远覆盖继承上下文**。

# 6. 问题三：用户纠正系统理解时，是否重跑路由、是否覆盖上一轮 slot？

## 6.1 纠正分四类

|  **纠正类型**  |  **用户表达**  |  **是否重跑路由**  |  **是否覆盖 slot**  |
| --- | --- | --- | --- |
|  实体纠正  |  “不是 B 项目，是 C 项目”  |  是，重跑受影响任务  |  覆盖 project slot  |
|  时间纠正  |  “不是昨天，是上周”  |  是，重查数据、重算报告  |  覆盖 date slot  |
|  输出纠正  |  “日报太长，改成三段”  |  否，只重渲染结果  |  不覆盖业务 slot  |
|  意图纠正  |  “不是查消耗，是查 ROI”  |  是，重新匹配能力  |  覆盖 metric/intent  |

## 6.2 slot 覆盖规则

建议每个 slot 都采用版本化设计：

    {
      "slot": "project",
      "old_value": "B项目",
      "new_value": "C项目",
      "correction_type": "explicit_user_correction",
      "affected_tasks": ["T1", "T2"],
      "rerun_policy": "rerun_downstream_tasks"
    }

规则如下：

1.  用户显式纠正 > 系统推断 > 历史继承。
    
2.  只覆盖被纠正的 slot，不影响其他 slot。
    
3.  如果纠正影响数据源，则重查数据并重做下游分析。
    
4.  如果只影响文案风格，则不重查数据。
    
5.  如果纠正涉及预算、计划状态、出价、回传口径，必须重新进入确认流。
    
6.  不直接删除旧结果，而是生成新版本，保留审计链路。
    

## 6.3 示例

用户：

> “查一下 B 项目昨天消耗，做成日报。”

系统完成后，用户说：

> “不是 B，是 C。”

系统处理：

*   覆盖 `project = C`；
    
*   保留 `date = 2026-05-25`；
    
*   保留 `report_type = 日报`；
    
*   重跑数据查询；
    
*   重生成日报；
    
*   在结果中提示“已按 C 项目重算”。
    

用户说：

> “不是日报，改成周报。”

系统处理：

*   覆盖 `report_type = 周报`；
    
*   如果之前时间是“昨天”，周报时间范围不明确，需要追问：
    

> 周报要按“本周截至昨天”还是“上周完整自然周”生成？

# 7. 问题四：用户说“刚才那个项目”“上次那个包”“这个指标”时，引用解析规则

## 7.1 建立 Reference Ledger

系统需要维护一个“引用账本”，记录对话中出现过的所有业务对象：

    {
      "references": [
        {
          "object_type": "project",
          "object_id": "project_B_001",
          "display_name": "B项目",
          "mentioned_text": "B项目",
          "turn_id": 3,
          "role": "primary_target",
          "last_used_intent": "data_query",
          "salience_score": 0.93
        },
        {
          "object_type": "metric",
          "metric_code": "D1_ROAS",
          "display_name": "D1 ROAS",
          "turn_id": 4,
          "role": "diagnosis_metric",
          "salience_score": 0.88
        }
      ]
    }

## 7.2 引用解析优先级

|  **优先级**  |  **来源**  |  **示例**  |
| --- | --- | --- |
|  1  |  当前页面选中对象  |  用户在看板点选了某项目  |
|  2  |  最近一轮明确提到的同类型对象  |  “刚才那个项目”  |
|  3  |  最近一次成功执行任务的主对象  |  刚查过 B 项目消耗  |
|  4  |  当前业务工作台默认对象  |  当前项目组默认项目  |
|  5  |  历史会话/任务记录  |  “上次那个包”  |

## 7.3 具体规则

### “刚才那个项目”

默认指当前会话中最近一次作为主对象出现的项目。

如果最近出现过多个项目，例如系统刚对比了 A、B、C 三个项目，则不能直接选择，需要追问：

> 你说的“刚才那个项目”是 A、B 还是 C？

### “上次那个包”

优先查当前会话最近一次出现的包。如果当前会话没有包，再查用户历史任务中的最近包。

但“包”不能跨类型解析成“项目”。如果系统只找到项目，没有找到包，应该提示：

> 我没找到上一轮明确提到的包，只找到 B 项目。你是指 B 项目下的哪个包？

### “这个指标”

优先级：

1.  当前图表高亮指标；
    
2.  上一轮用户显式提到的指标；
    
3.  上一轮系统结果中的主指标；
    
4.  如果系统上一轮列了多个指标，则追问。
    

例如上一轮结果同时展示了“消耗、CPA、D1 ROAS、付费率”，用户说：

> “这个指标为什么掉了？”

系统不能猜，应追问：

> 你指的是 D1 ROAS、CPA，还是付费率？

## 7.4 引用置信度算法

建议计算一个 `reference_confidence`：

    reference_confidence =
    0.35 * recency_score +
    0.30 * type_match_score +
    0.20 * task_role_score +
    0.10 * ui_focus_score +
    0.05 * name_similarity_score

处理规则：

|  **分数**  |  **行为**  |
| --- | --- |
|  ≥ 0.85  |  自动解析，并在回复中明示理解  |
|  0.70 - 0.85  |  可执行低风险查询，但要展示假设  |
|  0.55 - 0.70  |  追问确认  |
|  < 0.55  |  不执行，要求用户明确对象  |

# 8. 问题五：路由置信度低到什么程度必须追问？

## 8.1 不建议只用一个总分

路由置信度应拆成五个维度：

|  **维度**  |  **含义**  |
| --- | --- |
|  intent\_confidence  |  用户到底想查数据、做报表、改预算，还是问知识  |
|  entity\_confidence  |  项目、包、账户、媒体是否唯一  |
|  slot\_confidence  |  时间、指标、维度、口径是否明确  |
|  capability\_confidence  |  系统是否有能力完成  |
|  risk\_confidence  |  操作风险是否可控  |

总分可以这样计算：

    route_confidence =
    0.30 * intent_confidence +
    0.25 * entity_confidence +
    0.20 * slot_confidence +
    0.15 * capability_confidence +
    0.10 * context_confidence

## 8.2 建议阈值

|  **场景**  |  **自动执行阈值**  |  **追问阈值**  |  **强制确认**  |
| --- | --- | --- | --- |
|  只读数据查询  |  ≥ 0.80  |  < 0.70  |  否  |
|  报表生成  |  ≥ 0.78  |  < 0.70  |  外发时需要  |
|  归因诊断  |  ≥ 0.82  |  < 0.75  |  否  |
|  创意脚本生成  |  ≥ 0.75  |  < 0.65  |  涉合规时需要  |
|  预算/出价/暂停/开启  |  ≥ 0.90  |  < 0.90  |  必须确认  |
|  批量操作  |  ≥ 0.95  |  < 0.95  |  必须确认  |
|  修改回传口径  |  ≥ 0.95  |  < 0.95  |  必须确认  |

## 8.3 必须追问的情况

即使总置信度较高，以下情况也必须追问：

1.  项目、包、账户命中多个候选。
    
2.  时间范围不明确，且会影响结论。
    
3.  指标口径不唯一，例如“ROI”可能指广告 ROI、付费 ROI、D1 ROAS、D7 ROAS。
    
4.  用户要求执行写操作，例如“把预算提上去”“关掉这些计划”。
    
5.  用户用了“全部”“所有”“一键处理”这类高风险范围词。
    
6.  系统能力部分缺失，继续执行可能造成误导。
    
7.  涉及品牌安全、合规、素材审核、外部发送。

# 9. 问题六：同一意图命中多个能力时的优先级

## 9.1 先判断是“互补能力”还是“竞争能力”

很多情况下不是二选一，而是需要编排多个能力。

例如：

> “B 项目昨天 ROAS 掉了，帮我分析原因。”

这不是只调“知识问答”，也不是只调“数据查询”，而是：

1.  查询 B 项目昨天及基准期数据；
    
2.  查询渠道、素材、包、计划、付费、留存、回传延迟；
    
3.  调用归因诊断 Agent；
    
4.  生成异常原因排序；
    
5.  给出建议动作。
    

## 9.2 能力优先级

建议优先级如下：

|  **优先级**  |  **能力**  |  **原则**  |
| --- | --- | --- |
|  P0  |  权限与风控能力  |  先判断用户能不能做  |
|  P1  |  业务实体解析能力  |  先确认项目、包、账户、指标  |
|  P2  |  可信数据源能力  |  数值事实先查 BI/API/MMP  |
|  P3  |  专业 Agent 能力  |  归因、策略、创意、合规  |
|  P4  |  报表/内容生成能力  |  基于已验证数据生成  |
|  P5  |  通用 LLM/RAG  |  只做解释、归纳、补充知识  |
|  P6  |  case/人工流转  |  系统不能解决时生成工单  |

## 9.3 Agent 路由建议

结合数字优化师矩阵，可以这样分配：

|  **用户意图**  |  **主能力**  |  **辅助能力**  |
| --- | --- | --- |
|  查消耗、查 CPA、查 ROAS  |  数据查询能力 / 磐石 Agent  |  报表 Agent  |
|  解释异常、归因诊断  |  磐石 Agent  |  智囊 Agent  |
|  制定投放策略  |  智囊 Agent  |  磐石 Agent、护盾 Agent  |
|  生成素材脚本  |  灵感 Agent  |  护盾 Agent  |
|  检查合规风险  |  护盾 Agent  |  灵感 Agent  |
|  调预算、关计划、开计划  |  执行 Agent  |  风控网关、人类确认  |
|  做日报/周报/月报  |  报表 Agent  |  数据查询、磐石 Agent  |

已有研究中也把数字优化师拆成数据归因、创意增长、业务策略、合规审计等不同角色，这种路由方式可以直接映射到 Agent 矩阵。

## 9.4 冲突处理规则

如果多个能力都能回答，按以下规则选择：

1.  **用户明确指定优先**：用户说“只给我结论，不用查数据”，则走知识/总结能力。
    
2.  **可信数据源优先**：涉及数值，必须先查数据。
    
3.  **专业 Agent 优先于通用 LLM**：归因诊断优先走磐石 Agent，而不是通用问答。
    
4.  **低风险能力先行**：先查询、模拟、生成建议，再进入执行。
    
5.  **合规能力强制后置检查**：涉及素材、文案、外发内容，必须过护盾 Agent。

# 10. 问题七：能力部分可用时，是返回部分结果、生成 case，还是继续追问？

## 10.1 决策矩阵

|  **情况**  |  **推荐动作**  |  **示例**  |
| --- | --- | --- |
|  缺的是用户才能提供的信息  |  追问  |  “你要查哪个项目？”  |
|  缺的是非关键参数，且有默认值  |  先执行并明示假设  |  “按默认日报模板生成”  |
|  数据源部分不可用  |  返回部分结果 + 标明缺失 + 生成 case  |  巨量数据正常，腾讯 API 异常  |
|  权限不足  |  返回可访问范围 + 生成权限 case  |  只能看项目，不能看账户级数据  |
|  回传延迟导致数据不完整  |  返回当前值 + 标注延迟风险 + 可给预测值  |  SKAN/MMP 延迟  |
|  写操作部分可执行  |  不建议自动部分执行，需确认  |  10 个计划里 7 个可调预算  |
|  合规能力不可用  |  阻断高风险输出  |  素材无法过审计，不允许自动上线  |
|  用户目标不可实现  |  生成 case 或替代方案  |  平台 API 不支持某操作  |

## 10.2 示例：数据源部分不可用

用户：

> “查一下 B 项目昨天消耗，做成日报。”

系统发现：

*   巨量数据可用；
    
*   腾讯广告 API 异常；
    
*   内部 BI 可用；
    
*   MMP 回传延迟 6 小时。
    

推荐输出：

> 已生成 B 项目 2026-05-25 日报草稿。  
当前结果包含巨量、内部 BI 数据；腾讯广告数据暂不可用，MMP 深度转化存在约 6 小时回传延迟，因此 ROAS 和付费率为临时口径。  
我已将“腾讯广告 API 拉取失败”生成数据 case，日报中已标记缺失项，未将临时结果作为最终结论。

这里不应该继续追问用户，因为用户无法解决 API 异常；也不应该装作数据完整。

## 10.3 示例：缺少关键业务 slot

用户：

> “帮我把那个包的预算提一下。”

系统必须追问，因为缺少：

*   哪个包；
    
*   提多少；
    
*   哪个平台/账户；
    
*   生效时间；
    
*   是否有预算上限；
    
*   是否允许自动执行。
    

推荐回复：

> 需要确认几个关键项后才能操作：你说的是哪个包？预算要从多少调到多少？这属于投放写操作，我会先生成变更预览，不会直接执行。

## 10.4 case 生成标准

当系统不能完成任务，但问题不是用户能立刻补充解决的，应生成 case。case 应包含：

    {
      "case_type": "data_source_unavailable",
      "user_goal": "生成B项目昨天日报",
      "affected_capability": "tencent_ads_api",
      "known_slots": {
        "project": "B项目",
        "date": "2026-05-25",
        "report_type": "daily_report"
      },
      "impact": "腾讯渠道消耗、激活、ROAS缺失",
      "temporary_output": "已生成不含腾讯数据的临时日报",
      "owner": "data_platform_team",
      "priority": "P1"
    }

# 11. 推荐的交互模式

## 11.1 高置信度、低风险

用户：

> “查一下 B 项目昨天消耗，顺便做成日报。”

系统：

> 已识别为两个任务：查询 B 项目 2026-05-25 消耗，并基于结果生成日报草稿。使用默认项目日报模板，不会自动外发。

## 11.2 高置信度、高风险

用户：

> “把 B 项目今天预算提高 20%。”

系统：

> 这是预算变更操作，需要确认。  
当前理解：B 项目，今天预算上调 20%，影响 12 个计划，预计日预算从 50 万调整到 60 万。  
请确认是否执行。

## 11.3 低置信度

用户：

> “看看刚才那个指标为什么不行。”

系统：

> 我需要确认你指的是哪个指标。上一轮结果里包含消耗、CPA、D1 ROAS、付费率。你要分析哪一个？

## 11.4 纠正理解

用户：

> “不是 B，是 C。”

系统：

> 已把项目从 B 项目改为 C 项目，沿用 2026-05-25 和日报模板重新查询并生成。

# 12. MVP 落地优先级

## P0：先做安全可用的基础路由

必须支持：

1.  单意图识别；
    
2.  多意图拆解；
    
3.  项目、包、指标、时间 slot 抽取；
    
4.  上下文继承；
    
5.  只读查询与报表生成；
    
6.  高风险操作确认；
    
7.  低置信度追问。
    

目标是让系统可靠完成“查数、解释、生成日报”这类高频场景。

## P1：做上下文和纠错能力

重点支持：

1.  “刚才那个项目”；
    
2.  “这个指标”；
    
3.  “不是 B，是 C”；
    
4.  “按刚才口径再查一次”；
    
5.  slot 版本化；
    
6.  任务重跑与下游重算。
    

这一步决定系统是否像一个真正懂业务的优化师，而不是一次性问答工具。

## P2：接入多 Agent 和复杂编排

重点支持：

1.  磐石 Agent 做归因诊断；
    
2.  灵感 Agent 做创意脚本；
    
3.  智囊 Agent 做策略设计；
    
4.  护盾 Agent 做合规审计；
    
5.  case 自动生成；
    
6.  预算、计划、素材等写操作的治理网关。
    

这一步对应从“AI 辅助工具”升级到“数字优化师多智能体中枢”。

# 13. 最终建议：用三条产品规则统一所有边界

## 规则一：先还原任务图，再执行能力

不要问“这是哪个 intent”，而要问：

> 用户要完成几个任务？这些任务之间有什么依赖？哪些 slot 已明确？哪些能力能完成？风险等级是什么？

## 规则二：上下文只做候选，不做无条件事实

“刚才”“上次”“这个”都必须走引用解析。只有在实体唯一、类型匹配、风险较低时才自动继承；否则追问。

## 规则三：系统不完整时，不假装完整

能力部分可用时，优先返回可验证的部分结果，并清楚标注缺失、延迟、置信度和影响范围；用户能补的就追问，用户不能补的就生成 case。这样才能建立优化师对 AI 系统的信任。
