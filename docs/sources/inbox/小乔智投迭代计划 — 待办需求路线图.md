OpenAI Agents SDK 最佳实践对比

参考 OpenAI Agents SDK 官方架构 (https://developers.openai.com/api/docs/guides/agents)（2026-04 更新），行业主流 Agent  系统有以下核心模式：

模式: Runner 执行引擎  OpenAI Agents SDK: Runner 类，清晰生命周期循环（LLM→tool→handoff→repeat）  小乔智投当前: route.ts 4007 行单体，所有编排逻辑在一个文件  差距: 🔴 D13: Runner 单体化  ────────────────────────────────────────  模式: Guardrails 三层防护  OpenAI Agents SDK: Input / Tool I/O / Output 三层，并行执行，tripwire 熔断  小乔智投当前: 仅 contract-safety.ts 单层后置检查  差距: 🔴 D14: 单层 guardrail，无 input/tool guardrail，无 tripwire  ────────────────────────────────────────  模式: Trace & Span 可观测  OpenAI Agents SDK: 自动 trace-and-span 模型，OpenTelemetry 兼容  小乔智投当前: trace.ts 有 trace\_id 但无 span\_id/parent\_span，非结构化  差距: 🟡 D15: Trace 非结构化，无 span 层级  ────────────────────────────────────────  模式: Lifecycle Hooks  OpenAI Agents SDK: RunHooks(全局) + AgentHooks(单 Agent)：on\_run\_start/end, on\_tool\_start/end, on\_llm\_start/end,  on\_handoff  小乔智投当前: 无 hook 系统，事件 inline 推送  差距: 🟡 D16: 无生命周期 hook  ────────────────────────────────────────  模式: Typed Function Tools  OpenAI Agents SDK: @function\_tool + Pydantic 自动 JSON schema + input/output guardrails  小乔智投当前: MCP tool 通过 tool-capability-normalization 适配，但无 per-tool input/output guardrail  差距: 🟡 D17: 无 per-tool guardrail  ────────────────────────────────────────  模式: Structured Output  OpenAI Agents SDK: output\_type Pydantic 模型强制 LLM 输出匹配 schema  小乔智投当前: Planner 用 contract validator；answer composer / intent router 仍用自由文本  差距: 🟡 D18: LLM 输出未强制结构化

▎ 与项目原则的兼容性：这些模式均符合"Fat MCP/Fat Skill + Thin Chat Runtime"——Runner 分解不引入新业务逻辑，Guardrails  ▎ 是薄校验层，Trace/Hook 是可观测性基础设施，都不增加 Multi-Agent 复杂度。
