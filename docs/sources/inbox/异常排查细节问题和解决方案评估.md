1\. 异常排查细节

● “数据不对”如何拆成数据延迟、口径差异、回传失败、归因失败、权限缺失。

● 诊断需要哪些最小字段，不同异常类型是否不同。

● 多轮仍无法定位时，case 的标题、优先级、负责人怎么生成。大模型用后台的提示词控制生成，不需要负责人。

● 诊断结论的置信度如何表达。

● 已检查项、未检查项、无法检查项如何区分。



这一部分本质上是在定义：



AI 广告系统的“异常诊断操作系统（Diagnostic OS）”



不是普通问答。



真正的目标是：



把“数据不对”这种模糊抱怨，结构化拆成：



哪类异常；

哪个链路；

哪个层级；

哪个证据；

哪些已经排除；

目前最可能原因；

还缺什么信息；

是否需要升级为 case。



这里如果设计不好，系统就会：



一直追问；

一直重复查数据；

看起来像“AI在装懂”；

无法形成团队信任。



下面给你一套偏“头部游戏公司数据排障体系”的方案。



1\. “数据不对”如何拆解



用户说：



“数据不对”



系统不能直接问：



“哪里不对？”



而应该：



先进入 Diagnostic Intent



内部转成：



{

&#x20; "intent": "diagnostic",

&#x20; "problem\_statement": "数据不对"

}



然后自动进入：



异常分类树（Diagnostic Taxonomy）

1.1 推荐一级分类



建议固定六大类：



一级分类	本质

数据延迟	数据还没到

数据缺失	数据没产生

回传失败	SDK/MMP/API失败

归因异常	attribution错误

口径差异	统计逻辑不同

权限/展示问题	用户看到的不完整

1.2 二级异常树

A. 数据延迟



包括：



子类

SKAN延迟

ETL未完成

流式计算积压

API同步延迟

分区未生成

B. 数据缺失

子类

计划无数据

某媒体无数据

某时段无数据

某维度被过滤

C. 回传失败

子类

SDK未上报

MMP回传失败

API签名错误

postback失败

token失效

D. 归因失败

子类

click丢失

install未匹配

SKAN覆盖

归因窗口错误

去重失败

E. 口径差异



这是最常见。



子类

时区不同

汇率不同

去重逻辑不同

ROI窗口不同

自然量是否包含

BI与媒体口径差异

F. 权限/展示问题

子类

无账户权限

行级过滤

数据脱敏

字段隐藏

当前仅看部分媒体

1.3 系统不能一上来追问



正确方式：



先自动做：



一级自动诊断



例如：



检查：

\- 数据成熟度

\- ETL状态

\- API状态

\- 回传状态

\- 权限

\- 最近异常日志



很多问题用户自己根本不知道。



2\. 诊断最小字段（Minimum Diagnostic Fields）



这是核心。



不同异常需要不同字段。



不能一个统一 schema。



2.1 通用最小字段



任何诊断都至少需要：



字段	必须

项目/project	是

时间范围	是

指标	是

数据来源	是

查询维度	否

媒体/platform	否

账户/account	否

2.2 数据延迟诊断



至少需要：



{

&#x20; "project": "",

&#x20; "date": "",

&#x20; "data\_source": "",

&#x20; "etl\_batch": "",

&#x20; "partition\_status": ""

}



系统检查：



分区是否完成；

回传成熟度；

当前延迟分钟数。

2.3 回传失败诊断



必须增加：



{

&#x20; "app\_id": "",

&#x20; "event\_name": "",

&#x20; "mmp": "",

&#x20; "postback\_status": "",

&#x20; "sdk\_version": ""

}



否则根本无法定位。



2.4 归因异常诊断



必须：



{

&#x20; "click\_time": "",

&#x20; "install\_time": "",

&#x20; "attribution\_window": "",

&#x20; "device\_type": "",

&#x20; "media\_source": ""

}

2.5 口径差异诊断



必须：



{

&#x20; "report\_a": "",

&#x20; "report\_b": "",

&#x20; "timezone": "",

&#x20; "currency": "",

&#x20; "metric\_definition": ""

}

2.6 动态字段补全



建议：



Diagnostic Slot Filling Engine



系统自动推断：



字段	来源

project	当前会话

media	当前图表

metric	用户问题

report	当前页面

timezone	项目默认配置



减少追问。



3\. 多轮仍无法定位时，case 如何生成



你说：



大模型后台提示词控制生成，不需要负责人。



这个方向对。



建议：



AI Diagnostic Case Generator



不要只是生成一句：



“数据异常工单”



而是：



生成结构化 Case

3.1 Case 自动生成时机



建议：



条件	是否生成

自动诊断失败	是

超过3轮追问	是

涉及平台接口异常	是

数据链路断裂	是

权限问题	否

用户主动要求	是

3.2 Case 标题生成规则



不要纯自然语言。



建议：



\[异常类型]\[项目]\[时间]\[核心指标]



例如：



【回传异常】B项目 iOS D1付费事件缺失（2026-05-25）

3.3 Case 优先级规则



自动算。



P0



系统级：



全平台挂；

所有项目无数据；

核心回传中断。

P1



业务严重：



大R回传失败；

ROI异常暴跌；

主媒体数据缺失。

P2



部分异常：



某媒体部分缺失；

某维度异常。

P3



轻微：



展示错误；

文案问题；

非核心字段。

3.4 Case 内容结构

{

&#x20; "case\_title": "",

&#x20; "diagnostic\_type": "",

&#x20; "symptom": "",

&#x20; "affected\_scope": "",

&#x20; "checked\_items": \[],

&#x20; "suspected\_root\_causes": \[],

&#x20; "missing\_information": \[],

&#x20; "temporary\_workaround": "",

&#x20; "evidence": \[]

}

4\. 诊断结论置信度如何表达



这是非常重要的。



AI 不能：



“应该是…”



这种很危险。



建议：



Diagnostic Confidence Layer

4.1 不要只给一个百分比



应该：



多维置信度

类型	含义

数据完整度	数据够不够

证据强度	是否有直接证据

链路覆盖率	检查了多少环节

规则匹配度	是否命中已知模式

AI推断成分	是否依赖推理

4.2 推荐展示方式



不要：



置信度：82%



太像假的。



建议：



高置信度



当前高度怀疑为 SKAN 回传延迟。

已检测到：



ETL正常；

API正常；

postback存在明显延迟；

同类项目出现一致现象。

当前诊断可信度：高。

中置信度



当前可能与归因窗口配置差异有关。

已排除接口失败与权限问题，但缺少媒体侧 click 明细，暂无法完全确认。

当前诊断可信度：中。



低置信度



当前无法确定根因。

现有证据不足，且部分链路无法访问。建议生成异常 case 进一步排查。



4.3 推荐置信度等级

等级	条件

高	有直接证据

中	有间接证据

低	依赖推理

未知	数据不足

5\. 已检查项 / 未检查项 / 无法检查项



这是：



Diagnostic Trace



必须做。



否则用户会觉得 AI 在胡说。



5.1 三类必须区分

类型	含义

已检查	系统实际检查过

未检查	理论应该检查但还没检查

无法检查	权限/API/数据限制

5.2 推荐展示结构

已检查项

✓ 腾讯广告API状态

✓ ETL任务状态

✓ iOS postback日志

✓ BI聚合表

未检查项

○ 媒体侧click原始日志

○ 海外MMP实时队列

无法检查项

× AppsFlyer原始设备级日志（当前无权限）

× SKAN明细（平台未开放）

5.3 不允许伪检查



这是重点。



LLM 不能说：



“已检查 ETL”



除非：



真的调用了检查能力



否则属于：



虚假可观察性（Fake Observability）



这是企业 AI 系统的大忌。

7\. 最终建议：异常系统必须“像 SRE 系统”



不要把它做成：



聊天机器人



应该做成：



AI版广告数据SRE系统



核心不是：



“回答问题”



而是：



可信地定位问题



所以最重要的是：



能力	是否必须

链路状态	必须

真实检查	必须

证据回显	必须

排除过程	必须

不确定性表达	必须

Case升级	必须

可追溯性	必须



这才会让优化师真正相信：



“这个 AI 不是在聊天，而是真的在排障。”
