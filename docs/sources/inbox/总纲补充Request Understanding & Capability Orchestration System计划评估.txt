三、意图到底放哪里？

不要放在这些地方：

Unified Semantic Contract 下面  ❌
Data Visualization UX 下面      ❌
AI Runtime UI 下面              ❌
Component Registry 下面         ❌
Prompt 里面硬写                 ❌

正确位置是：

Enterprise AI Chat OS
└─ Request Understanding System
   └─ Intent Governance

但它会和这些模块发生关系：

Intent Governance
  ↓
UserRequirementContract
  ↓
Capability Selection Policy
  ↓
Tool Invocation Plan
  ↓
Runtime Display Protocol
  ↓
SemanticResultContract
  ↓
Component Registry

也就是说：

Intent 决定走哪条业务路径；
Capability 决定用什么能力；
Runtime 记录执行过程；
SemanticResultContract 负责最终结果；
Component Registry 负责前端渲染。


四、不要只做 Intent，要升级成 UserRequirementContract

只做意图会不够。

例如：

看下近 30 天素材消耗和 ROI 趋势

如果只识别成：

intent = report_query

还是会被日报抢走。

应该解析成：

type UserRequirementContract = {
  intent: "report_query"

  requestedSubject: "material"

  requestedView: "trend"

  businessDomain: "advertising"

  metrics: ["cost", "roi"]

  dimensions: ["date", "material"]

  dateRange: {
    type: "relative"
    value: "last_30_days"
  }

  granularity: "day"

  outputPreference: {
    preferredRegions: ["summary", "chart", "table"]
    chartTypeHint: "line"
  }

  confidence: number

  ambiguity: {
    hasAmbiguity: boolean
    candidates?: string[]
    clarificationQuestion?: string
  }
}

这样后续能力选择才有依据。

真正的问题不是：

report_query 还是 material-analysis

而是：

用户请求的主体是谁？
请求的是数据、趋势、分析、诊断还是素材内容理解？
需要哪些指标、维度、时间粒度？
哪个能力对这个主体和数据源最权威？

九、针对“素材数据调用成日报”的标准化解法

不要写：

素材问题强制 get_zt_ad_mat_report

要写成系统规则：

当 UserRequirement.requestedSubject = material
且 requestedView 属于 data_query / trend_query / performance_analysis
能力选择阶段必须优先选择：
subject = material
且 authoritativeFor 包含 material-performance
且支持所需 metrics / dimensions / granularity 的 capability。

account / day-report / roi-summary 类泛化能力不得作为 primary capability 胜出。
只有当素材专用能力不存在、不可用、无权限、指标不支持或数据为空时，才允许进入 fallback。
fallback 必须写入 sourceRefs / evidenceRefs / warnings，并在 UI 中披露。

这才符合你们的产品化标准。

十一、最终判断

你的直觉是对的：

现在总纲还不够。

但不是因为缺更多 UI 规范，也不是因为缺更多渲染组件，而是缺：

请求理解
能力编排
业务语义
上下文承接
MCP 治理
路由观测
结果组装

一句话收口：

Enterprise AI Chat OS 不能只定义“结果怎么渲染”，还必须定义“用户请求如何被理解、能力如何被选择、工具如何被治理、结果如何被组装、路由如何被解释”。

所以，意图不是总纲之外的新体系；它应该被升级为：

Request Understanding System

并和：

Capability Orchestration System
Business Semantic Layer
Runtime Display Protocol
Unified Semantic Contract
Component Registry
Observability & Evaluation

一起进入总架构。
