1. 数据查询与报表细节问题
● 默认时间范围规则：用户没说时间时是否默认昨天、近 7 天，还是必须追问。
● 指标名歧义：例如“成本”是激活成本、付费成本还是消耗。
● 查询结果为空时，是数据为 0、数据延迟、权限问题，还是接口失败。
● 报表草稿、报表、报表模板、定时报表产物之间的转换规则。
● 用户修改查询结果后再保存，保存的是原始数据还是加工视图。
● 定时报表失败几次后暂停，是否通知用户。

这部分本质上是在定义：

“AI 广告数据 Copilot 的数据语义层 + 报表状态机 + 数据可信度治理”。

如果这里不设计清楚，后面一定会出现：

AI 乱猜指标；
用户不知道数据为什么是 0；
报表和草稿混乱；
保存后口径漂移；
定时报表失控刷失败通知。

下面我按“查询语义 → 数据可信度 → 报表生命周期 → 定时任务治理”四层给完整方案。

1. 默认时间范围规则

这是 AI 数据系统里最容易“看起来聪明、实际上危险”的地方。

1.1 核心原则
原则一：不同任务类型，默认时间不同

不能全系统统一默认“昨天”或“近7天”。

应该按：

查询类型	默认时间
实时监控/异常排查	今天
常规日报查询	昨天
趋势分析	最近7天
周期分析	最近30天
ROI/回收分析	按指标自动扩展
对比分析	当前周期 vs 上一周期
用户未明确且高风险	必须追问
1.2 广告业务推荐默认规则
A. “查消耗/点击/激活”

默认：

昨天（自然日）

因为：

广告行业默认日报语义；
当天数据存在回传延迟；
用户最常看昨日完整数据。

用户：

“看下 B 项目消耗”

系统：

默认按昨天（2026-05-25）查询 B 项目消耗。

B. “看趋势”

默认：

最近7天

因为趋势至少需要多个点。

用户：

“看看最近 ROI 趋势”

系统：

默认按最近7天查看 ROI 趋势。

C. “分析 ROAS/回收”

不能默认昨天。

原因：

D7/D30 ROAS 必须等窗口成熟；
昨天数据天然不完整。

推荐：

指标	默认窗口
D1 ROAS	最近7天
D7 ROAS	最近14天
D30 ROAS	最近45天

系统要自动补成熟期。

D. “异常/告警”

默认：

今天实时

因为用户通常在盯盘。

1.3 必须追问的情况

以下必须追问：

场景	原因
“ROI怎么样”	不知道 D1/D7/D30
“最近效果不太行”	时间范围过于模糊
“看看回收”	回收口径不明确
“分析一下”	没有指标和时间
涉及复盘/汇报	时间影响结论
2. 指标名歧义规则

这是 AI BI 系统最核心的治理点之一。

2.1 不允许大模型自由猜指标

必须引入：

受控指标词典（Metric Registry）

例如：

{
  "metric_alias": "成本",
  "possible_metrics": [
    "激活成本(CPI)",
    "注册成本(CPR)",
    "付费成本(CPA)",
    "广告消耗(Spend)"
  ],
  "default_by_scene": {
    "买量优化": "CPI",
    "投放日报": "Spend",
    "付费分析": "CPA"
  }
}
2.2 指标解析优先级
优先级	来源
当前句子明确指标	“付费成本”
当前页面上下文	当前图表展示 CPA
用户历史偏好	用户经常把“成本”说成 CPI
当前任务场景	投放日报默认 Spend
系统默认	最后兜底
2.3 推荐规则
“成本”

默认不要直接猜。

如果上下文不足：

系统：

你说的“成本”是：

激活成本（CPI）
注册成本（CPR）
付费成本（CPA）
广告消耗（Spend）
“ROI”

必须拆：

可能含义
D1 ROAS
D7 ROAS
D30 ROAS
广告ROI
付费ROI
“回收”

不能直接等于 ROI。

因为很多公司：

回收 = ROAS
回收 = 充值金额
回收 = 现金回收

必须走词典。

3. 查询结果为空时怎么判断

这是 AI 数据系统可信度核心。

不能直接返回：

“没有数据”

必须区分：

类型	含义
真正为0	数据真实为0
数据延迟	数据还没回来
权限不足	用户没权限
接口失败	系统错误
条件过滤过严	被筛没了
数据未产出	ETL未完成
3.1 推荐 Empty Result Resolver

系统必须做：

Step1：检查任务状态
SUCCESS
PARTIAL_SUCCESS
DELAYED
FAILED
NO_PERMISSION
EMPTY
Step2：检查数据链路

检查：

检查项
数据源接口
ETL状态
分区状态
回传延迟
权限过滤
SQL返回
是否被筛空
3.2 用户展示规则
A. 真正为0

B项目昨天消耗为0。
当前未检测到投放计划消耗。

B. 数据延迟

当前数据尚未完整回传。
iOS SKAN数据预计还有约4小时延迟。

C. 权限问题

你当前没有查看 B 项目账户级数据的权限。

D. 接口失败

腾讯广告接口调用失败，暂时无法获取数据。
已生成数据异常 case。

E. ETL未完成

今日明细数据仍在计算中，预计 10:20 完成。

4. 报表草稿、报表、模板、定时报表产物的转换规则

这是最容易失控的部分。

建议明确：

四层对象模型
对象	含义
Report Template	模板
Report Draft	草稿
Report Snapshot	固化报表
Scheduled Report Job	定时任务
4.1 Report Template（模板）

只保存：

布局
指标
图表
默认时间
过滤规则
样式

不保存具体数据。

4.2 Report Draft（草稿）

用户临时编辑状态。

特点：

可改指标
可改图表
可改筛选
可改文案
不具备正式版本号

草稿生命周期：

创建 → 编辑 → 预览 → 发布/丢弃
4.3 Report Snapshot（正式报表）

正式固化版本。

特点：

数据冻结
有版本号
有生成时间
有证据快照
有查询口径

这是：

汇报版
审计版
外发版
4.4 Scheduled Report Job（定时报表）

是：

任务定义

不是报表本身。

例如：

{
  "cron": "每天9点",
  "template": "海外项目日报模板",
  "receivers": ["发行群"],
  "timezone": "Asia/Shanghai"
}

每次执行后生成：

Report Snapshot
5. 用户修改查询结果后再保存，保存原始数据还是加工视图？

必须同时保存：

类型	是否保存
原始查询结果	必须
用户加工视图	必须
加工操作链	必须
5.1 为什么？

否则：

AI 无法追溯；
用户无法复盘；
数据口径会漂；
后续重算会错。
5.2 推荐结构
{
  "raw_query_result": {},
  "transformations": [
    "过滤低消耗计划",
    "按媒体聚合",
    "新增ROI列"
  ],
  "final_view": {},
  "snapshot_time": "2026-05-26 09:00:00"
}
5.3 重要规则
保存“视图” ≠ 保存“数据”

用户保存的是：

可复现的数据加工过程

而不是一张静态表。

这样后面：

可重新拉取；
可重算；
可审计；
可 Diff；
可版本化。
6. 定时报表失败几次后暂停，是否通知用户？

必须有：

Job Reliability Policy
6.1 推荐失败策略
连续失败次数	行为
1次	自动重试
2次	降级重试
3次	通知用户
5次	自动暂停
7次	标记异常任务
6.2 重试机制
短暂失败

自动：

指数退避
更换节点
降级接口
使用缓存
数据延迟

延后：

15分钟
30分钟
1小时
权限失败

立即通知。

因为无法自动恢复。

6.3 用户通知规则

不要每次失败都通知。

否则：

会变成报警轰炸；
用户很快关闭通知。

推荐：

第一次失败

静默重试。

连续失败3次

通知：

“海外项目日报”连续3次生成失败。
原因：腾讯广告接口超时。
系统将在30分钟后再次尝试。

自动暂停时

通知：

“海外项目日报”已连续失败5次，系统已自动暂停。
你可以：

重新启用
修改模板
检查权限
联系管理员
7. 最终建议：必须建立“数据可信度层”

你现在这个系统，已经不是普通 Chat。

本质是：

AI 数据操作系统

所以必须在：

LLM
↓
语义层
↓
指标层
↓
权限层
↓
数据可信度层
↓
执行层

中间加入：

Data Reliability Layer

负责：

指标标准化
时间默认规则
空结果解释
数据成熟度
回传延迟
权限过滤
报表版本
数据快照
查询可复现性

否则系统一定会出现：

“AI回答看起来像真的，但实际上完全不可信”

这会直接摧毁广告优化师对系统的信任。
